ПРОФИЛЬ И БИОРИТМЫ: КОНТРАКТ ДЛЯ ФРОНТЕНДА
algorithm_version: 1.0.0
Формат эталонного набора: schema_version = 1.

1. Файлы и проверка

contracts/fixtures/biorhythm_vectors.json — входы и ожидаемые снимки /biorhythms/now.
contracts/fixtures/biorhythm_api_examples.json — независимые примеры всех шести маршрутов.
OpenAPI работающего сервера: GET /openapi.json; Swagger UI: /docs.
Подробные формулы опубликованы также в описании GET /api/v1/biorhythms/now.

Генерация из каталога backend:
  uv run python -m scripts.generate_biorhythm_vectors
Проверка актуальности без записи:
  uv run python -m scripts.generate_biorhythm_vectors --check
Проверки паритета:
  Для PowerShell сначала: $env:DEBUG = "false"
  Для POSIX shell сначала: export DEBUG=false
  uv run pytest tests/unit/test_biorhythm_vectors.py
  uv run pytest tests/integration/test_biorhythm_examples.py
Для интеграционного прогона должен работать Docker: тесты запускают отдельные PostgreSQL и Redis.

Генератор не использует случайность, текущие часы, БД или Redis. Все даты фиксированы.
В наборе нет реальных персональных данных. Поле input.profile содержит только данные
для расчёта: это фрагмент профиля, а не полный ответ /me и не подтверждение онбординга.
Каждый API-пример начинается с context заново; выполнять примеры как цепочку не нужно.
UUID/email в примерах заменяются данными текущего пользователя. Access-токен не хранится.

2. Время и вычислительное рождение

birth_date — YYYY-MM-DD, не ранее 1900-01-01 и не позже текущей локальной даты пользователя.
birth_time — HH:mm:ss, секунды только 00; null означает неизвестное время.
Дата и известное время образуют вычислительный момент в UTC. Если время неизвестно,
для вычисления берётся 12:00:00 UTC, но публичное поле остаётся null.
Это соглашение вычисления, а не утверждение о фактическом UTC-моменте рождения.
Текущий timezone — имя IANA. Его изменение не сдвигает вычислительное рождение.
Хронотип и часы работы/сна не меняют три синусоиды.

at — ISO 8601 с Z или UTC-смещением; Unix timestamp и время без пояса не принимаются.
Знак + в query кодируется как %2B (обычный URLSearchParams делает это автоматически).
Ответные at и crossings[].at записаны в UTC с Z; date — локальная дата пользователя.
Вычисления сохраняют точность микросекунды. В JavaScript Date точность — миллисекунды:
для проверки векторов с микросекундами используйте целочисленные микросекунды/BigInt,
а не предварительное округление через Date.parse(). Поле value сравнивается с допуском.

3. Формула, фазы, проценты и направление

t = (at_utc - birth_utc) в фактически прошедших секундах / 86400.
value = sin(2*pi*t/P).
Периоды P в сутках: physical = 23, emotional = 28, intellectual = 33.
Для устойчивости на больших датах можно сначала взять остаток целочисленных
микросекунд по периоду P*86400*1000000; затем перевести долю периода в угол.
Остаток для отрицательного времени должен быть неотрицательным.
Чистый движок допускает время до рождения; HTTP API такие точки отклоняет.

Значение ограничивается [-1, 1]. Если расстояние до -1, -0.5, 0, 0.5 или 1
не превышает 1e-12, значение заменяется этой границей. Фаза определяется после
нормализации, до округления процентов:
  peak:       [0.5, 1]
  rising:     [0, 0.5)
  declining:  (-0.5, 0)
  minimum:    [-1, -0.5]

percent = roundTiesToEven(value * 1000) / 10.
Один десятичный знак; половинные случаи округляются к ближайшему чётному целому.
Пример: value=0.1235 -> 12.4, value=0.1245 -> 12.4.
JavaScript Math.round() не реализует это правило. Операции — над IEEE 754 float64;
округляется результат value*1000, а не строка ранее округлённого value.
Отрицательный ноль заменяется положительным. value=0.49999 даёт percent=50.0,
но фазу rising. Нельзя определять фазу по percent.

trend = up при положительном cos(2*pi*t/P), down при отрицательном.
Если |cos| <= 1e-12: на максимуме down, на минимуме up.
Фаза rising не означает обязательный рост: phase и trend — разные признаки.

4. Критические дни

Для каждого цикла аналитически вычисляются моменты birth_utc + k*P/2 суток.
В API k неотрицателен для допустимых точек после рождения. Само рождение — пересечение k=0.
Локальный день — полуинтервал [начало дня, начало следующего дня). На DST это
не обязательно 24 часа. Пересечение точно на правой границе принадлежит следующему дню.
Принадлежность дню точная, без допуска 1e-12 для времени.
level — число разных циклов с пересечением в этот день, а не число одновременных событий.
kind: level 0 -> none, 1 -> single, 2 -> double, 3 -> triple.
crossings упорядочены по at, затем physical, emotional, intellectual при одинаковом at.
Критичность в снимке/ряде относится ко всему локальному дню, включая часы до пересечения.

5. Маршруты и профиль

Все шесть маршрутов используют Bearer access-токен подтверждённого активного пользователя.
Идентификатор пользователя из тела или query не используется для выбора чужих данных.
Все персональные HTTP-ответы имеют Cache-Control: no-store.

GET /api/v1/me
Возвращает id, email, display_name, profile, onboarding.
Существующий пользователь без профиля: profile=null, next_step=birth_date, не 404.
onboarding содержит completed_at и next_step: birth_date, chronotype, first_tasks либо null.

PATCH /api/v1/me/profile
Разрешены только birth_date, birth_time, timezone, chronotype, work_start, work_end, sleep_time.
Отсутствующее поле сохраняется. Явный null разрешён для birth_date, birth_time, chronotype;
у завершённого профиля очистить birth_date или chronotype нельзя (409 PROFILE_INCOMPLETE).
work_end > work_start в пределах одной локальной даты. Отбой может быть после полуночи.
Ответ — полный актуальный ProfileDocument, как у GET /me.
PATCH не завершает онбординг. Завершение с созданием задач/плана относится к другому модулю.
profile_changed — точка подключения будущего пересчёта; вызов после успешного коммита БД.

GET /api/v1/biorhythms/now?at=...
at необязателен, по умолчанию точные текущие часы сервера. Ответ — BiorhythmSnapshot.
Пример полного ответа в момент рождения 2000-01-01 00:00:00 UTC:
  algorithm_version=1.0.0, timezone=UTC, at=2000-01-01T00:00:00Z, date=2000-01-01;
  все cycles: value=0, percent=0, phase=rising, trend=up;
  critical: level=3, kind=triple, три crossings в этот момент.
Машиночитаемые полные JSON-ответы находятся в biorhythm_api_examples.json.

GET /api/v1/biorhythms?from=YYYY-MM-DD&to=YYYY-MM-DD&step=day|hour
Даты from/to включительны. По умолчанию step=day. Диапазон — от 1 до 62 дней.
day — одна точка в локальный полдень; при повторении полудня берётся ранний момент.
hour — UTC-шаг в один час от начала каждого локального дня, без включения его правой границы.
На следующих локальных сутках сетка начинается заново; при дробном DST между последней
и следующей первой точкой может быть не час. Несуществующая дата/полдень — ошибка 422.
Ответ: algorithm_version, timezone, start, end, step, points, period=null.
Точка: at, date, cycles, critical. Порядок точек хронологический.

GET /api/v1/biorhythms/critical-days?from=YYYY-MM-DD&to=YYYY-MM-DD
Тот же диапазон локальных дат. Ответ: algorithm_version, timezone, start, end, days.
В days только критические даты; отсутствие событий — пустой массив, не ошибка.
Элемент days: date, level, kind, crossings. Проверка рождения использует начало первого дня.

GET /api/v1/biorhythms/forecast?period=day|week|month
period обязателен. Прогноз начинается с текущей локальной даты пользователя.
day — текущий локальный день с часовым шагом; week — текущая дата + 6 следующих, суточный шаг.
month — до соответствующего числа следующего месяца исключительно; если числа нет,
исключительная граница ограничивается последним днём следующего месяца.
Пример: 2024-01-31 -> точки по 2024-02-28 включительно (29 точек).
Ответ имеет форму ряда для графика, но period заполнен.

Момент /now до рождения, первая фактическая точка ряда/прогноза до рождения либо
начало первого дня critical-days до рождения дают 422. Ряд не обрезается молча.
Биоритмы требуют завершённого онбординга; /me и PATCH профиля доступны до завершения.

6. Ошибки и кэш

Единая форма: {"error":{"code":"...","message":"...","details":{...}}}.
401 AUTHENTICATION_REQUIRED — отсутствующий/невалидный токен, неактивная или отозванная сессия.
403 EMAIL_NOT_VERIFIED — email не подтверждён.
409 ONBOARDING_REQUIRED — сначала завершить настройку; перечитать /me и next_step.
409 PROFILE_INCOMPLETE — запрещённая очистка обязательных данных завершённого профиля.
422 VALIDATION_ERROR — некорректные данные; details.fields[] содержит field, code, message.
Имена field: body.birth_date, body.work_end, query.at, query.from, query.to, query.step и т.д.
Пример: {"error":{"code":"VALIDATION_ERROR","message":"Ошибка проверки данных",
"details":{"fields":[{"field":"query.to","code":"RANGE_TOO_LONG",
"message":"Максимальный диапазон — 62 дня"}]}}}.
Клиент выбирает поведение по code, а не по тексту message.

Внутренний Redis-кэш: TTL 86400 секунд. Ключ включает algorithm_version, user_id,
нормализованное рождение, флаг известного времени, текущий пояс и параметры операции.
Изменение рождения/пояса использует новый ключ. Хронотип и режим не меняют синусоиды.
Проверки авторизации и готовности профиля предшествуют чтению кэша.
Повреждённый JSON пересчитывается; при недоступном Redis сервер считает локально.
HTTP no-store не отключает этот внутренний кэш.

7. Паритет, точность и изменения версии

В vectors каждый input.profile + input.at даёт expected формы BiorhythmSnapshot.
expected.value при экспорте округляется до 12 знаков после запятой; API сохраняет полную float64-точность.
Сравнение value: абсолютное расхождение <= 1e-12. Остальные поля сравниваются точно.
Моменты сравниваются как UTC-инстанты с точностью до микросекунды; JSON использует Z.
У процентов сравниваются числа: 50 и 50.0 эквивалентны. Знак нулевого процента положительный.
manual_controls — вручную заданные четверти периодов и границы +/-0.5, привязанные к id вектора.
rounding_controls — отдельные входы функции округления, включая половинные случаи.
Тесты сверяют весь набор со скалярным math.sin и независимо вычисленными пересечениями.
Внешний калькулятор нельзя считать эталоном без совпадения UTC-шкалы рождения, неизвестного
времени, текущего пояса, границ дня, округления и фаз.

При изменении формул, фаз, правил времени, округления или критических дней повышается
ALGORITHM_VERSION в backend/app/modules/biorhythm/config.py. Затем обновляются этот контракт,
векторы и клиентская реализация. Изменение алгоритма требует пересмотра ручных контролей;
одной перегенерации недостаточно. Версия присутствует во всех ответах и ключах Redis.
Ветки фронтенда и бэкенда используют один и тот же файл fixtures; успешный серверный
прогон не заменяет проверку паритета в будущей клиентской реализации.
