ПЛАНИРОВЩИК: ВНУТРЕННИЙ КОНТРАКТ И ПРАВИЛА РЕАЛИЗАЦИИ
Этап 1 из 9. Версия внутреннего контракта: 1.

1. Источники и границы

Основание: раздел 6 исходного backend-плана; разделы 1–11 контракта фронтенда,
в частности профиль, /onboarding/preview и /onboarding/complete; текущие модели ORM.
Раздел 12 фронтендового предложения НЕ используется.

Владимир: planner, суточная энергия, размещение, перерывы, критические дни,
пересчёт, объяснения и адаптеры расчёта/сохранения расписания.
Григорий: CRUD задач, пользовательские статусы, даты, HTTP /tasks и владение
транзакцией изменения задачи. Его публичные схемы здесь не определяются.
Не создаём GET /schedule и новые ошибки из исключённого раздела 12.
Не меняем API биоритмов, его value/percent, фазы и ограничение диапазона 62 дня.
Новые модели ниже — внутренние snapshots, не тела публичного API и не ORM.

2. Точка вызова

ScheduleBuilder(context: PlanContext) -> PlanResult — чистый синхронный вызов.
Без БД, Redis, HTTP, системных часов, случайных UUID и побочных эффектов.
Время передаётся явно. Библиотечная валидация поднимает ValueError; адаптеры
будущих этапов переводят ошибки в существующий общий HTTP-формат.
Сейчас определён контракт вызова; реального алгоритма build_schedule ещё нет.

PlanContext:
  profile: PlanProfile — нормализованные параметры пользователя;
  day: локальная календарная дата;
  now: явный UTC-момент расчёта (вход со смещением нормализуется);
  tasks: неизменяемый набор PlanTask выбранного дня;
  mode: preview, initial или replan;
  fixed_slots: сохранённые интервалы с причиной запрета перемещения.
Владелец данных проверяет авторизацию, принадлежность задач пользователю,
полноту профиля и блокировки ДО создания контекста. Ядро не принимает user_id.

PlanProfile:
  birth_utc: вычислительное рождение из существующего ProfileService;
  timezone: текущий IANA-пояс;
  chronotype: lark/dove/owl;
  work_start/work_end: локальное рабочее окно в пределах одной даты;
  sleep_time: локальный отбой, может быть после полуночи;
  lunch_start/lunch_duration_min: обед, 0 минут отключает его;
  work_days: ISO-дни недели 1–7, без повторов.
Расчёт использует существующие чистые функции biorhythm.engine.
Не вызывать BiorhythmService из preview: его guard требует завершённого
онбординга, тогда как preview разрешён до завершения при полном профиле.

PlanTask:
  ref: ровно один из task_id (UUID) или task_index (целый индекс >= 0);
  kind: intellectual/physical/creative/routine;
  duration_min: строго целое 5–480; 17 минут остаются 17 минутами;
  planned_date: текущая дата контекста;
  priority: high/medium/low;
  status: pending/scheduled/done/skipped;
  preferred_start: локальное пожелание или null;
  deadline: календарная date или null — как в текущей БД;
  is_pinned/pinned_start: признак и точный момент закрепления;
  created_at: момент создания для стабильной сортировки или null у черновика.
В preview используются исходные индексы, без искусственных сохранённых UUID.
В replan — UUID. initial допускает индексы до сохранения либо назначенные UUID;
сопоставление индексов с созданными записями выполняет вызывающий сервис.
Название/описание и правила их редактирования остаются в модуле задач.
Старое pinned_start при is_pinned=false не означает закрепление: решает флаг.

3. Результат

PlanResult:
  day, timezone, algorithm_version;
  slots: хронологически отсортированные PlanSlot;
  unscheduled: ссылки на неразмещённые задачи и reason_codes;
  metrics: requested_min, planned_min, capacity_min, high_intensity_min,
           critical_level, load_factor;
  moves: решения о переносе с from_date/to_date и reason_code;
  status_changes: только реальные переходы pending <-> scheduled;
  warnings: машинный код и необязательные task/target_date.
Версия планировщика будет задана вместе с конфигурацией на этапе 2;
версия уже реализованных биоритмов 1.0.0 не переименовывается.

PlanSlot:
  kind: task/break/lunch/rest;
  interval: полуинтервал UTC [start, end), end > start;
  task: TaskRef только для task, иначе null;
  is_pinned, score, reason_codes, explanation;
  preservation: pinned/done/started/past/system либо null.
Сравнения интервалов выполняются после нормализации в UTC, включая DST fold.
score — конечный числовой рейтинг; это не процент. Предпочтение +0.3 может
поднять рейтинг выше 1, поэтому контракт не ограничивает его единицей.
explanation внутри ядра допускает null; адаптер preview обязан получить
непустое безопасное русское пояснение до публикации ответа.

Обязательные инварианты готового алгоритма:
  - задача неделима; длительность слота равна её duration_min;
  - каждая задача pending/scheduled ровно в одном из slots/unscheduled/moves;
  - done сохраняет свой существующий слот, skipped не планируется заново;
  - фиксированные интервалы сохраняются без изменения;
  - task-слот ссылается на входную задачу; дубликатов и потерянных ссылок нет;
  - слоты не пересекаются; соприкасающиеся полуинтервалы допустимы;
  - будущая работа укладывается в доступное окно, обязательные перерывы и дедлайн;
  - requested_min/прочие минутные метрики неотрицательны;
  - planned_min <= requested_min; неразмещённые задачи не теряются.
Эти инварианты размещения будут реализованы и проверены на этапах 2–7.
Наличие dataclass само по себе не подтверждает допустимость готового плана.

4. Приоритет ограничений и разрешение неоднозначностей

Сначала сохранить историю, done, начавшиеся и закреплённые интервалы.
При их конфликте не двигать их молча: вернуть доменную ошибку для адаптера.
Затем применить рабочее окно, календарь, занятые интервалы, обед/обязательный
отдых, дедлайн и лимиты нагрузки. Только среди допустимых вариантов выбирать
по энергии, пожеланиям и мягкому штрафу за одинаковые типы подряд.
Высокий приоритет и preferred_start не отменяют жёсткие ограничения.

Рабочее окно — жёсткая доступность; скрытый wake_time=07:00 не урезает его.
sleep_time сохраняется как характеристика режима, не создаёт неявного
запрета внутри явно выбранных рабочих часов. work_days ограничивает
автоматический выбор будущих дат и ночную генерацию. Явный расчёт выбранной
даты не запрещается скрытым дефолтом work_days: в частности, онбординг может
завершаться в субботу/воскресенье. Сохранённая история/фиксации сохраняются.

Шаг поиска начал — 15 минут, но длительность и конец НЕ округляются.
Начало сетки привязывается к рабочему окну, а не к полуночи UTC.
Закреплённое начало может быть вне этой сетки и сохраняется точно.
На сегодня новые старты не раньше now; прошлые/начавшиеся слоты не двигаются.
Локальные несуществующие или неоднозначные границы рабочего окна/обеда
не угадываются: использовать существующие ошибки времени на этапе 2.
В preview границы task-слота должны однозначно восстанавливаться из даты,
локальных часов и пояса: формат PlanPreview не передаёт fold/UTC-смещение.
Все сроки проверяются как фактически прошедшее время UTC, не как разность
двух одинаковых настенных часов при переводе стрелок.

Дедлайн date означает окончание соответствующей локальной календарной даты:
задача должна завершиться не позже следующей локальной полуночи.
Это включительная дата, а не придуманный точный timestamp 23:59:59.
Дедлайны с временем и миграцию Task.deadline сейчас не добавляем.

Обед резервируется только в пересечении с рабочим окном. Если он вне окна,
его минуты не вычитаются. Сон/обед через полночь не расширяют рабочее окно.
Пользовательские задачи 5–480 минут неделимы. Перерыв располагается между
целыми задачами или после длинного блока, не разрезает существующую задачу.
Обязательный перерыв между двумя интенсивными задачами — минимум 10 минут.
После блока >90 и <=120 минут — 15 минут; после >120 либо двух подряд
интеллектуальных задач — 30 минут. При совпадении причин берётся максимум,
а не сумма; обед/отдых достаточной длины может закрывать требование перерыва.
Не требуется фиктивный перерыв за последней задачей, если дальнейшей работы нет.
Системные блоки резервируются при поиске, а не вставляются поверх готовых задач.

Профили: lark -1 час, dove 0, owl +3 часа относительно базовой кривой.
Типы связаны с циклами: intellectual->intellectual, physical->physical,
creative->emotional; routine предпочитает менее энергичные интервалы.
Высокий приоритет -> интенсивность -> длительность -> created_at -> UUID;
для черновиков роль стабильного created_at/UUID выполняет исходный индекс.
При равных оценках выбирается самое раннее допустимое UTC-начало.
Не использовать системные часы или случайный tie-break внутри ядра.

Критические коэффициенты: 0=1.0, 1=0.8, 2=0.65, 3=0.5;
minimum хотя бы одного цикла дополнительно умножает коэффициент на 0.9.
Двойной день: один rest 30 минут; тройной: два rest по 30 минут.
Вместимость учитывает фактически зарезервированные системные блоки и
коэффициент, один и тот же перерыв не вычитается повторно.
Лимит интеллектуальных+физических минут: 240 * load_factor.
Плотность >85% вместимости — предупреждение, а не предварительный вычет 15%.
Правила определения цикла для дневного minimum и округления вместимости
фиксируются при реализации нагрузки: локальный полдень, округление минут вниз.

Автопереносы: только незакреплённые intellectual/physical в критический день,
если приоритет high либо длительность >=60 и дедлайн допускает перенос.
Искать среди следующих 7 дней без критичности, с подходящим циклом и реальным
свободным непрерывным интервалом. Нельзя считать неизвестный будущий день пустым.
До этапа 6 данных доступности следующих дней в PlanContext нет: такие решения
пока не рассчитываются. Этап 6 добавит явный read-only контекст будущих дней.
Если дня нет, задача остаётся на исходной дате и размещается по её ограничениям
либо попадает в unscheduled; потеря задачи или бессрочное ожидание недопустимы.
Применение TaskMove/изменение planned_date — обязанность общей транзакции CRUD.

5. Preview, completion и интеграция с задачами

preview: только индексы, без записи задач/плана/профиля, без автопереносов,
без TaskStatusChange. Каждая задача ровно один раз в slots или unscheduled.
Адаптер возвращает только task-слоты в PlanPreview: task_index,
start_time/end_time (локальные HH:mm:ss), непустое explanation.
Если реальные ограничения мешают части задач, HTTP 200 и неразмещённые индексы.
Если сумма длительностей больше рабочего окна, HTTP 422 body.tasks по контракту.
Проверка planned_date == сегодняшняя локальная дата — в сервисе, не в ядре.

initial: первый сохраняемый план. Для completion все задачи должны поместиться;
иначе адаптер поднимает 409 PLAN_CAPACITY_EXCEEDED и транзакция откатывается.
Не переносить первые задачи на другую дату для обхода этой проверки.
Повторная проверка контекста, идемпотентность и запись completed_at — у сценария
completion, не у чистого ядра. Полностью этот сценарий сейчас не реализуется.

replan: сохранённые UUID, история/фиксации, явный now. После расчёта вызывающий
сервис применяет разрешённые изменения pending/scheduled и TaskMove.
Пользовательские done/skipped и completed_at остаются ответственностью CRUD.

Будущий интеграционный вызов:
  открыть одну транзакцию и захватить общий lock пользователя/даты;
  применить изменение задачи без commit;
  прочитать согласованные профиль, задачи и существующие слоты;
  вызвать ScheduleBuilder(PlanContext(...));
  сохранить новую версию расписания и применить согласованные изменения задач;
  при переносах заблокировать даты в одном порядке, пересчитать затронутые дни;
  выполнить один внешний commit. При любой ошибке откатить всё.
Планировщик/его repository не делает самостоятельный commit.
Посткоммитный profile_changed не заменяет этот синхронный вызов для CRUD.

6. Границы готовности первого этапа

Реализованы модели и защитные проверки их структуры, а не распределение задач.
Нет маршрутов, миграций, заглушки успешного планирования и изменений задач в БД.
Дальше: временная сетка (этап 2), энергия (3), ограничения (4), размещение (5),
критичность/объяснения (6), пересчёт (7), сервисы/preview (8), итоговая приёмка (9).
