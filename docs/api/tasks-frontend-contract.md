# CRUD задач: ограничения и подключение фронтенда

Дата: **18 ноября 2026 года**. Шаг 2 задачи. Основание — [сверка текущего кода](tasks-schedule-audit.md).

**Статус:** серверные правила и пакет для согласования подготовлены. Подтверждение фронтендера и изменения UI ещё не получены. Документ описывает существующий API; серверные ограничения и интеграция Core на этом шаге не меняются.

## 1. Решения для текущей интеграции

Сохраняем текущий CRUD и его ответы. Фронтенд адаптирует запросы к нему, используя отдельные транспортные типы вместо отправки объекта формы целиком. Создание и изменение возвращают задачу, удаление — пустой ответ. Чтение расписания будет отдельным методом; на этом шаге он ещё не реализован.

| Предмет согласования | Решение со стороны бэкенда | Что требуется от фронтенда |
| --- | --- | --- |
| Поля записи | Только семь полей из раздела 2; PATCH дополнительно требует `version` | Собирать тело по списку разрешённых полей; не копировать в него весь `Task` |
| Предпочтительное время и закрепление | `preferred_start`, `is_pinned`, `pinned_start` доступны только в ответе | Не отправлять даже `null`/`false`; скрыть или отключить ввод в сценарии реального сохранения, сохранив отображение существующего закрепления |
| Прошлые даты | CRUD допускает прошлую дату задачи и просроченный дедлайн | Убрать запреты относительно `today`/`now` из модели и HTML-ограничений; оставить проверку формата и взаимного порядка дат |
| Лимиты | Название — 1–200 Unicode code points после trim; длительность — целое 5–480; явного максимума описания нет | Для названия учитывать code points (`Array.from(title.trim()).length`), не вводить другой предел описания или длительности |
| Повторы и напоминания | `TaskFormOptions` не является частью CRUD; индивидуальные настройки не сохраняются этим API | Не объединять options с запросом и не обещать их сохранение; отключить эти настройки в API-сценарии. Глобальные настройки уведомлений этим решением не меняются |
| Версия и статус | Итог назначает сервер с учётом подключённого пересчёта | После ответа заменить локальную задачу серверной; не вычислять `version + 1` и не подставлять `pending` |
| Расписание | Не входит в ответ записи задачи | После появления GET расписания перечитывать план отдельно; не ожидать `{task, schedule, changes}` |

Это список решений для подтверждения совместимости, а не свидетельство уже выполненных правок фронтенда.

## 2. Поля и форматы запросов

Префикс `/api/v1`, JSON, существующий Bearer. Для записи нужен профиль с корректным IANA-поясом; завершение онбординга для CRUD не обязательно. Для защищённых запросов email должен быть подтверждён. Все ответы используют `Cache-Control: no-store`.

| Поле | POST `/tasks` | PATCH `/tasks/{task_id}` |
| --- | --- | --- |
| `title` | Обязательно, строка 1–200 после trim | Необязательно, те же ограничения; `null` запрещён |
| `description` | Строка или `null`; default `null` | Необязательно; `null` очищает, пустая строка допустима |
| `type` | Обязательно: `intellectual`, `physical`, `creative`, `routine` | Необязательно; `null` запрещён |
| `priority` | `high`, `medium`, `low`; default `medium` | Необязательно; `null` запрещён |
| `duration_min` | Обязательное целое 5–480; строка, дробь и bool запрещены | Необязательно, те же ограничения; `null` запрещён |
| `planned_date` | Обязательная календарная дата `YYYY-MM-DD` | Необязательно; `null` запрещён |
| `deadline` | ISO 8601 с датой, временем и явным смещением либо `null`; default `null` | Необязательно; `null` очищает |
| `version` | Не принимается | Обязательное целое от 1, полученное из последнего ответа задачи |

Пропуск поля PATCH сохраняет прежнее значение. Тело только с `version` недопустимо; минимум одно изменяемое поле обязательно. Неизвестные поля дают `422 VALIDATION_ERROR`. Клиентский ID, `status`, `completed_at`, `created_at`, `updated_at`, `user_id` и поля закрепления в записи запрещены.

`planned_date` — дата в поясе профиля. Локальная дата `deadline` в этом же поясе не может быть раньше `planned_date`. Проверяется итоговое состояние после PATCH, включая не переданные заново значения. Поэтому при переносе за старый дедлайн нужно одновременно изменить или очистить дедлайн.

`datetime-local` преобразуется в момент в **поясе профиля**, затем отправляется с `Z` или явным смещением. Сервер возвращает UTC с `Z`. Дата без времени и момент без смещения для дедлайна запрещены. Существующее сохранение исходного момента при редактировании, включая секунды и DST, нужно сохранить.

Проверка возможности размещения остаётся планировщику: корректная длительность CRUD не означает, что задача обязательно поместится в день. Отсутствие места само по себе не является основанием ужесточать поле `duration_min` или запрещать сохранение формы.

## 3. Транспортные типы и ответы

Ниже — образец типов для отдельной фронтендовой правки, не изменение `frontend/src` на этом шаге. Строковые форматы и числовые границы проверяются во время выполнения.

```ts
type TaskType = 'intellectual' | 'physical' | 'creative' | 'routine'
type TaskPriority = 'high' | 'medium' | 'low'
type TaskStatus = 'pending' | 'scheduled' | 'done' | 'skipped'

type TaskCreateRequest = {
  title: string
  description?: string | null
  type: TaskType
  priority?: TaskPriority
  duration_min: number
  planned_date: string
  deadline?: string | null
}

// На сервере дополнительно проверяется наличие хотя бы одного изменяемого поля.
type TaskUpdateRequest = Partial<TaskCreateRequest> & { version: number }
type TaskStatusRequest = { version: number }

type TaskResponse = Required<TaskCreateRequest> & {
  id: string
  status: TaskStatus
  completed_at: string | null
  version: number
  created_at: string
  updated_at: string
  preferred_start: string | null
  is_pinned: boolean
  pinned_start: string | null
}

type TaskList = {
  items: TaskResponse[]
  total: number
  limit: number
  offset: number
}
```

Все поля `TaskResponse` обязательны; nullable-поля присутствуют со значением `null`. `preferred_start` — локальное `HH:mm:ss`; дедлайн, выполнение, создание, обновление и `pinned_start` — UTC-моменты. Внутренние поля ORM в ответ не входят. Неизвестные дополнительные поля ответа клиент игнорирует.

POST возвращает `201 TaskResponse`; PATCH и команды статуса — `200 TaskResponse`. DELETE `/tasks/{task_id}?version=N` возвращает `204`, JSON разбирать не нужно. До завершения онбординга задача может сохраниться без плана. После завершения включён пересчёт: статус, дата и версия берутся из итогового ответа.

GET `/tasks` возвращает `TaskList`. Допустимы `date` либо включительный `from`/`to` (можно одну границу), `status`, `type`, `limit` (1–100, default 50), `offset` (от 0, default 0). `date` с диапазоном, обратный диапазон, повторы и неизвестные параметры дают `422`. Клиент учитывает `total`, а не считает первую страницу полным списком.

## 4. Примеры запросов

Примеры независимы друг от друга. Число `7` означает ранее прочитанную версию конкретной задачи, а не ожидаемую версию после предыдущего примера.

### Создание — `TaskCreate`

POST `/api/v1/tasks`:

```json
{
  "title": "Подготовить отчёт",
  "type": "intellectual",
  "duration_min": 60,
  "planned_date": "2026-11-18",
  "deadline": "2026-11-18T18:00:00+05:00"
}
```

При поясе профиля `Asia/Yekaterinburg` дедлайн ответа — `2026-11-18T13:00:00Z`. ID, статус и версия берутся из ответа.

### Изменение названия и очистка описания — `TaskPatch`

PATCH `/api/v1/tasks/{task_id}`:

```json
{
  "version": 7,
  "title": "Обновить отчёт",
  "description": null
}
```

### Перенос с очисткой старого дедлайна — `TaskPatch`

PATCH `/api/v1/tasks/{task_id}`:

```json
{
  "version": 7,
  "planned_date": "2026-11-19",
  "deadline": null
}
```

### Выполнение — `TaskStatusCommand`

POST `/api/v1/tasks/{task_id}/complete`:

```json
{
  "version": 7
}
```

`/skip` и `/reopen` принимают такое же тело. `complete` и `skip` применяются к `pending`/`scheduled`; для перехода из `done` в `skipped` или обратно сначала нужен `reopen`. Возврат в работу может сразу привести к `scheduled` после пересчёта. Прямой PATCH статуса не используется.

## 5. Ошибки и повторные запросы

Формат ошибки: `{error: {code, message, details}}`. Для валидации `details.fields[]` содержит `field`, `code`, `message`; путь поля включает источник, например `body.deadline`. Конфликт не возвращает актуальную задачу внутри ошибки — её нужно перечитать.

| Код | Действие клиента |
| --- | --- |
| `401 AUTHENTICATION_REQUIRED` | Использовать существующее обновление авторизации/повторный вход |
| `403 EMAIL_NOT_VERIFIED` | Предложить подтверждение email |
| `409 PROFILE_INCOMPLETE` | Перечитать `/me`, заполнить timezone через существующий профиль |
| `409 TASK_VERSION_CONFLICT` | Сохранить черновик, перечитать задачу, предложить повторное применение изменений; не перезаписывать автоматически |
| `409 TASK_PINNED` | Не менять поля размещения закреплённой задачи; ввод pin/unpin в этот API не добавлен |
| `409 TASK_STATUS_CONFLICT` | Перечитать задачу и обновить доступные действия |
| `404 TASK_NOT_FOUND` | Показать недоступность задачи и обновить список; чужой и удалённый ID выглядят одинаково |
| `422 VALIDATION_ERROR` | Показать сообщения полей, сохранить введённые значения |
| Другой `409`, включая `CONFLICT` планировщика | Показать сообщение, перечитать актуальные данные; не выдавать операцию за успешную |
| `503 PLANNER_UNAVAILABLE` | Показать временную недоступность; при неоднозначном исходе проверить состояние перед повторной записью |

При потере ответа записи сначала проверить состояние. CRUD не поддерживает клиентский ID и `Idempotency-Key`; автоматический повтор создания после сетевой ошибки способен создать дубликат. Это не меняет отдельную идемпотентность онбординга.

Повтор совпадающих полей или команды с актуальной версией может вернуть задачу без изменений. Устаревшая версия конфликтует и в таком случае. Версию всегда получать из ответа, а не увеличивать локально.

## 6. Передача фронтендеру и критерии подтверждения

| Расхождение из сверки | Конкретная фронтендовая работа |
| --- | --- |
| F-01, F-07 | Разделить типы запроса/ответа, собирать тело по разрешённым ключам, добавить служебные моменты в транспортный ответ |
| F-02, F-03 | Согласовать разрешённые сервером прошлые даты; изменить проверки модели и HTML `min`, сохранив проверку порядка дня задачи и дедлайна |
| F-04 | Считать длину названия по code points; проверить граничные значения и emoji |
| F-05 | Отключить неподдерживаемые настройки при реальном сохранении; не сообщать об их сохранении |
| F-06 | Отдельно подключить клиенты CRUD, команды статуса, обработку конфликтов и пагинацию; заменить локальный предпросмотр реальной записью |
| S-01–S-03 | Учесть отдельный будущий GET и различие транспортного DTO и модели таймлайна; окончательный контракт чтения оформляется на шаге 3 |

Для проверки согласованного поведения нужны: обычное создание без read-only полей; название длиной 200/201 и длительность 5/480 против 4/481; прошлые даты; дедлайн в поясе профиля; очистка nullable-полей; перенос с изменением/очисткой дедлайна; конфликт версии с сохранением черновика; итоговый `scheduled` и версия из ответа; удаление без разбора JSON. Работа с историческими слотами, чьи задачи уже недоступны через CRUD, остаётся отдельным вопросом подключения таймлайна из сверки.

**Готовность серверной части шага 2:** правила, транспортные типы, примеры и список адаптаций подготовлены. Для завершения именно совместного согласования фронтендер должен подтвердить решения раздела 1 либо перечислить возражения по ID F-01–F-07. Подтверждение в текущей работе не получено; отправка сообщений команде и правки фронтенда не выполнялись.
