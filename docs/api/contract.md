# Единый API-контракт Perfect Day · v1

Версия: **1.0**, 6 ноября 2026 года. Единый источник требований для фронтенда и бэкенда в области авторизации, профиля и онбординга. Документ объединяет прежний контракт auth и предложение по профилю. Названия и смысл полей, статусы, ошибки и правила повторов ниже фиксируются для `/api/v1`.

Это целевой контракт, а не утверждение о готовности всех методов. Авторизация реализована; профиль и завершение онбординга предстоит реализовать. Перед совместным выпуском владельцы фронтенда и бэкенда проверяют реализацию по этому документу. Документ не заменяет проверку совместимости тестами.

Дополнение от 11 ноября 2026 года: раздел 12 — **предложение фронтенда, требует согласования с бэкендом**. Он описывает данные для графиков биоритмов, форм задач и суточного таймлайна. Этот раздел не означает готовность API и не меняет существующие методы разделов 1–11.

## 1. Область действия и совместимость

В v1 входят email/password-аутентификация, подтверждение email, сессии, восстановление и смена пароля, профиль, сохранение шагов, предпросмотр и завершение онбординга с первыми задачами. Социальный вход и тест хронотипа сюда не входят. API чтения сохранённого расписания, создания/редактирования задач и биоритмов описан как несогласованное предложение в разделе 12; до согласования он также вне утверждённой области v1. Раздел предпросмотра добавлен как совместимое расширение v1; существующие схемы профиля и завершения не меняются.

Совместимые расширения v1: новые маршруты и необязательные поля ответов. Клиент игнорирует неизвестные поля ответов. Удаление или переименование полей, изменение типов, обязательности, перечислений, семантики ошибок и успешных статусов требуют `/api/v2` либо отдельного согласованного плана миграции. Новое обязательное поле запроса не добавляется в v1. Изменение политики лимитов и сроков безопасности документируется; клиент использует `expires_in` и `Retry-After`, а не зашитые значения.

| Область | Бэкенд | Фронтенд |
| --- | --- | --- |
| Auth, все 12 методов | Реализован | Регистрация, login, verify, resend, refresh и logout подключены; остальные экраны подключаются отдельно |
| GET `/me` | Не реализован | Клиент и локальная заглушка готовы |
| PATCH `/me/profile` | Не реализован | Клиент и локальная заглушка готовы |
| POST `/onboarding/preview` | Не реализован | Клиент и предварительная локальная раскладка готовы |
| POST `/onboarding/complete` | Не реализован | Клиент и локальная заглушка готовы |

## 2. Общие правила HTTP и форматов

- Базовый путь: `/api/v1`. Пути в таблицах указаны относительно него. JSON — UTF-8, `Content-Type: application/json`. Исключение: login принимает `application/x-www-form-urlencoded`.
- Защищённые методы принимают `Authorization: Bearer <access_token>`. Cookie не заменяет Bearer для профиля, онбординга и управления сессиями.
- Все обязательные поля передаются явно. Неизвестные поля JSON-запросов отклоняются с `422 VALIDATION_ERROR`. Неизвестные поля ответов игнорируются клиентом.
- Идентификаторы пользователя и сессии — строки UUID. Пользователь определяется авторизацией; `user_id` в запросах профиля не передаётся.
- Моменты времени — ISO 8601 с UTC-смещением (`Z` или `+00:00`). Календарные даты — `YYYY-MM-DD`, локальное время — `HH:mm:ss` без смещения. Эти локальные значения нельзя автоматически преобразовывать в UTC на клиенте.
- Текущий часовой пояс пользователя — IANA-имя, например `Asia/Yekaterinburg`. Он нужен для расписания и текущей даты и определяется браузером при сохранении первого шага. Отдельного часового пояса рождения в интерфейсе и публичном API нет.
- Ответы с токенами и персональными данными профиля/сессий: `Cache-Control: no-store`. Ответ `204` не содержит тела. Клиент не пытается разобрать его как JSON.
- Email валидируется, пробелы по краям удаляются, значение приводится к нижнему регистру; уникальность регистронезависима. Пароли и токены не обрезаются и не нормализуются.

### Общая ошибка

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Ошибка проверки данных",
    "details": {
      "fields": [
        { "field": "body.password", "code": "string_too_short", "message": "Слишком короткая строка" }
      ]
    }
  }
}
```

`error.code` и `error.message` обязательны. Сервер возвращает `details` как объект, при отсутствии подробностей — `{}`; для ошибок полей это объект с `fields`. Клиент устойчив к отсутствующему или null `details` в ответах промежуточной инфраструктуры. Путь поля включает источник и индекс: `body.birth_date`, `body.tasks.0.duration_min`, `header.idempotency-key`. Клиент принимает неизвестные коды и показывает безопасное `message`. Текст сообщения не используется для принятия решений. Ошибки не содержат введённый пароль, токен, исходное тело, traceback, `ctx` или внутренние тексты исключений. Неизвестный тип ошибки валидации получает сообщение «Некорректное значение».

| HTTP | Общий код | Назначение |
| --- | --- | --- |
| 401 | `AUTHENTICATION_REQUIRED` | Нет действующей авторизации; заголовок `WWW-Authenticate: Bearer` |
| 404 | `NOT_FOUND` | Неизвестный маршрут |
| 405 | `METHOD_NOT_ALLOWED` | Неверный метод; сохраняется `Allow` |
| 422 | `VALIDATION_ERROR` | Некорректные поля, типы или формат запроса |
| 429 | `RATE_LIMIT_EXCEEDED` | Ограничение частоты; `Retry-After` в секундах |
| 500 | `INTERNAL_ERROR` | Непредвиденная ошибка с безопасным сообщением |
| 503 | `SERVICE_UNAVAILABLE` | Недоступна необходимая инфраструктура |

Обработчики сохраняют `WWW-Authenticate`, `Allow`, `Retry-After`. В production `DEBUG=false`. Диагностический `/ready` имеет отдельный формат, описанный в разделе 11.

## 3. Авторизация

Пароль: 8–128 символов, минимум одна буква и одна цифра. Политика применяется при регистрации, сбросе и смене пароля. Хэширование — Argon2 через `pwdlib`; access — JWT HS256 через PyJWT, секрет из окружения. Подробности границ модуля: [ADR 0005](../../backend/docs/adr/0005-auth-boundaries.md).

### Методы

| Метод и путь | Запрос и авторизация | Успех |
| --- | --- | --- |
| POST `/auth/register` | JSON `{email, password}`, доверенный Origin | 202 `MessageResponse`; сессия не выдаётся |
| POST `/auth/resend-verification` | JSON `{email}`, доверенный Origin | 202 `MessageResponse` |
| POST `/auth/verify-email` | JSON `{token}`, доверенный Origin | 200 `TokenResponse` + refresh-cookie |
| POST `/auth/login` | Form `username=email`, `password`, необязательный `grant_type=password`; доверенный Origin | 200 `TokenResponse` + refresh-cookie |
| POST `/auth/refresh` | Refresh-cookie, доверенный Origin; без тела и обязательного access | 200 `TokenResponse` + новая refresh-cookie |
| POST `/auth/logout` | Refresh-cookie, доверенный Origin; access не требуется | 204; отзыв текущей сессии и очистка cookie |
| POST `/auth/logout-all` | Bearer; без тела | 204; отзыв всех сессий и очистка cookie |
| GET `/auth/sessions` | Bearer | 200 `SessionsResponse` |
| DELETE `/auth/sessions/{id}` | Bearer; UUID сессии | 204; отзыв своей сессии, для текущей очистка cookie |
| POST `/auth/password/forgot` | JSON `{email}`, доверенный Origin | 202 `MessageResponse` |
| POST `/auth/password/reset` | JSON `{token, new_password}`, доверенный Origin | 204; смена пароля, отзыв всех сессий, очистка cookie |
| POST `/auth/password/change` | Bearer, JSON `{old_password, new_password}` | 204; смена пароля, отзыв всех сессий, очистка cookie |

Все поля тел auth — строки. Email-токен: 1–256 символов; `old_password`: 1–128. Form-login использует правила существующего OAuth2PasswordRequestForm, а не JSON-схему. Социальный вход и выдача refresh в JSON для мобильного клиента не предусмотрены.

### Ответы

`TokenResponse`:

```json
{ "access_token": "<jwt>", "token_type": "bearer", "expires_in": 900 }
```

`expires_in` — положительное целое число секунд. Refresh никогда не передаётся в JSON. Auth-ответ не содержит пользователя, профиль или статус онбординга: после login/verify клиент запрашивает `/me`.

`MessageResponse`:

```json
{ "message": "Если действие доступно для указанного адреса, письмо будет отправлено" }
```

Register, resend и forgot возвращают нейтральный `202`, не раскрывающий наличие адреса. Регистрация существующего адреса не меняет пароль, не создаёт сессию и не отправляет новое письмо. Профиль при регистрации не создаётся. Повторная отправка подтверждённому адресу не создаёт новый токен. Forgot отправляет письмо только активной подтверждённой учётной записи. Технические сбои и лимиты по-прежнему возвращают соответствующие ошибки.

`SessionsResponse`:

```json
{
  "items": [
    {
      "id": "33fbd053-f913-413e-917a-ae31814cefa6",
      "created_at": "2026-11-06T08:00:00Z",
      "expires_at": "2026-12-06T08:00:00Z",
      "last_used_at": "2026-11-06T09:00:00Z",
      "ip": "127.0.0.1",
      "user_agent": "Mozilla/5.0",
      "is_current": true
    }
  ]
}
```

Список содержит только активные сессии текущего пользователя по убыванию `last_used_at`, без пагинации. ID стабилен при ротации. `ip` и `user_agent` могут быть null, обновляются при refresh и не являются условиями авторизации. Чужая и отсутствующая сессия одинаково дают `404 SESSION_NOT_FOUND`. Повторный отзыв своей другой сессии допустим, пока сессия вызывающего активна. Отзыв текущей делает её Bearer недействительным, поэтому следующий запрос с ним даёт `401`. Logout с отсутствующей или недействительной cookie остаётся идемпотентным: `204` и очистка cookie.

### Ошибки auth

| HTTP | Код | Сценарий |
| --- | --- | --- |
| 401 | `INVALID_CREDENTIALS` | Неправильный email или пароль |
| 403 | `EMAIL_NOT_VERIFIED` | Правильный пароль, но email не подтверждён |
| 400 | `INVALID_EMAIL_TOKEN` | Повреждённый, истёкший, использованный токен или токен другого назначения |
| 401 | `INVALID_REFRESH_TOKEN` | Отсутствующий, истёкший, отозванный или повторно использованный refresh |
| 400 | `INVALID_CURRENT_PASSWORD` | Неверный старый пароль |
| 404 | `SESSION_NOT_FOUND` | Чужая или отсутствующая сессия |
| 403 | `CSRF_ORIGIN_DENIED` | Источник не разрешён |

Дополнительно действуют общие `422`, `429`, `503`. Ошибка login не запускает refresh и не повторяется автоматически.

### Письма и смена пароля

Ссылки: `${FRONTEND_URL}/verify-email#token=...` и `${FRONTEND_URL}/reset-password#token=...`. Клиент читает fragment, убирает токен из адресной строки и передаёт его в тело соответствующего POST. GET ссылки не меняет состояние; подтверждение выполняется явным действием пользователя.

Назначения токенов разделены: `verify_email` действует 24 часа, `reset_password` — 60 минут по умолчанию. Они одноразовые; в БД хранится SHA-256. Resend/forgot аннулирует прежний токен того же назначения. Токен подтверждения не подходит для сброса и наоборот. Одновременные подтверждения сериализуются; только одно успешно.

Пользователь и токен сначала фиксируются в PostgreSQL, затем письмо ставится в Celery. Сбой публикации даёт `503`; созданная неподтверждённая учётная запись сохраняется. Пользователь может запросить resend. Если публикация регистрации не удалась, немедленный resend допускается. Сетевая неопределённость не гарантирует, что письмо не поставлено в очередь. SMTP-задача имеет до трёх повторов с задержкой; email и токен скрыты в представлении аргументов и ошибках. Сообщения брокера содержат необходимые данные доставки и находятся в доверенной инфраструктуре.

Reset/change атомарно меняют пароль, отзывают все сессии и аннулируют остальные ссылки сброса. Ответ — пустой `204`, очистка cookie, `Cache-Control: no-store`. Автовход не выполняется; нужен новый login.

## 4. Cookie, CORS и жизненный цикл сессии

Cookie называется `refresh_token`: `HttpOnly`, `SameSite=Strict`, `Path=/api/v1/auth`, без `Domain`. `Secure=true` на staging/production; false допускается только для локального HTTP и тестов. Срок cookie — остаток абсолютного срока сессии. Удаление использует то же имя и путь.

Access по умолчанию действует 15 минут, отдельная сессия после login/verify — 30 дней. Refresh не продлевает абсолютный срок сессии. Ротация атомарна; повтор старого refresh отзывает всю сессию. Конкурирующие refresh не создают две действующие ветки. PostgreSQL — источник истины для отзыва; положительное состояние сессии не кэшируется в Redis. Отзыв сессии немедленно лишает силы её access.

CORS разрешает точные `CORS_ORIGINS` и credentials, без wildcard. Локально фронтенд `http://localhost:5173`, API `http://localhost:8000`; не смешивать `localhost` и `127.0.0.1`. Стенд — один сайт по HTTPS, в том числе допустимые поддомены. Для прямого cross-origin доступа браузера сервер открывает чтение `Retry-After`; через Vite `/api`-proxy expose не требуется.

Публичные изменяющие состояние auth POST из таблицы требуют точного доверенного Origin. При его отсутствии проверяется origin Referer. `Origin: null`, недоверенный источник и отсутствие обоих заголовков дают `403 CSRF_ORIGIN_DENIED`. Bearer-only методы не принимают cookie вместо access и не требуют этой cookie-проверки Origin. Ручным клиентам и Swagger для публичных auth POST нужен разрешённый Origin.

Обязательное поведение клиента:

1. Access хранится только в памяти. Пароль, access, refresh и email-токен не сохраняются в localStorage/sessionStorage. Auth fetch использует `credentials: 'include'`.
2. При загрузке приложения выполняется один refresh, затем `/me`. До ответа маршруты ждут восстановления. `401` refresh переводит на вход; сеть/`503` показывают повтор восстановления без потери черновика.
3. `401` защищённого запроса запускает один сериализованный refresh, затем максимум один повтор исходного запроса. Параллельные запросы используют общий результат. Сам refresh, login и verify не получают автоматических повторов. Сетевая ошибка refresh может означать уже выполненную ротацию.
4. Refresh сериализуется между вкладками через Web Locks. В текущей реализации без Web Locks гарантируется сериализация только внутри вкладки; это ограничение клиента, не разрешение параллельной ротации сервером. Вход/выход синхронизируются через BroadcastChannel.
5. Окончательный `401` завершает локальную авторизацию. `403`, `422`, `429`, сеть и `5xx` не превращаются в успешный ответ или ложный выход. Поздний ответ старого запроса не восстанавливает сессию после выхода или смены аккаунта.
6. Выход сначала подтверждается серверным logout. При сетевой ошибке клиент сообщает о ней и даёт повторить; не сообщает об успешном отзыве. После успеха очищаются access, профиль, Query cache и текущий черновик, закрываются защищённые маршруты.
7. После `/me` новый пользователь идёт на `next_step`, завершивший настройку — на исходный запрошенный внутренний URL с query/hash либо на `/today`. Внешний URL возврата не принимается. Переход напрямую на более поздний шаг возвращает к необходимому; назад к сохранённым шагам идти можно. Начальный экран знакомства не требует отдельного серверного шага.

## 5. Профиль: GET `/me`

Bearer обязателен. Успех: `200 ProfileDocument`, включая новый аккаунт без профиля. Отсутствие строки профиля не является `404`. Все три метода профиля/онбординга возвращают одну схему.

Новый аккаунт:

```json
{
  "id": "b7b6cdd4-0d1b-43ad-b657-e1f7f9a6766c",
  "email": "anna@example.com",
  "display_name": null,
  "profile": null,
  "onboarding": { "completed_at": null, "next_step": "birth_date" }
}
```

Сохранённый профиль:

```json
{
  "id": "b7b6cdd4-0d1b-43ad-b657-e1f7f9a6766c",
  "email": "anna@example.com",
  "display_name": "Анна",
  "profile": {
    "birth_date": "2003-09-20",
    "birth_time": null,
    "timezone": "Asia/Yekaterinburg",
    "chronotype": "owl",
    "work_start": "12:00:00",
    "work_end": "22:00:00",
    "sleep_time": "01:00:00"
  },
  "onboarding": { "completed_at": null, "next_step": "first_tasks" }
}
```

Все показанные ключи обязательны в ответе. `display_name` — строка или null; при null интерфейс использует email. `profile` — null либо объект со всеми перечисленными ключами. `birth_date`, `birth_time`, `chronotype` nullable до заполнения; неизвестное время рождения остаётся null и не мешает завершению. `timezone`, `work_start`, `work_end`, `sleep_time` не null. При создании профиля значения по умолчанию: `timezone=UTC`, `work_start=08:00:00`, `work_end=18:00:00`, `sleep_time=23:00:00`. Клиент первого шага явно передаёт текущий пояс браузера.

| Условие | `completed_at` | `next_step` |
| --- | --- | --- |
| Нет профиля или даты рождения | null | `birth_date` |
| Есть дата, но нет хронотипа или валидного режима | null | `chronotype` |
| Профиль заполнен, завершение не подтверждено | null | `first_tasks` |
| Завершение подтверждено | UTC timestamp | null |

Состояния проверяются в указанном порядке; завершённый профиль всегда остаётся полным. `completed_at` и `next_step` назначаются только сервером. Начальные часы не означают автоматически выбранный хронотип. Черновик клиента не изменяет серверный прогресс.

## 6. Сохранение шагов: PATCH `/me/profile`

Bearer обязателен. Успех: `200 ProfileDocument`. Метод создаёт профиль, если его ещё нет, и атомарно применяет переданные поля. Разрешены только `birth_date`, `birth_time`, `timezone`, `chronotype`, `work_start`, `work_end`, `sleep_time`. `display_name` доступен в ответе, но редактирование имени этим контрактом не предусмотрено.

Отсутствующее поле сохраняет прежнее значение. Null очищает только nullable-поля: `birth_date`, `birth_time`, `chronotype`. Пустой объект допустим, создаёт профиль с начальными значениями и не завершает онбординг. Ошибка в одном поле откатывает весь PATCH. Проверяется итоговое состояние с учётом сохранённых полей. Для завершённого профиля очищать `birth_date` или `chronotype` нельзя: `409 PROFILE_INCOMPLETE`, состояние не меняется. Валидное редактирование завершённого профиля сохраняет `completed_at` и `next_step=null`.

Первый шаг:

```json
{ "birth_date": "2003-09-20", "birth_time": null, "timezone": "Asia/Yekaterinburg" }
```

- `birth_date`: существующая дата от `1900-01-01` до текущей даты включительно в итоговом `timezone`.
- `birth_time`: `HH:mm:ss`, секунды `00`, от `00:00:00` до `23:59:00`, либо null. UI редактирует часы и минуты.
- `timezone`: валидное IANA-имя; пустая строка и null недопустимы. Это текущий пояс расписания, а не место рождения.
- `birth_timezone`, `birth_tz`, `birth_at_utc`, `birth_time_known`, `user_id`, `onboarding` и `completed_at` не принимаются из тела.

Совместимость с существующей БД: серверу предстоит заполнять внутренние `birth_tz=UTC` и `birth_at_utc` из даты и времени в фиксированной вычислительной шкале UTC; если время неизвестно, использовать 12:00 и `birth_time_known=false`. При указанном времени — `birth_time_known=true`. Это соглашение для расчёта, а не утверждение о реальном UTC-моменте рождения. Текущий `timezone` не используется для восстановления исторического места рождения; его изменение не меняет вычислительную дату рождения. Эти поля не раскрываются в DTO и не запрашиваются у пользователя. Существующие миграции не переписываются; реализацию такого преобразования и тесты добавляет владелец профиля. Текущий DB constraint завершения требует заполненного `birth_at_utc`.

Второй шаг:

```json
{ "chronotype": "owl", "work_start": "12:00:00", "work_end": "22:00:00", "sleep_time": "01:00:00" }
```

`chronotype`: `lark`, `dove`, `owl`. Сервер назначает `chronotype_source=manual`. Время — `HH:mm:ss`, секунды `00`. Рабочее окно в пределах одной локальной даты, `work_end > work_start`; пересечение полуночи не поддерживается. Отбой может быть после полуночи, его нельзя сравнивать строкой с концом рабочего дня. PATCH одного хронотипа не перезаписывает часы: клиент явно передаёт выбранный режим.

Режимы выбора интерфейса: `lark` — 08–18, отбой 23:00; `dove` — 09–19, отбой 23:30; `owl` — 12–22, отбой 01:00. Пользователь может менять часы. Предпросмотр окон справа является примером, а не ответом планировщика. Существующие подписи карточек слева не являются API-полями. Алгоритм биоритмов не определяется этим контрактом.

## 7. Завершение: POST `/onboarding/complete`

Bearer и заголовок `Idempotency-Key: <UUID>` обязательны. Успех: `200 ProfileDocument` с непустым `onboarding.completed_at` и `next_step=null`. Завершение подтверждает только сервер. Промежуточного `202`, фонового polling или отдельного фиктивного результата плана в этом методе нет.

```json
{
  "planned_date": "2026-11-06",
  "tasks": [
    { "title": "Подготовка к экзамену", "type": "intellectual", "duration_min": 90 }
  ]
}
```

| Поле | Правило |
| --- | --- |
| `planned_date` | Обязательная дата `YYYY-MM-DD`, равная текущей дате в сохранённом `profile.timezone` при первой обработке |
| `tasks` | Обязательный массив от 1 до 100 элементов, порядок сохраняется |
| `title` | Обязательная строка; сервер удаляет пробелы по краям, после этого 1–200 символов |
| `type` | `intellectual`, `physical`, `creative`, `routine` |
| `duration_min` | Обязательное целое число 5–480 включительно; дроби, строки и boolean недопустимы |

Сумма длительностей не превышает длину рабочего окна; нарушение — `422 VALIDATION_ERROR`, поле `body.tasks`. Клиентские ID строк не передаются. Сервер назначает ID задач. Профиль должен содержать дату рождения, хронотип и валидный режим; иначе `409 PROFILE_INCOMPLETE` без побочных эффектов. Внутренние поля профиля из раздела 6 вычисляет сервер, а не клиент.

Задачи, план на `planned_date` и отметка завершения фиксируются одной транзакцией. Ошибка не оставляет частичных задач или завершённого профиля. При невозможности разместить все задачи с учётом ограничений планировщика — `409 PLAN_CAPACITY_EXCEEDED`; при технической недоступности планировщика — `503 PLANNER_UNAVAILABLE`. Задачи не теряются молча, частичный план не подтверждает завершение. Алгоритм выбора слотов — ответственность планировщика. Чтение плана отдельным GET не входит в этот метод и не является условием открытия приложения.

### Повторные запросы

Ключ ограничен текущим пользователем и операцией завершения онбординга. Сервер хранит ключ успешной операции, точное разобранное JSON-тело и успешный ответ до удаления аккаунта, без TTL. Различие пробелов JSON и порядка ключей объекта не меняет тело; порядок массива и значения строк значимы, включая пробелы в названии до trim. Несовпадение тела с использованным ключом даёт `409 IDEMPOTENCY_CONFLICT` без изменений.

После проверки авторизации сервер сначала проверяет успешный повтор: тот же ключ и тело возвращают сохранённый `200` без повторного создания задач, даже если наступил следующий день или профиль позже изменён. Конкурирующие запросы с одним ключом сериализуются и получают один результат. Неуспешная/откаченная транзакция не фиксирует ключ как успешный: тот же ключ и тело можно повторить. При завершённом онбординге новый ключ даёт `409 ONBOARDING_ALREADY_COMPLETED` и не добавляет новые задачи.

Для нового запроса после проверки успешного повтора сервер проверяет: уже завершённый онбординг, полноту профиля, актуальность даты, валидацию и вместимость плана. Несовпадение текущей даты — `409 PLANNED_DATE_CHANGED`, details: `{ "planned_date": "YYYY-MM-DD", "timezone": "IANA" }`, где дата — актуальная серверная. Неверный формат даты/UUID — `422`.

Клиент сохраняет ключ и точное тело отправки в черновике этого аккаунта. Потеря ответа не создаёт новый ключ. При ручном повторе отправляются прежние ключ и тело; редактирование формы создаёт новую операцию. После `PLANNED_DATE_CHANGED` клиент обновляет заявку и ключ; после `IDEMPOTENCY_CONFLICT` не повторяет изменённое тело под прежним ключом. При `ONBOARDING_ALREADY_COMPLETED` клиент перечитывает `/me` и открывает приложение только при подтверждённом завершении. Сохранённый ответ повторной операции не подменяет последующие актуальные чтения `/me`.

### Ошибки профиля и онбординга

| HTTP | Код | Действие клиента |
| --- | --- | --- |
| 401 | `AUTHENTICATION_REQUIRED` | Один refresh и максимум один повтор |
| 403 | `EMAIL_NOT_VERIFIED` | Предложить подтвердить почту |
| 409 | `ONBOARDING_REQUIRED` | Для будущих функций, требующих настройки: перечитать `/me`, открыть `next_step` |
| 409 | `PROFILE_INCOMPLETE` | Сохранить черновик, перечитать `/me`, открыть необходимый шаг |
| 409 | `ONBOARDING_ALREADY_COMPLETED` | Перечитать `/me`, проверить завершение |
| 409 | `IDEMPOTENCY_CONFLICT` | Показать ошибку, не повторять изменённое тело с тем же ключом |
| 409 | `PLANNED_DATE_CHANGED` | Предложить новую отправку на актуальную дату |
| 409 | `PLAN_CAPACITY_EXCEEDED` | Сохранить задачи; предложить изменить длительность/режим |
| 422 | `VALIDATION_ERROR` | Показать ошибки полей, сохранить введённые значения |
| 429 | `RATE_LIMIT_EXCEEDED` | Соблюсти `Retry-After` |
| 503 | `SERVICE_UNAVAILABLE` / `PLANNER_UNAVAILABLE` | Сохранить черновик, дать повторить запрос |

GET `/me`, PATCH `/me/profile` и POST `/onboarding/complete` доступны до завершения настройки и сами не возвращают `ONBOARDING_REQUIRED`. `404` для существующего пользователя без профиля не является допустимым бизнес-ответом этих методов.

## 8. Предпросмотр плана и временные заглушки

### Предпросмотр плана: POST `/onboarding/preview`

Метод предназначен для правой карточки «Ваш план на сегодня» на экране «v4 · 1.4 · Первые задачи». Bearer обязателен; метод доступен до завершения онбординга. Тело — тот же `OnboardingRequest`, что у `/onboarding/complete`: `planned_date` и `tasks`. Действуют те же правила полей и полноты сохранённого профиля. Часы, хронотип и пояс берутся из сохранённого профиля текущего пользователя. `Idempotency-Key` не нужен: расчёт не создаёт задач, расписания, записи завершения или иных пользовательских данных, повтор безопасен.

Успех — `200 PlanPreview`, `Cache-Control: no-store`:

```json
{
  "planned_date": "2026-11-06",
  "timezone": "Asia/Yekaterinburg",
  "slots": [
    {
      "task_index": 0,
      "start_time": "10:00:00",
      "end_time": "11:30:00",
      "explanation": "Утреннее интеллектуальное окно подходит для сосредоточенной работы"
    }
  ],
  "unscheduled_task_indexes": []
}
```

Все показанные поля обязательны. `planned_date` совпадает с датой запроса; `timezone` — IANA-пояс сохранённого профиля. `start_time` и `end_time` — локальные часы `HH:mm:ss` с секундами `00` в этой дате и поясе; это не UTC timestamps. Рабочий день не пересекает полночь. Интервал строго положительный, находится внутри рабочего дня и длится `duration_min` соответствующей задачи. `slots` отсортированы по времени, не пересекаются, не заходят на системные перерывы. Здесь возвращаются только задачи, без строк обеда, отдыха и перерывов.

`task_index` — целочисленный индекс в массиве исходного запроса, начиная с нуля. Название и тип берутся из соответствующей задачи запроса; постоянных task ID у предпросмотра нет. Каждая задача встречается ровно один раз: либо одним неделимым слотом в `slots`, либо индексом в `unscheduled_task_indexes`. Повторяющиеся и выходящие за границы индексы недопустимы. Пустой массив `slots` допустим, если все задачи перечислены как неразмещённые.

`explanation` — непустое безопасное текстовое пояснение размещения на русском, без HTML. Причину формирует планировщик. Проценты биоритмов допустимы только по реальным расчётам сервера; фронтенд не придумывает значения и не разбирает текст как машинный код. Карточка показывает сверху моноширинный интервал, под ним название, ниже пояснение меньшим шрифтом; цветная точка соответствует типу задачи. Для неразмещённых задач показывается «Время не определено» и предложение изменить длительность или режим.

Если общая длительность не превышает рабочего окна, но реальные ограничения мешают разместить часть задач, preview возвращает `200` с неразмещёнными индексами. Completion при той же ситуации возвращает `409 PLAN_CAPACITY_EXCEEDED` и ничего не сохраняет. Превышение общей длительности рабочего окна — `422` в обоих методах. Другие ошибки: `401 AUTHENTICATION_REQUIRED`, `403 EMAIL_NOT_VERIFIED`, `409 PROFILE_INCOMPLETE`, `409 PLANNED_DATE_CHANGED`, `422 VALIDATION_ERROR`, `429 RATE_LIMIT_EXCEEDED`, `503 SERVICE_UNAVAILABLE` / `PLANNER_UNAVAILABLE`, в общем формате.

Клиент пересчитывает preview после изменения задач с задержкой 350 мс, отменяет устаревшие запросы, не показывает ответ предыдущего набора задач как новый. Сеть, ошибки авторизации, валидации и `5xx` показываются с возможностью повторить; они не подменяются удачным локальным расчётом. Дата и профиль могут измениться между preview и complete: completion заново проверяет данные и атомарно строит окончательный план. Предпросмотр не гарантирует неизменность интервалов и не даёт статус «Готово». Переход в приложение выполняется только после подтверждённого завершения. Получение сохранённого плана для главной страницы остаётся отдельным будущим API.

### Режим разработки

До реализации трёх методов профиля клиент при их `404` использует локальную заглушку. При `404` `/onboarding/preview` включается предварительная локальная раскладка по окнам выбранного хронотипа: без расчёта биоритмов, вымышленных процентов и статуса «Готово». Локальный preview не сохраняет план и не завершает настройку. Настоящие register/login/verify/resend/refresh/logout остаются на API. Заглушка требует настоящую сессию и не создаёт авторизацию.

Профиль и первые задачи хранятся только в браузере, отдельно по `pd-local-profile:<user_id>`. Декодирование `sub` из полученного access используется исключительно для разделения локальных данных, не для серверной проверки JWT. Клиентское `local=true` — метаданные заглушки, не поле серверной схемы. Черновик также привязан к владельцу; чужой аккаунт его не получает.

При доступном `/me` серверный ответ всегда имеет приоритет. Локальное завершение не подтверждает серверное. Автоматической отправки накопленных данных на сервер нет. Сеть, `401`, `403` и `5xx` не подменяются успешной заглушкой. После реализации методов профиля, preview и завершения команда удаляет fallback до production-приёмки; это не альтернативный серверный режим и не часть постоянного API.

## 9. Границы бэкенда и хранение

| Область | Владелец auth | Владелец профиля/биоритмов |
| --- | --- | --- |
| Учётная запись | Регистрация, пароль, подтверждение, безопасность `User` | Использует `User.id` |
| Профиль | Не создаёт профиль при регистрации | `UserProfile`, `/me`, `/me/profile`, завершение |
| Авторизация | `get_current_user`, проверка access и сессии | Подключает общую зависимость, ограничивает данные `user.id` |
| Сессии | Таблицы, refresh, отзыв, список устройств | Не реализует альтернативную проверку JWT |
| План/биоритмы | Не реализует | Расчёты, создание задач/плана, проверка онбординга |
| Redis | Auth-лимиты `pd:auth:` | Отдельные префиксы для своего кэша |

Публичный импорт: `from app.core.security import get_current_user`, сигнатура `async def get_current_user(...) -> User`. Роутер использует `Annotated[User, Depends(get_current_user)]`; внутренние аргументы не передаёт. Тесты могут использовать `app.dependency_overrides[get_current_user]`.

Зависимость читает только Bearer, проверяет HS256, обязательные `sub`, `sid`, `iat`, `exp`, срок JWT, пользователя и сессию в PostgreSQL. Алгоритм не берётся из непроверенного JWT. Отсутствующий/некорректный access, отсутствующая, истёкшая, отозванная или чужая сессия, неактивный/удалённый/отсутствующий пользователь дают `401 AUTHENTICATION_REQUIRED`. Активный пользователь без подтверждения — `403 EMAIL_NOT_VERIFIED`.

Зависимость не требует Redis, профиля или завершённого онбординга, не загружает профиль и завершает собственную транзакцию чтения до роутера. Сервис профиля может открыть `session.begin()` на той же сессии БД. Дополнительная проверка онбординга для биоритмов/расписания остаётся у их владельца.

Текущая head миграций — `0005`, auth-таблицы: `sessions`, `refresh_tokens`, `email_tokens`. Существующие миграции не переписываются; новые строятся поверх объединённой head. Перед объединением проверяется одна Alembic head. Изменения ORM и миграция входят в один PR. Общие `app/main.py`, `app/core/config.py`, `app/db/models.py`, `app/workers/celery_app.py`, `pyproject.toml`, `uv.lock` и Compose согласуются владельцами. Новые задачи добавляются к существующему Beat, модели — к общей metadata. Никто не очищает Redis целиком.

Celery Beat раз в час запускает `auth.cleanup_expired`: удаляет истёкшие сессии с историей refresh каскадно и истёкшие email-токены. Отозванные сессии и использованные refresh сохраняются до исходного срока для обнаружения повторов. Неистёкшие email-токены, пользователи, профили и Redis-кэш не удаляются. Повторный запуск безопасен; нужны worker и beat.

## 10. Лимиты и конфигурация

| Действие auth | Текущий лимит |
| --- | --- |
| Login | 5 запросов/мин на IP + email |
| Register | 10 запросов/час на IP |
| Forgot | 3 запроса/час отдельно на IP и email |
| Change password | 5 запросов/мин на пользователя |
| Resend | 1 запрос/60 секунд на email |
| Прочие публичные auth-маршруты | 30 запросов/мин на IP |

Лимиты действуют и для неизвестных адресов. Redis DB 0, `pd:auth:`, ключи с TTL, email в ключе хэшируется. Недоступность Redis на лимитируемом методе — `503`. IP берётся из соединения; forwarded-заголовки доверяются только настроенному reverse proxy. Отдельных численных лимитов профиля v1 не задаёт; клиент в любом случае обрабатывает `429` инфраструктуры с `Retry-After`.

| Настройка | Значение по умолчанию / правило |
| --- | --- |
| `FRONTEND_URL` | `http://localhost:5173`; staging/production HTTPS без query, fragment и credentials |
| `CORS_ORIGINS` | Точные разрешённые origin фронтенда; для Swagger при необходимости отдельно разрешается origin API |
| `JWT_SECRET` | Стабильный собственный секрет не короче 32 символов, хранится только в локальном/серверном окружении |
| `ACCESS_TTL_MIN` | 15, положительное |
| `REFRESH_TTL_DAYS` | 30, положительное |
| `EMAIL_VERIFICATION_TTL_HOURS` | 24, положительное |
| `PASSWORD_RESET_TTL_MIN` | 60, положительное |
| `REFRESH_COOKIE_SECURE` | По ENV; staging/production true обязательно |
| `SMTP_HOST` | localhost при прямом запуске, mailpit в Compose |
| `SMTP_PORT`, `SMTP_FROM` | 1025, noreply@example.com |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | Пустые, если сервер не требует входа |

## 11. Запуск и приёмка

Запуск и сохранение JWT-секрета: [README](../../README.md). Локально из `backend`: `docker compose up -d --build --wait`. Дождаться `/api/v1/ready`: `db: ok`, `redis: ok`. API: `http://localhost:8000`, Swagger: `/docs`, Mailpit: `http://localhost:8025`, фронтенд: `http://localhost:5173`. На Windows при прямом запуске Celery используется `--pool=solo`.

Служебные GET: `/health` возвращает `200 {"status":"ok"}`. `/ready` — диагностика PostgreSQL и Redis; при недоступности возвращает собственный `503` с состояниями, а не общую бизнес-ошибку. Они не требуют Bearer.

### Обязательные сценарии совместной проверки

1. Register возвращает нейтральный `202`, сессии ещё нет. Повтор регистрации не меняет пароль. До подтверждения правильный login даёт `403 EMAIL_NOT_VERIFIED`.
2. Письмо появляется в Mailpit; ссылка открывает экран без автоматического подтверждения. Явный verify даёт `200`, cookie и access. Повтор токена — `400 INVALID_EMAIL_TOKEN`. Resend соблюдает 60 секунд и заменяет прежний токен.
3. Новый аккаунт получает `/me` с `profile=null`, `next_step=birth_date`. Дата и необязательное время сохраняются без поля часового пояса рождения; текущий пояс передаётся автоматически. После перезагрузки возвращается правильный шаг.
4. PATCH даты переводит к хронотипу, PATCH хронотипа/часов — к задачам. Некорректный PATCH ничего не меняет. Прямой переход вперёд не обходит необходимый шаг.
5. Completion создаёт задачи/план/отметку вместе. Повтор ключа и тела после потери ответа не дублирует данные, включая повтор на следующий день. Другое тело с ключом — конфликт; новый ключ после завершения — уже завершено. Две параллельные отправки дают один результат.
6. Ошибка планировщика откатывает все изменения. Неактуальная дата, незаполненный профиль, слишком длинные задачи и некорректные поля имеют описанные коды. Ошибки не теряют черновик и не сообщают ложное завершение.
7. Существующий завершивший настройку пользователь возвращается на запрошенный URL. Перезагрузка восстанавливает сессию через cookie, access не появляется в браузерном хранилище. Несколько защищённых `401` выполняют один refresh; исходные запросы повторяются максимум один раз.
8. Проверяются отзыв сессии, logout-all, чужой UUID, абсолютный срок, параллельные вкладки, повтор старого refresh, сеть/`503`, поздний ответ после выхода и смена аккаунта. Черновики разных пользователей не смешиваются.
9. Forgot нейтрален, reset/change отзывают все сессии, старые access/refresh недействительны, требуется новый вход. Cleanup безопасен и не удаляет живые данные.
10. Сравниваются OpenAPI работающего API и этот контракт: методы, типы, статусы, Bearer, cookie, ошибки, `Retry-After`, CORS. Выполняется приёмка с настоящим API профиля и отключёнными локальными заглушками. Тесты с заглушками не подтверждают готовность серверной интеграции.
11. Preview пересчитывается при изменении названия, типа, длительности и набора задач, показывает время, название и пояснение в порядке макета. Устаревший ответ не заменяет новый. Проверяются неразмещённые задачи, отсутствие пересечений и попадания на перерывы, разные хронотипы, длинные названия и узкий экран. Ни предпросмотр, ни его ошибка не создают задачи и не завершают онбординг.

## 12. Предложение фронтенда: задачи, таймлайн и биоритмы

**Статус: предложение фронтенда, требует согласования с бэкендом. Дата: 11 ноября 2026 года.** Все новые пути, схемы и коды ошибок ниже предложены для обсуждения, а не описывают работающий сервер. Требования продукта уже зафиксированы: длительность задачи обязательна; заполненный дедлайн обязательно содержит дату и время. Дедлайн остаётся необязательным полем: отсутствие срока передаётся как `null`.

Цель первого этапа — подготовить модели и примеры для вёрстки без API. Раздел также заранее фиксирует целевое поведение следующей задачи «Финализация главного экрана: связка графиков, таймлайна и рекомендаций; закрепление задач; адаптивная проверка». Реализация серверных методов, миграций, расчётов и фронтенд-интеграции в первый этап не входит. `PlanPreview` онбординга из раздела 8 остаётся отдельной схемой: там индексы черновика и локальные часы, здесь постоянные ID и моменты времени сохранённых слотов.

### 12.1. Общие правила и предлагаемые методы

Все пути относительно `/api/v1`, Bearer обязателен. Пользователь определяется по сессии; `user_id` в запросах отсутствует. Предлагается использовать существующие общие ошибки из раздела 2, `Cache-Control: no-store` и профильный IANA-пояс из `/me`.

| Метод | Запрос | Успех |
| --- | --- | --- |
| GET `/biorhythms` | Query `from`, `to` — включительные локальные даты | 200 `BiorhythmSeries` |
| GET `/schedule` | Query `date` — локальная дата | 200 `DailySchedule`, в том числе пустой день |
| GET `/tasks/{id}` | UUID задачи | 200 `Task` для формы редактирования |
| POST `/tasks` | JSON `TaskCreateRequest`; при создании закреплённой задачи — также контрольные поля из 12.8 | 201 `Task` с назначенным ID после пересчёта плана |
| PATCH `/tasks/{id}` | UUID, JSON `TaskUpdateRequest`; при изменении закрепления — также контрольные поля из 12.8 | 200 актуальный `Task` с новой версией после пересчёта плана |

Моменты `deadline`, `pinned_start`, `completed_at`, `start_at`, `end_at` и `at` содержат дату, время и смещение. Предлагается принимать ISO 8601 с явным смещением (`Z`, `+00:00`, `+05:00` и т. п.) и возвращать нормализованный UTC с `Z`. Это уточнение формата для новых методов; существующие разделы 1–11 не меняются. Дата без времени и datetime без смещения для этих API-полей недопустимы.

`planned_date`, `date`, `from`, `to` — `YYYY-MM-DD` в поясе профиля. `preferred_start`, `work_start`, `work_end` — локальные `HH:mm:ss` с секундами `00`. Клиент не превращает локальную дату в UTC-полночь и не прибавляет фиксированные 24 часа при определении границ пользовательского дня: возможен DST.

### 12.2. Задача и значения формы

Предварительные TypeScript-модели: [task.ts](../../frontend/src/shared/model/task.ts). Четыре типа и русские названия вынесены из онбординга в общую модель; старые импорты из `onboarding.ts` поддерживаются через реэкспорт.

Все поля `TaskCreateRequest` в таблице передаются явно, включая `null` у незаполненных необязательных полей. Поля полного ответа `Task` также обязательны, nullable-поля не пропускаются.

| Поле | Тип и правило |
| --- | --- |
| `title` | Строка, после обрезки пробелов 1–200 символов |
| `description` | Строка или `null`; пустое описание формы преобразуется в `null` |
| `type` | `intellectual`, `physical`, `creative`, `routine`; обязательный выбор |
| `priority` | `high`, `medium`, `low`; начальное значение формы `medium` |
| `duration_min` | Обязательное целое 5–480 минут, без значения по умолчанию; строки, дроби и boolean отклоняются |
| `planned_date` | Обязательная локальная дата дня, к которому относится задача |
| `preferred_start` | Локальное желаемое время или `null`; это пожелание, не закрепление |
| `deadline` | Полный момент дедлайна **с датой и временем**, либо `null` |
| `is_pinned` | Boolean, начальное значение формы `false` |
| `pinned_start` | При `is_pinned=true` обязателен полный момент начала; при `false` — `null` |

Дополнительные поля ответа `Task`:

| Поле | Тип и правило |
| --- | --- |
| `id` | UUID |
| `status` | `pending` — не размещена; `scheduled` — размещена; `done` — выполнена; `skipped` — пропущена |
| `completed_at` | Момент выполнения или `null`; для `done` обязателен момент |
| `version` | Целое от 1 для обнаружения конкурентного редактирования |

Пример POST `/tasks`:

```json
{
  "title": "Подготовка к экзамену",
  "description": "Решить задания и выписать вопросы преподавателю.",
  "type": "intellectual",
  "priority": "high",
  "duration_min": 90,
  "planned_date": "2026-11-11",
  "preferred_start": "10:00:00",
  "deadline": "2026-11-11T09:00:00Z",
  "is_pinned": false,
  "pinned_start": null
}
```

Пример ответа `201 Task` при нехватке подходящего места: задача сохранена, пересчёт выполнен, задача осталась неразмещённой. Если подходящий интервал найден, ответ имеет `status=scheduled`; чтение `/schedule` возвращает соответствующий слот.

```json
{
  "id": "10000000-0000-4000-8000-000000000003",
  "title": "Подготовка к экзамену",
  "description": "Решить задания и выписать вопросы преподавателю.",
  "type": "intellectual",
  "priority": "high",
  "duration_min": 90,
  "planned_date": "2026-11-11",
  "preferred_start": "10:00:00",
  "deadline": "2026-11-11T09:00:00Z",
  "is_pinned": false,
  "pinned_start": null,
  "status": "pending",
  "completed_at": null,
  "version": 1
}
```

В `Asia/Yekaterinburg` этот дедлайн отображается как 11 ноября, **14:00**. Формат даты без времени не допускается ни в создании, ни в редактировании. Старый или просроченный дедлайн при чтении сохраняется и отображается, не скрывается.

PATCH принимает `version` прочитанной задачи и изменённые поля из `TaskCreateRequest`; хотя бы одно изменяемое поле обязательно. Отсутствующее поле не меняется, явный `null` очищает nullable-поле. `title`, `type`, `priority`, `duration_min`, `planned_date`, `is_pinned` нельзя обнулить. Связанные поля закрепления проверяются после применения изменений: для снятия закрепления отправляются одновременно `is_pinned=false` и `pinned_start=null`. При изменении закрепления дополнительно обязательны `expected_schedule` и `expected_context_revision` из 12.8. Клиент не задаёт ID, статус и момент выполнения этим PATCH; планировщик может изменить `pending`/`scheduled` в той же операции.

```json
{
  "version": 1,
  "duration_min": 60,
  "deadline": "2026-11-12T13:00:00Z"
}
```

Успех — полный `Task` с применёнными полями и `version=2`. При устаревшей версии предлагается `409 TASK_VERSION_CONFLICT` без перезаписи чужих изменений. Чужой и отсутствующий UUID одинаково дают `404 TASK_NOT_FOUND`. Ошибки полей — `422 VALIDATION_ERROR`, например `body.duration_min`, `body.deadline`, `body.pinned_start`.

`TaskFormValues` — отдельная клиентская модель, не тело API. Пустые обязательные контролы допустимы в черновике: `type=''`, `durationMin=''`. В API они не отправляются до успешной валидации. `deadlineLocal` и `pinnedStartLocal` — значения `datetime-local` вида `2026-11-11T14:00` в поясе профиля; отсутствие значения — пустая строка. Адаптер формы должен учитывать IANA-пояс профиля и неоднозначное/несуществующее время при DST. Использовать `new Date(datetimeLocal)` с неявным поясом компьютера или просто приписывать `Z` нельзя. Сам адаптер и валидация формы реализуются на следующем этапе.

### 12.3. Суточный таймлайн

Предварительная модель первого этапа: [schedule.ts](../../frontend/src/shared/model/schedule.ts). Она покрывает базовые поля; дополнительные поля главного экрана ниже и контрольные поля записи из 12.8 должны быть добавлены в TypeScript при реализации соответствующего этапа. `DailySchedule` содержит данные выбранного локального дня целиком:

| Поле | Смысл |
| --- | --- |
| `date`, `timezone` | Дата запроса и IANA-пояс профиля |
| `work_start`, `work_end` | Рабочее окно из профиля, локальные часы; конец позже начала в пределах дня |
| `schedule` | `{id: UUID, version: integer >= 1}` или `null`, если сохранённого плана ещё нет |
| `tasks` | Полные `Task` за эту дату, включая выполненные, пропущенные и неразмещённые; без удалённых |
| `slots` | Занятые интервалы по возрастанию `start_at`, без пересечений |
| `unscheduled_task_ids` | ID задач со статусом `pending`, которым не назначен слот |
| `context_revision` | Непустая непрозрачная строка версии исходных данных профиля и алгоритма, общая с биоритмами; правила в 12.9 |
| `generated_at` | Момент формирования снимка в UTC; не заменяет контроль версий |
| `recommendations` | Массив `DayRecommendation` из 12.7, в порядке показа; отсутствие рекомендаций — `[]` |
| `load` | Объект нагрузки из 12.7; все значения в минутах |

Каждый `ScheduleSlot` содержит `id`, `kind`, `task_id`, `start_at`, `end_at`, `is_pinned`, `explanation`. Виды: `task`, `break`, `lunch`, `rest`. Конец строго позже начала, границы находятся внутри запрошенного локального дня. Слоты задач имеют существующий `task_id` из `tasks`; для обеда, перерыва и отдыха `task_id=null`, `is_pinned=false`. Пояснение — строка или `null`.

Задачи `scheduled` и `done` представлены одним неделимым слотом длительностью `duration_min`. Пропущенная задача не занимает слот. Каждая `pending` встречается ровно один раз в `unscheduled_task_ids`, её слота нет. Закрепление слота совпадает с задачей; при закреплении `start_at` совпадает с `pinned_start` как момент времени.

Пустой день — `200` с `tasks=[]`, `slots=[]`, `unscheduled_task_ids=[]`, `schedule=null`, а не `404`. При отсутствии плана, но наличии ожидающих задач, `tasks` и `unscheduled_task_ids` заполнены, `slots=[]`, `schedule=null`. Нехватка места при чтении — успешный ответ с неразмещёнными задачами; она не подменяется ошибкой загрузки.

Свободные интервалы фронтенд выводит из промежутков между слотами внутри рабочего окна. Для них нет отдельного типа задачи. Рабочее окно задаёт основной вид таймлайна; за его пределами интерфейс может показывать остальную часть суток. Значения времени отображаются в `timezone` ответа, независимо от настроек компьютера.

Пример GET `/schedule?date=2026-11-11` для пустого дня:

```json
{
  "date": "2026-11-11",
  "timezone": "Asia/Yekaterinburg",
  "work_start": "08:00:00",
  "work_end": "18:00:00",
  "schedule": null,
  "tasks": [],
  "slots": [],
  "unscheduled_task_ids": [],
  "context_revision": "ctx-demo-1",
  "generated_at": "2026-11-11T04:42:00Z",
  "recommendations": [],
  "load": {
    "planned_min": 0,
    "requested_min": 0,
    "capacity_min": 540,
    "level": "comfortable"
  }
}
```

Пример занятого слота (внутри `DailySchedule.slots`, при наличии соответствующей задачи в `tasks`):

```json
{
  "id": "20000000-0000-4000-8000-000000000003",
  "kind": "task",
  "task_id": "10000000-0000-4000-8000-000000000003",
  "start_at": "2026-11-11T05:00:00Z",
  "end_at": "2026-11-11T06:30:00Z",
  "is_pinned": false,
  "explanation": "Пик интеллектуального цикла и утреннее окно хронотипа."
}
```

В поясе примера это интервал **10:00–11:30**. Для цветовой маркировки фронтенд использует `Task.type` и существующие CSS-токены, без HEX-цветов в API: `intellectual` → `--type-intellectual`, `creative` → `--type-creative`, `physical` → `--type-physical`, `routine` → `--type-routine`. Системные интервалы используют `--type-rest`. Тип также обозначается текстом. `social` и `rest` не добавляются в перечисление пользовательских задач.

### 12.4. Биоритмы

Предварительные модели: [biorhythm.ts](../../frontend/src/shared/model/biorhythm.ts). GET `/biorhythms?from=2026-11-11&to=2026-11-17` возвращает одну точку на каждую календарную дату включительно. Предлагаемый максимум — 93 даты на запрос, чтобы поддержать неделю, месяц и три календарных месяца. Конец раньше начала или превышение диапазона — `422 VALIDATION_ERROR`. Масштаб интерфейса не передаётся: клиент вычисляет `from` и `to`.

`BiorhythmSeries` содержит `from`, `to`, `timezone`, `algorithm_version`, `points`. Для связки главного экрана ответ дополнительно содержит обязательные `context_revision` и `generated_at` по правилам 12.9; предварительная TypeScript-модель первого этапа пока покрывает базовые поля. Даты ответа совпадают с запросом, точки отсортированы без пропусков и дубликатов. Для дневного значения предлагается срез в локальный полдень; точный момент указан в `at`. Это решение, пороги фаз и правила определения критического дня требуют согласования с владельцем расчёта.

Каждый `BiorhythmPoint` содержит:

| Поле | Смысл |
| --- | --- |
| `date` | Локальная дата точки |
| `at` | Полный момент дневного среза в UTC |
| `cycles` | Объект с обязательными ключами `physical`, `emotional`, `intellectual` |
| `cycles.<cycle>.value` | Число **от −100 до +100**, проценты; повторно умножать на 100 на клиенте нельзя |
| `cycles.<cycle>.phase` | `rising` / `peak` / `falling` / `low`: подъём / пик / спад / минимум |
| `cycles.<cycle>.day_in_cycle` | Целый номер дня, 1–23 / 1–28 / 1–33 соответственно |
| `critical_cycles` | Уникальные имена циклов, пересекающих ноль в течение всего локального дня; пустой массив допустим |
| `recommendation` | Текст для карточки дня и подсказки, либо `null` |

Критический день не определяется фронтендом по округлённому проценту дневного среза: ноль может быть пересечён в другое время суток. Два и три элемента в `critical_cycles` позволяют выделить двойной и тройной критический день. Значения и фазы для мини-графиков, большой диаграммы и прогноза берутся из одних данных.

Пример ответа на однодневный запрос `/biorhythms?from=2026-11-11&to=2026-11-11` (числа демонстрационные):

```json
{
  "from": "2026-11-11",
  "to": "2026-11-11",
  "timezone": "Asia/Yekaterinburg",
  "algorithm_version": "demo-layout-v1",
  "context_revision": "ctx-demo-1",
  "generated_at": "2026-11-11T04:42:00Z",
  "points": [
    {
      "date": "2026-11-11",
      "at": "2026-11-11T07:00:00Z",
      "cycles": {
        "physical": { "value": 100, "phase": "peak", "day_in_cycle": 7 },
        "emotional": { "value": -90, "phase": "low", "day_in_cycle": 20 },
        "intellectual": { "value": 100, "phase": "peak", "day_in_cycle": 9 }
      },
      "critical_cycles": [],
      "recommendation": "Демонстрация: выбрать подходящие задачи по фазам циклов."
    }
  ]
}
```

При недостающих данных рождения предлагается `409 PROFILE_INCOMPLETE`. Нет данных профиля, сеть и серверная ошибка не заменяются нулевыми процентами или демонстрационной синусоидой. Реальный расчёт и кэш принадлежат бэкенду по [ADR 0003](../../backend/docs/adr/0003-biorhythms-computed-not-stored.md); этот этап не реализует их на фронтенде.

### 12.5. Наборы для вёрстки и границы первого этапа

Тестовые данные находятся в [planning.ts](../../frontend/src/shared/fixtures/planning.ts) и [biorhythms.ts](../../frontend/src/shared/fixtures/biorhythms.ts). Экспортируются:

- `DAILY_SCHEDULE_FIXTURES.normal` — четыре типа задач, два выполненных дела, закрепление, пропущенная задача, дедлайны с временем, обед, перерыв, отдых и свободные промежутки.
- `DAILY_SCHEDULE_FIXTURES.empty` — день без задач и плана.
- `DAILY_SCHEDULE_FIXTURES.overloaded` — обычный план и две неразмещённые задачи; общая нагрузка превышает рабочее окно.
- `TASK_FORM_FIXTURES` — пустая, заполненная и закреплённая формы, длительности 5/480 минут, длинное название и намеренно ошибочный черновик.
- `BIORHYTHM_FIXTURES` — неделя, месяц, три месяца с переходом года; искусственные значения, фазы и критические дни.
- `PLANNING_FIXTURE_CONTEXT` — фиксированные дата, пояс и момент «сейчас» для воспроизводимого отображения.

Наборы доступны через явный импорт, не подключены к рабочим экранам или HTTP fallback и не хранят данные аккаунта. Они не подтверждают готовность интеграции. Демонстрационный генератор биоритмов не использует дату рождения, а его пороги фаз не задают серверный алгоритм.

Это спецификация для будущей реализации, не дополнительная серверная работа первого этапа. После согласования команды изменения в пределах этих сценариев должны реализовываться по этому разделу.

### 12.7. Рекомендации и нагрузка главного экрана

Источник блока «Подсказки» и предупреждений дня — `DailySchedule.recommendations`. `BiorhythmPoint.recommendation` остаётся кратким прогнозом по циклам для графика и карточки даты, а `ScheduleSlot.explanation` объясняет размещение конкретной задачи. Они не заменяют друг друга и не должны объединяться фронтендом в вымышленные серверные рекомендации.

Все поля `DayRecommendation` обязательны; nullable-поля передаются явно:

| Поле | Тип и смысл |
| --- | --- |
| `id` | Непустая непрозрачная строка, стабильная для одной рекомендации в одной версии плана; не обязательно UUID |
| `kind` | `break`, `reschedule`, `critical_day`, `overload`, `general` |
| `severity` | `info`, `warning`, `danger` для обычной подсказки, предупреждения и усиленного предупреждения |
| `title`, `text` | Непустые строки для заголовка и текста, без HTML |
| `explanation` | Подробное пояснение для «Почему так?» или `null`; при `null` ссылка не показывается |
| `task_id` | UUID связанной задачи из `DailySchedule.tasks` или `null` |
| `slot_id` | UUID связанного слота из `DailySchedule.slots` или `null`; при наличии `task_id` ссылка должна соответствовать той же задаче |
| `target_date` | Локальная дата, о которой говорится в рекомендации, или `null`; может отличаться от даты экрана |
| `action` | Одно навигационное действие по таблице ниже или `null` |

`action` — один из объектов; `label` всегда непустая строка:

| `kind` | Остальные поля | Поведение клиента |
| --- | --- | --- |
| `open_task` | `label`, `task_id` | Открыть задачу текущего снимка; ID совпадает с `DayRecommendation.task_id` |
| `open_day` | `label`, `date` | Открыть план указанной локальной даты; `date` совпадает с `target_date` |
| `open_biorhythms` | `label`, `date` | Открыть графики с выбранной датой; `date` совпадает с `target_date` |

Сервер задаёт порядок рекомендаций, клиент его сохраняет. Пустой массив — нормальное состояние. Неизвестные `kind` рекомендации показываются как `general`; неизвестное действие не исполняется и его кнопка скрывается. Фронтенд выбирает собственный маршрут по известному действию; сервер не присылает произвольные URL. Нажатие рекомендации само по себе не переносит, не закрепляет и не изменяет задачу. `reschedule` предлагает другое время или дату, а переход открывает форму либо нужный день.

Пример элемента `recommendations`:

```json
{
  "id": "break-after:10000000-0000-4000-8000-000000000003",
  "kind": "break",
  "severity": "info",
  "title": "Перерыв в 11:30",
  "text": "После 90 минут учёбы запланирован отдых до 12:00.",
  "explanation": "Перерыв добавлен после длительного интеллектуального блока.",
  "task_id": "10000000-0000-4000-8000-000000000003",
  "slot_id": "20000000-0000-4000-8000-000000000003",
  "target_date": "2026-11-11",
  "action": {
    "kind": "open_task",
    "label": "Открыть задачу",
    "task_id": "10000000-0000-4000-8000-000000000003"
  }
}
```

Для предупреждения о критических днях используется `kind=critical_day`, `target_date` и, при необходимости, `open_day` или `open_biorhythms`. Все численные значения в тексте относятся к указанной дате, поясу и `context_revision` снимка. Если подробного пояснения нет, клиент его не генерирует.

`DailySchedule.load` содержит обязательные поля:

- `planned_min` — сумма `duration_min` задач `scheduled` и `done`, без системных слотов.
- `requested_min` — сумма задач `pending`, `scheduled`, `done`; пропущенные задачи исключены.
- `capacity_min` — доступная длительность для задач с учётом рабочего окна, обязательных перерывов и ограничений нагрузки. Считает сервер; это не всегда длина рабочего окна.
- `level` — `comfortable`, `busy`, `overloaded`. Пороги определяет версия алгоритма; наличие неразмещённых задач обязательно даёт `overloaded`.

Минуты — целые неотрицательные числа, `planned_min <= requested_min`. При нулевой вместимости клиент не делит на ноль. Распределение цветов нагрузки строится по типам задач того же снимка; цвета в API не передаются. Карточку ближайшей задачи фронтенд выбирает по локальному текущему времени из ещё не завершённых слотов, пояснение берёт из соответствующего слота. Если следующего слота нет, карточка не получает вымышленную задачу.

### 12.8. Закрепление и снятие закрепления

Используется существующий PATCH `/tasks/{id}`. При изменении `is_pinned` или `pinned_start` дополнительно передаются контрольные поля верхнего уровня:

- `expected_schedule` — `{id, version}` из текущего `DailySchedule.schedule`. Значение `null` разрешено только при отсутствии сохранённого плана и означает «ожидаю отсутствие активного плана», а не отключение проверки.
- `expected_context_revision` — строка из того же `DailySchedule.context_revision`.

Эти поля не сохраняются в задаче и не являются редактируемыми полями формы. `version` задачи также обязателен. Если активный план, его версия или версия контекста изменились, запрос отклоняется до любых записей. Изменять закрепление одновременно с `planned_date` этим запросом нельзя: изменение даты — отдельное редактирование с последующим чтением нового дня.

Пример закрепления текущего интервала **15:00–16:00** в `Asia/Yekaterinburg`:

```json
{
  "version": 1,
  "is_pinned": true,
  "pinned_start": "2026-11-11T10:00:00Z",
  "expected_schedule": {
    "id": "30000000-0000-4000-8000-000000000001",
    "version": 1
  },
  "expected_context_revision": "ctx-demo-1"
}
```

Правила:

1. Кнопка «Закрепить» на таймлайне сохраняет начало показанного слота, длительность не меняет. У `pending` нет показанного интервала: закрепление разрешено только через явный выбор будущего `pinned_start` в форме. Создание сразу закреплённой задачи через POST также требует обоих контрольных полей.
2. Начало соответствует `planned_date` в поясе профиля, интервал помещается в рабочее окно, не пересекает полночь и заканчивается не позже дедлайна, если он задан. Для новой фиксации начало должно быть в будущем по серверному времени.
3. Алгоритм сохраняет начало и длительность закреплённой задачи при последующих пересчётах. Прочие незакреплённые задачи могут переместиться или попасть в неразмещённые. Пересечение с другой закреплённой задачей, уже выполненным интервалом либо обязательным системным перерывом не допускается. Собственный прежний слот не считается конфликтом.
4. `done`, `skipped` и задачи с уже начавшимся слотом нельзя закрепить, открепить или передвинуть этим действием. История выполненных задач не меняется.
5. Для снятия закрепления передаются `is_pinned=false`, `pinned_start=null`, актуальные `version`, `expected_schedule`, `expected_context_revision`. Задача снова участвует в автоматическом размещении; сохранение прежнего времени не гарантируется.
6. При редактировании длительности или дедлайна уже закреплённой задачи также обязательны контрольные поля. Закреплённое начало сохраняется, итоговый интервал заново проходит все проверки. Нарушение ограничений не снимает закрепление автоматически.

Пример снятия после успешного закрепления и повторного чтения актуального плана:

```json
{
  "version": 2,
  "is_pinned": false,
  "pinned_start": null,
  "expected_schedule": {
    "id": "30000000-0000-4000-8000-000000000002",
    "version": 2
  },
  "expected_context_revision": "ctx-demo-1"
}
```

### 12.9. Пересчёт и согласованность главного экрана

Для этой задачи выбирается **синхронный атомарный пересчёт**, без фоновых job ID, polling и статуса `202`:

1. POST/PATCH проверяет авторизацию, версию задачи и применимые контрольные поля, затем валидирует итоговую задачу.
2. Сохранение задачи, новый активный план и данные для рекомендаций публикуются как один согласованный результат. При смене `planned_date` пересчитываются исходная и новая даты. Частично изменённый план не доступен другим запросам.
3. Успешный `201`/`200` означает, что пересчёт завершён. Ответ остаётся полным `Task`, а не обещанием будущего распределения. Незакреплённая задача может остаться `pending`; она появляется в `unscheduled_task_ids`. Невозможность разместить именно закреплённую задачу — ошибка с откатом, не успешное сохранение `pending`.
4. Обычный успешный PATCH увеличивает версию изменённой задачи ровно на один. Если пересчёт меняет публичный статус других задач, их версии также увеличиваются. Версия плана растёт в пределах пользователя и локальной даты даже при смене ID активной записи. Для нового сохранённого плана версия начинается с 1.
5. Повтор той же установки с актуальными контрольными полями, если данные уже совпадают, может вернуть `200` без изменения версий. Устаревшие версии всегда дают конфликт. Автоматического повтора мутации после сети или `5xx` нет: клиент сначала читает задачу и план и проверяет фактический результат.
6. При валидационной ошибке, конфликте или сбое планировщика задача, статусы других задач, активный план и рекомендации сохраняют прежнее состояние. Для недоступного расчёта используется `503 PLANNER_UNAVAILABLE` с безопасным сообщением.

`context_revision` — непрозрачная версия всех влияющих исходных данных: даты/времени рождения, хронотипа, часового пояса, режима дня и версии алгоритма. Сервер меняет её при изменении этих данных и возвращает одинаковое значение в биоритмах и расписании, рассчитанных по одному контексту. Ответ не должен маркировать старый план новой версией контекста. `generated_at` — UTC-момент формирования ответа; клиент не использует его вместо версии или для сравнения часов разных узлов сервера.

Получение и обновление экрана:

- Графики и таймлайн запрашиваются для выбранной локальной даты в поясе профиля. Главный экран берёт значения циклов за эту же дату. Мини-графикам можно запросить более широкий диапазон, содержащий выбранный день.
- `DailySchedule` — единый согласованный снимок `tasks`, `slots`, `load`, `recommendations`. Эти части не собираются из разных версий плана. Частичный ответ без обязательного поля не считается пустым днём.
- После успешной записи фронтенд отменяет устаревшие чтения и обновляет задачу и `/schedule` для затронутых дат. Старые рекомендации и нагрузка не показываются как новые до получения нового снимка. Данные биоритмов можно сохранить в кэше, если дата, пояс и `context_revision` не изменились.
- Если версии контекста или пояса графиков и плана различаются, клиент обновляет `/me` и оба набора. До согласования частей интерфейс показывает обновление, а не объединяет противоречащие данные. Автоматические повторы ограничиваются двумя попытками; затем доступно ручное повторение. Сервер обязан пересчитать устаревшее расписание в актуальном контексте либо вернуть явную ошибку, а не выдавать старые данные с новым токеном.
- Смена аккаунта, даты, пояса или контекста отменяет применимость предыдущих ответов. Ключи кэша учитывают владельца сессии, дату/диапазон и пояс; поздний ответ старого запроса не заменяет новый. Непрозрачные версии контекста сравниваются только на равенство.
- Загрузка — состояние запроса, а не поле сохранённой задачи. Во время закрепления кнопка занята и повторно не отправляет действие. Иконка закрепления подтверждает результат только после успеха; при оптимистичном отображении обязателен откат при ошибке.
- Если запись успешна, но последующее чтение не удалось, интерфейс сообщает «Изменение сохранено, не удалось обновить план» и повторяет чтение по действию пользователя. Повторно отправлять PATCH вместо чтения нельзя. При потере ответа самой записи её результат считается неизвестным до проверки через GET.
- Пустые `recommendations=[]` и отсутствие следующей задачи допустимы. Сетевая ошибка или `503` не превращаются в пустой день либо успешное закрепление. На смене локального дня клиент обновляет дату «Сегодня» и связанные данные; в фоне запросы не отправляются каждую секунду ради линии времени.

### 12.10. Ошибки закрепления и пересчёта

Используется общий формат `{error: {code, message, details}}` из раздела 2. Применимы также общие `401`, `403`, `429`, `500`, `503`. Новые коды этого предложения:

| HTTP | Код | Смысл и реакция клиента |
| --- | --- | --- |
| 404 | `TASK_NOT_FOUND` | Задачи нет или она чужая; обновить день, закрыть недоступное редактирование |
| 409 | `TASK_VERSION_CONFLICT` | Изменена задача; сохранить черновик, перечитать задачу и план |
| 409 | `SCHEDULE_VERSION_CONFLICT` | Активный план не совпадает с `expected_schedule`; перечитать день перед новым действием |
| 409 | `PLANNING_CONTEXT_CHANGED` | Изменились профиль, пояс или алгоритм; обновить профиль, графики и план |
| 409 | `PIN_INTERVAL_CONFLICT` | Интервал пересекает запрещённый занятый слот; показать конфликт и предложить другое время |
| 409 | `PIN_DEADLINE_CONFLICT` | Закреплённый интервал заканчивается позже дедлайна; изменить время, длительность или дедлайн |
| 409 | `TASK_NOT_PINNABLE` | Задача выполнена, пропущена, уже началась либо выбранное начало уже наступило |
| 409 | `PROFILE_INCOMPLETE` | Для расчёта не хватает данных профиля |
| 422 | `VALIDATION_ERROR` | Нет обязательных контрольных полей, неверный момент времени, дата, длительность или выход за рабочее окно; использовать полевые ошибки |
| 503 | `PLANNER_UNAVAILABLE` | Расчёт не выполнен, записи откатились; повторить после восстановления доступности |

Для `PIN_INTERVAL_CONFLICT` `details` содержит `conflicting_slot_ids` — массив UUID конфликтующих слотов текущего пользователя, без чужих данных. Для конфликтов версий подробности могут быть пустыми: источником новых значений остаётся GET, клиент не строит новый план из ошибки. Ошибка не возвращает фиктивный успешный `Task`.

```json
{
  "error": {
    "code": "PIN_INTERVAL_CONFLICT",
    "message": "Это время занято закреплённой задачей или обязательным перерывом.",
    "details": {
      "conflicting_slot_ids": ["20000000-0000-4000-8000-000000000005"]
    }
  }
}
```

### 12.11. Приёмка финализации главного экрана

Сценарии совместной проверки после реализации серверных методов:

1. Дата, пояс и `context_revision` графиков и расписания согласованы. Рекомендация открывает связанную задачу/дату, а «Почему так?» показывает серверное пояснение. Нет рекомендаций — нет пустых карточек и неработающих кнопок.
2. Закрепление сохраняет показанный интервал; повторный GET и перезагрузка подтверждают его. Последующий автоматический пересчёт не двигает закреплённую задачу. Снятие закрепления возвращает её в автоматическое размещение.
3. Проверяются конфликты двух закреплений, обязательный перерыв, дедлайн с временем, рабочие границы, начавшаяся и завершённая задача. Неуспех не меняет задачу, другие задачи, план и рекомендации.
4. Две вкладки с разными версиями не перезаписывают друг друга. Проверяются повторное нажатие, потеря ответа записи, успешная запись с ошибкой последующего GET и отказ планировщика. Черновик не теряется, успех не показывается без подтверждения.
5. После изменения одновременно обновляются таймлайн, ближайшая задача, нагрузка и рекомендации; поздние ответы не возвращают старые данные. Проверяются смена аккаунта, пояса, даты, переход через полночь и календарные дни с DST.

Адаптивная проверка — фронтендовая приёмка, не отдельные поля API. Проверить ширины 390 px из мобильного макета и 1440 px из десктопного, промежуточную ширину 768 px и узкий экран 320 px; обе темы, длинные названия и рекомендации, масштаб браузера 200%, пустой и перегруженный день. Учитываются мобильное представление таймлайна, отсутствие горизонтального переполнения страницы, доступность действий закрепления с клавиатуры и касанием. Один набор API-данных используется на всех ширинах; цвет дополняется текстом, иконка закрепления имеет доступное название и состояние.
