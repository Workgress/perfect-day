# Единый API-контракт Perfect Day · v1

Версия: **1.0**, 6 ноября 2026 года, дополнен CRUD задач 13 ноября 2026 года. Единый источник требований для фронтенда и бэкенда в области авторизации, профиля, онбординга и задач. Документ объединяет прежний контракт auth и предложение по профилю. Названия и смысл полей, статусы, ошибки и правила повторов ниже фиксируются для `/api/v1`.

Это целевой контракт, а не утверждение о готовности всех методов. Авторизация и маршруты профиля реализованы; предпросмотр и завершение онбординга предстоит реализовать. Перед совместным выпуском владельцы фронтенда и бэкенда проверяют реализацию по этому документу. Документ не заменяет проверку совместимости тестами.

Дополнение от 11 ноября 2026 года: раздел 12 — **предложение фронтенда, требует согласования с бэкендом**. Он описывает данные для графиков биоритмов, форм задач и суточного таймлайна. Этот раздел не означает готовность API и не меняет существующие методы разделов 1–11.

## 1. Область действия и совместимость

В исходный контракт v1 входят email/password-аутентификация, подтверждение email, сессии, восстановление и смена пароля, профиль, сохранение шагов, предпросмотр и завершение онбординга с первыми задачами. Целевой контракт CRUD задач добавлен отдельным разделом 12 без изменения существующих методов. Социальный вход, тест хронотипа, API чтения сохранённого расписания и API биоритмов этим документом не определяются. Раздел предпросмотра добавлен как совместимое расширение v1; существующие схемы профиля и завершения не меняются.

Совместимые расширения v1: новые маршруты и необязательные поля ответов. Клиент игнорирует неизвестные поля ответов. Удаление или переименование полей, изменение типов, обязательности, перечислений, семантики ошибок и успешных статусов требуют `/api/v2` либо отдельного согласованного плана миграции. Новое обязательное поле запроса не добавляется в v1. Изменение политики лимитов и сроков безопасности документируется; клиент использует `expires_in` и `Retry-After`, а не зашитые значения.

## 2. Общие правила HTTP и форматов

- Базовый путь: `/api/v1`. Пути в таблицах указаны относительно него. JSON — UTF-8, `Content-Type: application/json`. Исключение: login принимает `application/x-www-form-urlencoded`.
- Защищённые методы принимают `Authorization: Bearer <access_token>`. Cookie не заменяет Bearer для профиля, онбординга и управления сессиями.
- Все обязательные поля передаются явно. Неизвестные поля JSON-запросов отклоняются с `422 VALIDATION_ERROR`. Неизвестные поля ответов игнорируются клиентом.
- Идентификаторы пользователя и сессии — строки UUID. Пользователь определяется авторизацией; `user_id` в запросах профиля не передаётся.
- Моменты времени — ISO 8601 с UTC-смещением (`Z` или `+00:00`). Календарные даты — `YYYY-MM-DD`, локальное время — `HH:mm:ss` без смещения. Эти локальные значения нельзя автоматически преобразовывать в UTC на клиенте.
- Текущий часовой пояс пользователя — IANA-имя, например `Asia/Yekaterinburg`. Он нужен для расписания и текущей даты и определяется браузером при сохранении первого шага. Отдельного часового пояса рождения в интерфейсе и публичном API нет.
- Ответы с токенами и персональными данными профиля/сессий: `Cache-Control: no-store`. Ответ `204` не содержит тела. Клиент не пытается разобрать его как JSON.
- Email валидируется, пробелы по краям удаляются, значение приводится к нижнему регистру; уникальность регистронезависима. Пароли и токены не обрезаются и не нормализуются.

### Общая ошибка

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Ошибка проверки данных",
    "details": {
      "fields": [
        { "field": "body.password", "code": "string_too_short", "message": "Слишком короткая строка" }
      ]
    }
  }
}
```

`error.code` и `error.message` обязательны. Сервер возвращает `details` как объект, при отсутствии подробностей — `{}`; для ошибок полей это объект с `fields`. Клиент устойчив к отсутствующему или null `details` в ответах промежуточной инфраструктуры. Путь поля включает источник и индекс: `body.birth_date`, `body.tasks.0.duration_min`, `header.idempotency-key`. Клиент принимает неизвестные коды и показывает безопасное `message`. Текст сообщения не используется для принятия решений. Ошибки не содержат введённый пароль, токен, исходное тело, traceback, `ctx` или внутренние тексты исключений. Неизвестный тип ошибки валидации получает сообщение «Некорректное значение».

| HTTP | Общий код | Назначение |
| --- | --- | --- |
| 401 | `AUTHENTICATION_REQUIRED` | Нет действующей авторизации; заголовок `WWW-Authenticate: Bearer` |
| 404 | `NOT_FOUND` | Неизвестный маршрут |
| 405 | `METHOD_NOT_ALLOWED` | Неверный метод; сохраняется `Allow` |
| 422 | `VALIDATION_ERROR` | Некорректные поля, типы или формат запроса |
| 429 | `RATE_LIMIT_EXCEEDED` | Ограничение частоты; `Retry-After` в секундах |
| 500 | `INTERNAL_ERROR` | Непредвиденная ошибка с безопасным сообщением |
| 503 | `SERVICE_UNAVAILABLE` | Недоступна необходимая инфраструктура |

Обработчики сохраняют `WWW-Authenticate`, `Allow`, `Retry-After`. В production `DEBUG=false`. Диагностический `/ready` имеет отдельный формат, описанный в разделе 11.

## 3. Авторизация

Пароль: 8–128 символов, минимум одна буква и одна цифра. Политика применяется при регистрации, сбросе и смене пароля. Хэширование — Argon2 через `pwdlib`; access — JWT HS256 через PyJWT, секрет из окружения. Подробности границ модуля: [ADR 0005](../../backend/docs/adr/0005-auth-boundaries.md).

### Методы

| Метод и путь | Запрос и авторизация | Успех |
| --- | --- | --- |
| POST `/auth/register` | JSON `{email, password}`, доверенный Origin | 202 `MessageResponse` для нового адреса; занятый email — 409 `EMAIL_ALREADY_EXISTS`; сессия не выдаётся |
| POST `/auth/resend-verification` | JSON `{email}`, доверенный Origin | 202 `MessageResponse` |
| POST `/auth/verify-email` | JSON `{token}`, доверенный Origin | 200 `TokenResponse` + refresh-cookie |
| POST `/auth/login` | Form `username=email`, `password`, необязательный `grant_type=password`; доверенный Origin | 200 `TokenResponse` + refresh-cookie |
| POST `/auth/refresh` | Refresh-cookie, доверенный Origin; без тела и обязательного access | 200 `TokenResponse` + новая refresh-cookie |
| POST `/auth/logout` | Refresh-cookie, доверенный Origin; access не требуется | 204; отзыв текущей сессии и очистка cookie |
| POST `/auth/logout-all` | Bearer; без тела | 204; отзыв всех сессий и очистка cookie |
| GET `/auth/sessions` | Bearer | 200 `SessionsResponse` |
| DELETE `/auth/sessions/{id}` | Bearer; UUID сессии | 204; отзыв своей сессии, для текущей очистка cookie |
| POST `/auth/password/forgot` | JSON `{email}`, доверенный Origin | 202 `MessageResponse` |
| POST `/auth/password/reset` | JSON `{token, new_password}`, доверенный Origin | 204; смена пароля, отзыв всех сессий, очистка cookie |
| POST `/auth/password/change` | Bearer, JSON `{old_password, new_password}` | 204; смена пароля, отзыв всех сессий, очистка cookie |

Все поля тел auth — строки. Email-токен: 1–256 символов; `old_password`: 1–128. Form-login использует правила существующего OAuth2PasswordRequestForm, а не JSON-схему. Социальный вход и выдача refresh в JSON для мобильного клиента не предусмотрены.

### Ответы

`TokenResponse`:

```json
{ "access_token": "<jwt>", "token_type": "bearer", "expires_in": 900 }
```

`expires_in` — положительное целое число секунд. Refresh никогда не передаётся в JSON. Auth-ответ не содержит пользователя, профиль или статус онбординга: после login/verify клиент запрашивает `/me`.

`MessageResponse`:

```json
{ "message": "Если действие доступно для указанного адреса, письмо будет отправлено" }
```

С 13 ноября 2026 года повторная регистрация возвращает `409 EMAIL_ALREADY_EXISTS` с сообщением «Аккаунт с этой почтой уже существует». Проверка регистронезависима; пробелы по краям email удаляются. Любой существующий адрес, включая неподтверждённый, неактивный и мягко удалённый аккаунт, остаётся занятым. Регистрация не меняет существующий пароль, состояние аккаунта, токены или сессии и не отправляет новое письмо. При одновременной регистрации одного адреса создаётся один аккаунт и отправляется одно письмо; ответы — один `202` и один `409`.

Новая регистрация по-прежнему возвращает `202 MessageResponse` и не создаёт профиль или сессию. Resend и forgot сохраняют нейтральный `202`, не раскрывающий наличие адреса. Повторная отправка подтверждённому адресу не создаёт новый токен. Forgot отправляет письмо только активной подтверждённой учётной записи. Технические сбои и лимиты по-прежнему возвращают соответствующие ошибки. Это отдельная доработка регистрации, не изменение CRUD задач или завершения онбординга.

`SessionsResponse`:

```json
{
  "items": [
    {
      "id": "33fbd053-f913-413e-917a-ae31814cefa6",
      "created_at": "2026-11-06T08:00:00Z",
      "expires_at": "2026-12-06T08:00:00Z",
      "last_used_at": "2026-11-06T09:00:00Z",
      "ip": "127.0.0.1",
      "user_agent": "Mozilla/5.0",
      "is_current": true
    }
  ]
}
```

Список содержит только активные сессии текущего пользователя по убыванию `last_used_at`, без пагинации. ID стабилен при ротации. `ip` и `user_agent` могут быть null, обновляются при refresh и не являются условиями авторизации. Чужая и отсутствующая сессия одинаково дают `404 SESSION_NOT_FOUND`. Повторный отзыв своей другой сессии допустим, пока сессия вызывающего активна. Отзыв текущей делает её Bearer недействительным, поэтому следующий запрос с ним даёт `401`. Logout с отсутствующей или недействительной cookie остаётся идемпотентным: `204` и очистка cookie.

### Ошибки auth

| HTTP | Код | Сценарий |
| --- | --- | --- |
| 409 | `EMAIL_ALREADY_EXISTS` | Регистрация адреса, уже занятого аккаунтом; сообщение «Аккаунт с этой почтой уже существует» |
| 401 | `INVALID_CREDENTIALS` | Неправильный email или пароль |
| 403 | `EMAIL_NOT_VERIFIED` | Правильный пароль, но email не подтверждён |
| 400 | `INVALID_EMAIL_TOKEN` | Повреждённый, истёкший, использованный токен или токен другого назначения |
| 401 | `INVALID_REFRESH_TOKEN` | Отсутствующий, истёкший, отозванный или повторно использованный refresh |
| 400 | `INVALID_CURRENT_PASSWORD` | Неверный старый пароль |
| 404 | `SESSION_NOT_FOUND` | Чужая или отсутствующая сессия |
| 403 | `CSRF_ORIGIN_DENIED` | Источник не разрешён |

Дополнительно действуют общие `422`, `429`, `503`. Ошибка login не запускает refresh и не повторяется автоматически.

### Письма и смена пароля

Ссылки: `${FRONTEND_URL}/verify-email#token=...` и `${FRONTEND_URL}/reset-password#token=...`. Клиент читает fragment, убирает токен из адресной строки и передаёт его в тело соответствующего POST. GET ссылки не меняет состояние; подтверждение выполняется явным действием пользователя.

Назначения токенов разделены: `verify_email` действует 24 часа, `reset_password` — 60 минут по умолчанию. Они одноразовые; в БД хранится SHA-256. Resend/forgot аннулирует прежний токен того же назначения. Токен подтверждения не подходит для сброса и наоборот. Одновременные подтверждения сериализуются; только одно успешно.

Пользователь и токен сначала фиксируются в PostgreSQL, затем письмо ставится в Celery. Сбой публикации даёт `503`; созданная неподтверждённая учётная запись сохраняется. Пользователь может запросить resend. Если публикация регистрации не удалась, немедленный resend допускается. Сетевая неопределённость не гарантирует, что письмо не поставлено в очередь. SMTP-задача имеет до трёх повторов с задержкой; email и токен скрыты в представлении аргументов и ошибках. Сообщения брокера содержат необходимые данные доставки и находятся в доверенной инфраструктуре.

Reset/change атомарно меняют пароль, отзывают все сессии и аннулируют остальные ссылки сброса. Ответ — пустой `204`, очистка cookie, `Cache-Control: no-store`. Автовход не выполняется; нужен новый login.

## 4. Cookie, CORS и жизненный цикл сессии

Cookie называется `refresh_token`: `HttpOnly`, `SameSite=Strict`, `Path=/api/v1/auth`, без `Domain`. `Secure=true` на staging/production; false допускается только для локального HTTP и тестов. Срок cookie — остаток абсолютного срока сессии. Удаление использует то же имя и путь.

Access по умолчанию действует 15 минут, отдельная сессия после login/verify — 30 дней. Refresh не продлевает абсолютный срок сессии. Ротация атомарна; повтор старого refresh отзывает всю сессию. Конкурирующие refresh не создают две действующие ветки. PostgreSQL — источник истины для отзыва; положительное состояние сессии не кэшируется в Redis. Отзыв сессии немедленно лишает силы её access.

CORS разрешает точные `CORS_ORIGINS` и credentials, без wildcard. Локально фронтенд `http://localhost:5173`, API `http://localhost:8000`; не смешивать `localhost` и `127.0.0.1`. Стенд — один сайт по HTTPS, в том числе допустимые поддомены. Для прямого cross-origin доступа браузера сервер открывает чтение `Retry-After`; через Vite `/api`-proxy expose не требуется.

Публичные изменяющие состояние auth POST из таблицы требуют точного доверенного Origin. При его отсутствии проверяется origin Referer. `Origin: null`, недоверенный источник и отсутствие обоих заголовков дают `403 CSRF_ORIGIN_DENIED`. Bearer-only методы не принимают cookie вместо access и не требуют этой cookie-проверки Origin. Ручным клиентам и Swagger для публичных auth POST нужен разрешённый Origin.

Обязательное поведение клиента:

1. Access хранится только в памяти. Пароль, access, refresh и email-токен не сохраняются в localStorage/sessionStorage. Auth fetch использует `credentials: 'include'`.
2. При загрузке приложения выполняется один refresh, затем `/me`. До ответа маршруты ждут восстановления. `401` refresh переводит на вход; сеть/`503` показывают повтор восстановления без потери черновика.
3. `401` защищённого запроса запускает один сериализованный refresh, затем максимум один повтор исходного запроса. Параллельные запросы используют общий результат. Сам refresh, login и verify не получают автоматических повторов. Сетевая ошибка refresh может означать уже выполненную ротацию.
4. Refresh сериализуется между вкладками через Web Locks. В текущей реализации без Web Locks гарантируется сериализация только внутри вкладки; это ограничение клиента, не разрешение параллельной ротации сервером. Вход/выход синхронизируются через BroadcastChannel.
5. Окончательный `401` завершает локальную авторизацию. `403`, `422`, `429`, сеть и `5xx` не превращаются в успешный ответ или ложный выход. Поздний ответ старого запроса не восстанавливает сессию после выхода или смены аккаунта.
6. Выход сначала подтверждается серверным logout. При сетевой ошибке клиент сообщает о ней и даёт повторить; не сообщает об успешном отзыве. После успеха очищаются access, профиль, Query cache и текущий черновик, закрываются защищённые маршруты.
7. После `/me` новый пользователь идёт на `next_step`, завершивший настройку — на исходный запрошенный внутренний URL с query/hash либо на `/today`. Внешний URL возврата не принимается. Переход напрямую на более поздний шаг возвращает к необходимому; назад к сохранённым шагам идти можно. Начальный экран знакомства не требует отдельного серверного шага.

## 5. Профиль: GET `/me`

Bearer обязателен. Успех: `200 ProfileDocument`, включая новый аккаунт без профиля. Отсутствие строки профиля не является `404`. Все три метода профиля/онбординга возвращают одну схему.

Новый аккаунт:

```json
{
  "id": "b7b6cdd4-0d1b-43ad-b657-e1f7f9a6766c",
  "email": "anna@example.com",
  "display_name": null,
  "profile": null,
  "onboarding": { "completed_at": null, "next_step": "birth_date" }
}
```

Сохранённый профиль:

```json
{
  "id": "b7b6cdd4-0d1b-43ad-b657-e1f7f9a6766c",
  "email": "anna@example.com",
  "display_name": "Анна",
  "profile": {
    "birth_date": "2003-09-20",
    "birth_time": null,
    "timezone": "Asia/Yekaterinburg",
    "chronotype": "owl",
    "work_start": "12:00:00",
    "work_end": "22:00:00",
    "sleep_time": "01:00:00"
  },
  "onboarding": { "completed_at": null, "next_step": "first_tasks" }
}
```

Все показанные ключи обязательны в ответе. `display_name` — строка или null; при null интерфейс использует email. `profile` — null либо объект со всеми перечисленными ключами. `birth_date`, `birth_time`, `chronotype` nullable до заполнения; неизвестное время рождения остаётся null и не мешает завершению. `timezone`, `work_start`, `work_end`, `sleep_time` не null. При создании профиля значения по умолчанию: `timezone=UTC`, `work_start=08:00:00`, `work_end=18:00:00`, `sleep_time=23:00:00`. Клиент первого шага явно передаёт текущий пояс браузера.

| Условие | `completed_at` | `next_step` |
| --- | --- | --- |
| Нет профиля или даты рождения | null | `birth_date` |
| Есть дата, но нет хронотипа или валидного режима | null | `chronotype` |
| Профиль заполнен, завершение не подтверждено | null | `first_tasks` |
| Завершение подтверждено | UTC timestamp | null |

Состояния проверяются в указанном порядке; завершённый профиль всегда остаётся полным. `completed_at` и `next_step` назначаются только сервером. Начальные часы не означают автоматически выбранный хронотип. Черновик клиента не изменяет серверный прогресс.

## 6. Сохранение шагов: PATCH `/me/profile`

Bearer обязателен. Успех: `200 ProfileDocument`. Метод создаёт профиль, если его ещё нет, и атомарно применяет переданные поля. Разрешены только `birth_date`, `birth_time`, `timezone`, `chronotype`, `work_start`, `work_end`, `sleep_time`. `display_name` доступен в ответе, но редактирование имени этим контрактом не предусмотрено.

Отсутствующее поле сохраняет прежнее значение. Null очищает только nullable-поля: `birth_date`, `birth_time`, `chronotype`. Пустой объект допустим, создаёт профиль с начальными значениями и не завершает онбординг. Ошибка в одном поле откатывает весь PATCH. Проверяется итоговое состояние с учётом сохранённых полей. Для завершённого профиля очищать `birth_date` или `chronotype` нельзя: `409 PROFILE_INCOMPLETE`, состояние не меняется. Валидное редактирование завершённого профиля сохраняет `completed_at` и `next_step=null`.

Первый шаг:

```json
{ "birth_date": "2003-09-20", "birth_time": null, "timezone": "Asia/Yekaterinburg" }
```

- `birth_date`: существующая дата от `1900-01-01` до текущей даты включительно в итоговом `timezone`.
- `birth_time`: `HH:mm:ss`, секунды `00`, от `00:00:00` до `23:59:00`, либо null. UI редактирует часы и минуты.
- `timezone`: валидное IANA-имя; пустая строка и null недопустимы. Это текущий пояс расписания, а не место рождения.
- `birth_timezone`, `birth_tz`, `birth_at_utc`, `birth_time_known`, `user_id`, `onboarding` и `completed_at` не принимаются из тела.

Совместимость с существующей БД: серверу предстоит заполнять внутренние `birth_tz=UTC` и `birth_at_utc` из даты и времени в фиксированной вычислительной шкале UTC; если время неизвестно, использовать 12:00 и `birth_time_known=false`. При указанном времени — `birth_time_known=true`. Это соглашение для расчёта, а не утверждение о реальном UTC-моменте рождения. Текущий `timezone` не используется для восстановления исторического места рождения; его изменение не меняет вычислительную дату рождения. Эти поля не раскрываются в DTO и не запрашиваются у пользователя. Существующие миграции не переписываются; реализацию такого преобразования и тесты добавляет владелец профиля. Текущий DB constraint завершения требует заполненного `birth_at_utc`.

Второй шаг:

```json
{ "chronotype": "owl", "work_start": "12:00:00", "work_end": "22:00:00", "sleep_time": "01:00:00" }
```

`chronotype`: `lark`, `dove`, `owl`. Сервер назначает `chronotype_source=manual`. Время — `HH:mm:ss`, секунды `00`. Рабочее окно в пределах одной локальной даты, `work_end > work_start`; пересечение полуночи не поддерживается. Отбой может быть после полуночи, его нельзя сравнивать строкой с концом рабочего дня. PATCH одного хронотипа не перезаписывает часы: клиент явно передаёт выбранный режим.

Режимы выбора интерфейса: `lark` — 08–18, отбой 23:00; `dove` — 09–19, отбой 23:30; `owl` — 12–22, отбой 01:00. Пользователь может менять часы. Предпросмотр окон справа является примером, а не ответом планировщика. Существующие подписи карточек слева не являются API-полями. Алгоритм биоритмов не определяется этим контрактом.

## 7. Завершение: POST `/onboarding/complete`

Bearer и заголовок `Idempotency-Key: <UUID>` обязательны. Успех: `200 ProfileDocument` с непустым `onboarding.completed_at` и `next_step=null`. Завершение подтверждает только сервер. Промежуточного `202`, фонового polling или отдельного фиктивного результата плана в этом методе нет.

```json
{
  "planned_date": "2026-11-06",
  "tasks": [
    { "title": "Подготовка к экзамену", "type": "intellectual", "duration_min": 90 }
  ]
}
```

| Поле | Правило |
| --- | --- |
| `planned_date` | Обязательная дата `YYYY-MM-DD`, равная текущей дате в сохранённом `profile.timezone` при первой обработке |
| `tasks` | Обязательный массив от 1 до 100 элементов, порядок сохраняется |
| `title` | Обязательная строка; сервер удаляет пробелы по краям, после этого 1–200 символов |
| `type` | `intellectual`, `physical`, `creative`, `routine` |
| `duration_min` | Обязательное целое число 5–480 включительно; дроби, строки и boolean недопустимы |

Сумма длительностей не превышает длину рабочего окна; нарушение — `422 VALIDATION_ERROR`, поле `body.tasks`. Клиентские ID строк не передаются. Сервер назначает ID задач. Профиль должен содержать дату рождения, хронотип и валидный режим; иначе `409 PROFILE_INCOMPLETE` без побочных эффектов. Внутренние поля профиля из раздела 6 вычисляет сервер, а не клиент.

Задачи, план на `planned_date` и отметка завершения фиксируются одной транзакцией. Ошибка не оставляет частичных задач или завершённого профиля. При невозможности разместить все задачи с учётом ограничений планировщика — `409 PLAN_CAPACITY_EXCEEDED`; при технической недоступности планировщика — `503 PLANNER_UNAVAILABLE`. Задачи не теряются молча, частичный план не подтверждает завершение. Алгоритм выбора слотов — ответственность планировщика. Чтение плана отдельным GET не входит в этот метод и не является условием открытия приложения.

### Повторные запросы

Ключ ограничен текущим пользователем и операцией завершения онбординга. Сервер хранит ключ успешной операции, точное разобранное JSON-тело и успешный ответ до удаления аккаунта, без TTL. Различие пробелов JSON и порядка ключей объекта не меняет тело; порядок массива и значения строк значимы, включая пробелы в названии до trim. Несовпадение тела с использованным ключом даёт `409 IDEMPOTENCY_CONFLICT` без изменений.

После проверки авторизации сервер сначала проверяет успешный повтор: тот же ключ и тело возвращают сохранённый `200` без повторного создания задач, даже если наступил следующий день или профиль позже изменён. Конкурирующие запросы с одним ключом сериализуются и получают один результат. Неуспешная/откаченная транзакция не фиксирует ключ как успешный: тот же ключ и тело можно повторить. При завершённом онбординге новый ключ даёт `409 ONBOARDING_ALREADY_COMPLETED` и не добавляет новые задачи.

Для нового запроса после проверки успешного повтора сервер проверяет: уже завершённый онбординг, полноту профиля, актуальность даты, валидацию и вместимость плана. Несовпадение текущей даты — `409 PLANNED_DATE_CHANGED`, details: `{ "planned_date": "YYYY-MM-DD", "timezone": "IANA" }`, где дата — актуальная серверная. Неверный формат даты/UUID — `422`.

Клиент сохраняет ключ и точное тело отправки в черновике этого аккаунта. Потеря ответа не создаёт новый ключ. При ручном повторе отправляются прежние ключ и тело; редактирование формы создаёт новую операцию. После `PLANNED_DATE_CHANGED` клиент обновляет заявку и ключ; после `IDEMPOTENCY_CONFLICT` не повторяет изменённое тело под прежним ключом. При `ONBOARDING_ALREADY_COMPLETED` клиент перечитывает `/me` и открывает приложение только при подтверждённом завершении. Сохранённый ответ повторной операции не подменяет последующие актуальные чтения `/me`.

### Ошибки профиля и онбординга

| HTTP | Код | Действие клиента |
| --- | --- | --- |
| 401 | `AUTHENTICATION_REQUIRED` | Один refresh и максимум один повтор |
| 403 | `EMAIL_NOT_VERIFIED` | Предложить подтвердить почту |
| 409 | `ONBOARDING_REQUIRED` | Для будущих функций, требующих настройки: перечитать `/me`, открыть `next_step` |
| 409 | `PROFILE_INCOMPLETE` | Сохранить черновик, перечитать `/me`, открыть необходимый шаг |
| 409 | `ONBOARDING_ALREADY_COMPLETED` | Перечитать `/me`, проверить завершение |
| 409 | `IDEMPOTENCY_CONFLICT` | Показать ошибку, не повторять изменённое тело с тем же ключом |
| 409 | `PLANNED_DATE_CHANGED` | Предложить новую отправку на актуальную дату |
| 409 | `PLAN_CAPACITY_EXCEEDED` | Сохранить задачи; предложить изменить длительность/режим |
| 422 | `VALIDATION_ERROR` | Показать ошибки полей, сохранить введённые значения |
| 429 | `RATE_LIMIT_EXCEEDED` | Соблюсти `Retry-After` |
| 503 | `SERVICE_UNAVAILABLE` / `PLANNER_UNAVAILABLE` | Сохранить черновик, дать повторить запрос |

GET `/me`, PATCH `/me/profile` и POST `/onboarding/complete` доступны до завершения настройки и сами не возвращают `ONBOARDING_REQUIRED`. `404` для существующего пользователя без профиля не является допустимым бизнес-ответом этих методов.

## 8. Предпросмотр плана и временные заглушки

### Предпросмотр плана: POST `/onboarding/preview`

Метод предназначен для правой карточки «Ваш план на сегодня» на экране «v4 · 1.4 · Первые задачи». Bearer обязателен; метод доступен до завершения онбординга. Тело — тот же `OnboardingRequest`, что у `/onboarding/complete`: `planned_date` и `tasks`. Действуют те же правила полей и полноты сохранённого профиля. Часы, хронотип и пояс берутся из сохранённого профиля текущего пользователя. `Idempotency-Key` не нужен: расчёт не создаёт задач, расписания, записи завершения или иных пользовательских данных, повтор безопасен.

Успех — `200 PlanPreview`, `Cache-Control: no-store`:

```json
{
  "planned_date": "2026-11-06",
  "timezone": "Asia/Yekaterinburg",
  "slots": [
    {
      "task_index": 0,
      "start_time": "10:00:00",
      "end_time": "11:30:00",
      "explanation": "Утреннее интеллектуальное окно подходит для сосредоточенной работы"
    }
  ],
  "unscheduled_task_indexes": []
}
```

Все показанные поля обязательны. `planned_date` совпадает с датой запроса; `timezone` — IANA-пояс сохранённого профиля. `start_time` и `end_time` — локальные часы `HH:mm:ss` с секундами `00` в этой дате и поясе; это не UTC timestamps. Рабочий день не пересекает полночь. Интервал строго положительный, находится внутри рабочего дня и длится `duration_min` соответствующей задачи. `slots` отсортированы по времени, не пересекаются, не заходят на системные перерывы. Здесь возвращаются только задачи, без строк обеда, отдыха и перерывов.

`task_index` — целочисленный индекс в массиве исходного запроса, начиная с нуля. Название и тип берутся из соответствующей задачи запроса; постоянных task ID у предпросмотра нет. Каждая задача встречается ровно один раз: либо одним неделимым слотом в `slots`, либо индексом в `unscheduled_task_indexes`. Повторяющиеся и выходящие за границы индексы недопустимы. Пустой массив `slots` допустим, если все задачи перечислены как неразмещённые.

`explanation` — непустое безопасное текстовое пояснение размещения на русском, без HTML. Причину формирует планировщик. Проценты биоритмов допустимы только по реальным расчётам сервера; фронтенд не придумывает значения и не разбирает текст как машинный код. Карточка показывает сверху моноширинный интервал, под ним название, ниже пояснение меньшим шрифтом; цветная точка соответствует типу задачи. Для неразмещённых задач показывается «Время не определено» и предложение изменить длительность или режим.

Если общая длительность не превышает рабочего окна, но реальные ограничения мешают разместить часть задач, preview возвращает `200` с неразмещёнными индексами. Completion при той же ситуации возвращает `409 PLAN_CAPACITY_EXCEEDED` и ничего не сохраняет. Превышение общей длительности рабочего окна — `422` в обоих методах. Другие ошибки: `401 AUTHENTICATION_REQUIRED`, `403 EMAIL_NOT_VERIFIED`, `409 PROFILE_INCOMPLETE`, `409 PLANNED_DATE_CHANGED`, `422 VALIDATION_ERROR`, `429 RATE_LIMIT_EXCEEDED`, `503 SERVICE_UNAVAILABLE` / `PLANNER_UNAVAILABLE`, в общем формате.

Клиент пересчитывает preview после изменения задач с задержкой 350 мс, отменяет устаревшие запросы, не показывает ответ предыдущего набора задач как новый. Сеть, ошибки авторизации, валидации и `5xx` показываются с возможностью повторить; они не подменяются удачным локальным расчётом. Дата и профиль могут измениться между preview и complete: completion заново проверяет данные и атомарно строит окончательный план. Предпросмотр не гарантирует неизменность интервалов и не даёт статус «Готово». Переход в приложение выполняется только после подтверждённого завершения. Получение сохранённого плана для главной страницы остаётся отдельным будущим API.

### Режим разработки

До реализации трёх методов профиля клиент при их `404` использует локальную заглушку. При `404` `/onboarding/preview` включается предварительная локальная раскладка по окнам выбранного хронотипа: без расчёта биоритмов, вымышленных процентов и статуса «Готово». Локальный preview не сохраняет план и не завершает настройку. Настоящие register/login/verify/resend/refresh/logout остаются на API. Заглушка требует настоящую сессию и не создаёт авторизацию.

Профиль и первые задачи хранятся только в браузере, отдельно по `pd-local-profile:<user_id>`. Декодирование `sub` из полученного access используется исключительно для разделения локальных данных, не для серверной проверки JWT. Клиентское `local=true` — метаданные заглушки, не поле серверной схемы. Черновик также привязан к владельцу; чужой аккаунт его не получает.

При доступном `/me` серверный ответ всегда имеет приоритет. Локальное завершение не подтверждает серверное. Автоматической отправки накопленных данных на сервер нет. Сеть, `401`, `403` и `5xx` не подменяются успешной заглушкой. После реализации методов профиля, preview и завершения команда удаляет fallback до production-приёмки; это не альтернативный серверный режим и не часть постоянного API.

## 9. Границы бэкенда и хранение

| Область | Владелец auth | Владелец профиля/биоритмов |
| --- | --- | --- |
| Учётная запись | Регистрация, пароль, подтверждение, безопасность `User` | Использует `User.id` |
| Профиль | Не создаёт профиль при регистрации | `UserProfile`, `/me`, `/me/profile`, завершение |
| Авторизация | `get_current_user`, проверка access и сессии | Подключает общую зависимость, ограничивает данные `user.id` |
| Сессии | Таблицы, refresh, отзыв, список устройств | Не реализует альтернативную проверку JWT |
| План/биоритмы | Не реализует | Расчёты, создание задач/плана, проверка онбординга |
| Redis | Auth-лимиты `pd:auth:` | Отдельные префиксы для своего кэша |

Публичный импорт: `from app.core.security import get_current_user`, сигнатура `async def get_current_user(...) -> User`. Роутер использует `Annotated[User, Depends(get_current_user)]`; внутренние аргументы не передаёт. Тесты могут использовать `app.dependency_overrides[get_current_user]`.

Зависимость читает только Bearer, проверяет HS256, обязательные `sub`, `sid`, `iat`, `exp`, срок JWT, пользователя и сессию в PostgreSQL. Алгоритм не берётся из непроверенного JWT. Отсутствующий/некорректный access, отсутствующая, истёкшая, отозванная или чужая сессия, неактивный/удалённый/отсутствующий пользователь дают `401 AUTHENTICATION_REQUIRED`. Активный пользователь без подтверждения — `403 EMAIL_NOT_VERIFIED`.

Зависимость не требует Redis, профиля или завершённого онбординга, не загружает профиль и завершает собственную транзакцию чтения до роутера. Сервис профиля может открыть `session.begin()` на той же сессии БД. Дополнительная проверка онбординга для биоритмов/расписания остаётся у их владельца.

Текущая локальная head миграций — `0006` (дедлайн задачи со временем); auth-таблицы `sessions`, `refresh_tokens`, `email_tokens` добавлены в `0005`. Существующие миграции не переписываются; новые строятся поверх объединённой head. Перед объединением проверяется одна Alembic head. Изменения ORM и миграция входят в один PR. Общие `app/main.py`, `app/core/config.py`, `app/db/models.py`, `app/workers/celery_app.py`, `pyproject.toml`, `uv.lock` и Compose согласуются владельцами. Новые задачи добавляются к существующему Beat, модели — к общей metadata. Никто не очищает Redis целиком.

Celery Beat раз в час запускает `auth.cleanup_expired`: удаляет истёкшие сессии с историей refresh каскадно и истёкшие email-токены. Отозванные сессии и использованные refresh сохраняются до исходного срока для обнаружения повторов. Неистёкшие email-токены, пользователи, профили и Redis-кэш не удаляются. Повторный запуск безопасен; нужны worker и beat.

## 10. Лимиты и конфигурация

| Действие auth | Текущий лимит |
| --- | --- |
| Login | 5 запросов/мин на IP + email |
| Register | 10 запросов/час на IP |
| Forgot | 3 запроса/час отдельно на IP и email |
| Change password | 5 запросов/мин на пользователя |
| Resend | 1 запрос/60 секунд на email |
| Прочие публичные auth-маршруты | 30 запросов/мин на IP |

Лимиты действуют и для неизвестных адресов. Redis DB 0, `pd:auth:`, ключи с TTL, email в ключе хэшируется. Недоступность Redis на лимитируемом методе — `503`. IP берётся из соединения; forwarded-заголовки доверяются только настроенному reverse proxy. Отдельных численных лимитов профиля v1 не задаёт; клиент в любом случае обрабатывает `429` инфраструктуры с `Retry-After`.

### Обязательные сценарии совместной проверки

1. Register нового адреса возвращает `202`, сессии ещё нет. Повтор регистрации даёт `409 EMAIL_ALREADY_EXISTS`, не меняет аккаунт и не отправляет письмо; разный регистр email не обходит проверку. До подтверждения правильный login даёт `403 EMAIL_NOT_VERIFIED`.
2. Письмо появляется в Mailpit; ссылка открывает экран без автоматического подтверждения. Явный verify даёт `200`, cookie и access. Повтор токена — `400 INVALID_EMAIL_TOKEN`. Resend соблюдает 60 секунд и заменяет прежний токен.
3. Новый аккаунт получает `/me` с `profile=null`, `next_step=birth_date`. Дата и необязательное время сохраняются без поля часового пояса рождения; текущий пояс передаётся автоматически. После перезагрузки возвращается правильный шаг.
4. PATCH даты переводит к хронотипу, PATCH хронотипа/часов — к задачам. Некорректный PATCH ничего не меняет. Прямой переход вперёд не обходит необходимый шаг.
5. Completion создаёт задачи/план/отметку вместе. Повтор ключа и тела после потери ответа не дублирует данные, включая повтор на следующий день. Другое тело с ключом — конфликт; новый ключ после завершения — уже завершено. Две параллельные отправки дают один результат.
6. Ошибка планировщика откатывает все изменения. Неактуальная дата, незаполненный профиль, слишком длинные задачи и некорректные поля имеют описанные коды. Ошибки не теряют черновик и не сообщают ложное завершение.
7. Существующий завершивший настройку пользователь возвращается на запрошенный URL. Перезагрузка восстанавливает сессию через cookie, access не появляется в браузерном хранилище. Несколько защищённых `401` выполняют один refresh; исходные запросы повторяются максимум один раз.
8. Проверяются отзыв сессии, logout-all, чужой UUID, абсолютный срок, параллельные вкладки, повтор старого refresh, сеть/`503`, поздний ответ после выхода и смена аккаунта. Черновики разных пользователей не смешиваются.
9. Forgot нейтрален, reset/change отзывают все сессии, старые access/refresh недействительны, требуется новый вход. Cleanup безопасен и не удаляет живые данные.
10. Сравниваются OpenAPI работающего API и этот контракт: методы, типы, статусы, Bearer, cookie, ошибки, `Retry-After`, CORS. Выполняется приёмка с настоящим API профиля и отключёнными локальными заглушками. Тесты с заглушками не подтверждают готовность серверной интеграции.
11. Preview пересчитывается при изменении названия, типа, длительности и набора задач, показывает время, название и пояснение в порядке макета. Устаревший ответ не заменяет новый. Проверяются неразмещённые задачи, отсутствие пересечений и попадания на перерывы, разные хронотипы, длинные названия и узкий экран. Ни предпросмотр, ни его ошибка не создают задачи и не завершают онбординг.

### Правила планировщика и передача интеграции

Текущая версия — `planner-1.0.1`; версия математического ядра биоритмов остаётся `1.0.0`. Исправление 1.0.1 исключает из **preview** интервалы, у которых длительность по местным часам отличается от реальной из-за перевода стрелок: существующий декодер фронтенда проверяет обе границы и разность `HH:mm`. Неоднозначные местные границы также исключаются. Сохранённое расписание и completion используют точные UTC-интервалы; preview не гарантирует совпадения их конкретного размещения.

- Вычислительное рождение — дата и известное время в UTC, неизвестное время — 12:00 UTC. Часовой пояс профиля определяет локальный день, рабочее окно и отображение. Переход DST может менять реальную длину дня и рабочего окна.
- Шаг сетки — 15 реальных минут от локального `work_start`; начало округляется вверх относительно `now`. Длительность задачи сохраняется точно, без округления до шага, задача неделима. Явно выбранный текущий день разрешён независимо от скрытых `wake_time` и `work_days`; рабочие дни учитываются при автоматическом поиске будущей даты.
- Оценка типа `T`: среднее по длительности `c_T(local_hour - shift) * (0.75 + 0.25*sin(2*pi*t/P))`. Берутся середины 15-минутных частей и точная укороченная последняя часть. Периоды — 23/28/33 суток, сдвиги хронотипов — lark −1, dove 0, owl +3 часа. Для рутины — среднее `1 - max` трёх оценок. Предпочтительное начало даёт +0.3 в пределах ±30 реальных минут; сосед одинакового типа — штраф 0.15 с каждой стороны.
- Сортировка: приоритет high/medium/low, интенсивность intellectual/physical → creative → routine, длительность по убыванию, `created_at`, UUID. Для черновиков последняя развязка — исходный индекс. Приоритет не умножает оценку. Точное равенство оценки сохраняет самый ранний UTC-старт. Округлять оценку до выбора нельзя. Алгоритм детерминированный жадный, глобальный оптимум не гарантируется.
- Фазы и критичность дня определяются общим ядром биоритмов; для нагрузки и выбора будущей даты значение цикла берётся в местные 12:00. При повторяющемся полудне выбирается более ранний UTC-момент. Множители критичности 0/1/2/3: 1/0.8/0.65/0.5; любой минимум добавляет один множитель 0.9. Ёмкость — `floor((реальное рабочее окно − объединение системных интервалов) * load_factor)`. Интенсивные задачи ограничены `floor(240 * load_factor)` минутами. Резерв 15% не вычитается: `OVERLOAD` появляется при плановой нагрузке строго больше 85% ёмкости либо при неразмещённых задачах.
- Между интенсивными задачами — минимум 10 минут; после непрерывной работы >90 минут — 15 минут, >120 минут — 30 минут; между интеллектуальными задачами — 30 минут. Совпадающие требования берутся по максимуму, не суммируются. Обед и отдых могут выполнять требование перерыва. Для двойного/тройного критического дня обязательны 1/2 блока отдыха по 30 минут.
- Автопереносы разрешены только для обычного replan: незакреплённая и неначатая intellectual/physical задача, высокий приоритет **или** длительность ≥60 минут, дедлайн разрешает перенос. Выбирается ближайший известный рабочий некритический день из следующих семи, с соответствующим циклом ≥0, где целиком помещаются задача и все уже существовавшие задачи. Отсутствующий снимок будущего дня не означает свободный день. Рекомендации могут предпочитать подтверждённый пик ≥0.5; они сами не меняют даты. Дедлайн — включительная местная дата до следующей местной полуночи.
- При пересчёте прошедшие, начатые, выполненные и текущие закреплённые интервалы защищены. Начало ровно в `now` считается начатым, конец ровно в `now` — прошедшим. Пропущенная история остаётся видимой, но не расходует нагрузку/интенсивность. Утерянный снимок исторической задачи или несовместимое изменение длительности/начала отклоняются. Изменения профиля и затронутых текущих/будущих планов сохраняются атомарно.

`contracts/fixtures/planner_cases.json` содержит правила, ≥20 входов и полных ожидаемых результатов, включая хронотипы, критические дни, закрепления, дедлайны, перерывы, перегрузку, историю и DST. Раздел `http_preview_cases` содержит профиль, зафиксированный серверный момент, HTTP-тело и ожидаемый preview; его проверяют реальный API и настоящий `previewPlan` фронтенда. Внутренние `PlanContext`/`PlanResult` из эталонов **не являются** схемами CRUD. Интервалы, индексы и коды сравниваются точно, числа — с абсолютным допуском 1e-12. Для переносимости только экспорт округляет числа до 12 знаков; это не округление алгоритма.

Подключение CRUD Григория: внутри одной внешней `session.begin()` сначала войти в `ScheduleService.mutation(user_id)`, затем изменить/flush задачу и вызвать `replan(user_id, day, trigger)`. При смене даты пересчитать обе даты в той же транзакции. Используется мягкое удаление; исторические снимки нужны для сохранения истории. Сервис сам не делает commit. При автопереносах он сохраняет source и все `future_plans`, статусы и даты одной транзакцией. Новая версия деактивирует старую; блокировка пользователя предотвращает гонку первого плана и переносов. Для готового интерфейса БД необходима миграция `0006` (постоянные успешные повторы онбординга, точный коэффициент 0.585).

## 12. CRUD задач: контракт спринта

Зафиксирован 11 ноября 2026 года, шаг 1 из 8. На шаге 6 реализованы сервис и HTTP-маршруты задач. На шаге 2 добавлена новая миграция `0006`: в схеме `0005` поле `deadline` имеет тип `date`, после применения `0006` — `timestamptz`; ORM использует `datetime`. Раздел определяет контракт нашего CRUD, а не подтверждает согласование всех предложений фронтенда.

На шаге 3 добавлены Pydantic-схемы `TaskCreate`, `TaskPatch`, `TaskStatusCommand`, `TaskListQuery`, `TaskDeleteQuery`, `TaskResponse` и `TaskList` в `backend/app/modules/tasks/schemas.py`. Они проверяют поля и фильтры, сохраняют различие пропуска поля и `null` в PATCH, нормализуют моменты в UTC и исключают внутренние поля из ответа. Проверка профиля, переходов статуса, версий и итогового сочетания даты с дедлайном в поясе пользователя относится к сервису шага 5; схемы не обращаются к БД. Query-схемы принимают исходные `QueryParams` для обнаружения повторов; при подключении маршрутов на шаге 6 повторы нужно проверять до преобразования параметров в обычный словарь.

На шаге 4 добавлен `TaskRepository` в `backend/app/modules/tasks/repository.py`. `get(user_id, task_id, for_update=False)` читает только собственную неудалённую задачу; при блокировке обновляет ранее загруженное ORM-состояние. `list(user_id, query)` принимает проверенный `TaskListQuery` и возвращает `(items, total)` с фильтрами, порядком и пагинацией из 12.6. `save(task)` сохраняет подготовленный сервисом ORM-объект через flush/refresh без commit; владельца новой задачи задаёт сервис по авторизации, существующую задачу для изменения он получает через `get(..., for_update=True)`. Репозиторий не назначает статусы и версии, не удаляет строки физически и не меняет расписание. Транзакцией управляет вызывающий сервис шага 5.

На шаге 5 реализованы `TaskService` и `TaskChanged` с обработчиком по умолчанию без действий. Сервис принимает сессию, `Clock` и необязательный обработчик события; методы `get`/`list` возвращают DTO, `create` принимает `TaskCreate`, `patch` — `TaskPatch`, команды `complete`/`skip`/`reopen` и `delete` — прочитанную версию задачи. Все методы получают доверенный `user_id` от вызывающего кода; проверка JWT остаётся общей зависимостью маршрутов шага 6. Сервис сам открывает и завершает транзакцию, поэтому перед вызовом сессия должна быть без активной транзакции. Он проверяет профиль и локальную дату дедлайна, статусы, закрепление и версию под блокировкой; формирует ответ до commit и вызывает хук после commit. При переносе `moved_from_date` не заполняется: это поле для будущих автоматических переносов планировщика. После мягкого удаления обращения возвращают `404`, включая конкурентный запрос, ожидавший блокировку удалённой задачи. Маршруты и расписание этим шагом не подключаются.

### 12.1. Границы и зависимости

В спринт входят создание, чтение, редактирование, мягкое удаление, выполнение, пропуск и перенос задачи на другую дату. Все пути ниже относительны `/api/v1`, требуют Bearer и возвращают `Cache-Control: no-store`, включая ошибки. Пользователь определяется через существующий `get_current_user`; `user_id` из запроса не принимается.

Для любой записи нужен существующий профиль с корректным IANA-поясом, иначе `409 PROFILE_INCOMPLETE`. Завершённый онбординг не требуется. Чтение собственных задач доступно и без профиля. Используются существующие общие ошибки и утилиты времени; альтернативная авторизация не добавляется.

Ядро планировщика принадлежит второму бэкендеру: профили энергии, хронотипы, подбор слотов, перерывы, критические дни, автоматические переносы и объяснения не реализуются и не меняются. CRUD не вызывает планировщик и не изменяет `schedules`/`schedule_slots`. Пересчёт и согласованное обновление расписания подключаются отдельным интеграционным этапом; старое расписание после изменения задачи не считается автоматически актуальным.

Ввод предпочтительного времени, pin/unpin, фактических интервалов выполнения, повторений и подзадач отложен. Онбординг, регистрация, уведомления, синхронизация и фронтенд не входят в эти восемь шагов. Ветка `feature/biorhythms-task-forms-timeline` автоматически не объединяется.

| POST `/tasks/{id}/skip` | JSON `{"version": N}` | `200 Task` |
| POST `/tasks/{id}/reopen` | JSON `{"version": N}` | `200 Task` |

Перенос даты выполняется PATCH поля `planned_date`; отдельный `/move` в этом спринте не добавляется. Изменяющие методы возвращают только задачу либо пустой `204`, без оболочки `{task, schedule, changes}` и без фиктивного расписания. Сбой будущего расчёта не моделируется как успешный пересчёт.

### 12.3. Поля и форматы

| Поле | Создание | PATCH и валидация |
| --- | --- | --- |
| `title` | Обязательно | Строка; после удаления пробелов по краям 1–200 символов |
| `description` | По умолчанию `null` | Строка или `null`; `null` очищает |
| `type` | Обязательно | `intellectual`, `physical`, `creative`, `routine` |
| `priority` | По умолчанию `medium` | `high`, `medium`, `low` |
| `duration_min` | Обязательно | Строго целое число 5–480; строки, дроби и bool недопустимы |
| `planned_date` | Обязательно | Локальная календарная дата `YYYY-MM-DD` в поясе профиля |
| `deadline` | По умолчанию `null` | Момент с датой, временем и явным UTC-смещением либо `null` |
| `version` | Не принимается | Обязательное целое число от 1, версия прочитанной задачи |

Пропущенное в PATCH поле сохраняет прежнее значение. `null` допустим только для `description` и `deadline`; тело только с `version` недопустимо. Неизвестные поля отклоняются. Клиент не задаёт ID, статус, отметки времени, владельца или поля закрепления. Новая задача получает серверный UUID, `pending`, `version=1`, `is_pinned=false`, `pinned_start=null`, `preferred_start=null`; поля выполнения пусты.

`Task` содержит все семь полей задачи из таблицы без входной `version`, а также `id`, `status`, `completed_at`, `version`, `created_at`, `updated_at`, `preferred_start`, `is_pinned`, `pinned_start`. Все ключи обязательны в ответе; `description`, `deadline`, `completed_at`, `preferred_start`, `pinned_start` допускают `null`. Поля `preferred_start`, `is_pinned`, `pinned_start` доступны только для чтения и сохраняют существующие значения. Остальные внутренние поля ORM, включая `user_id`, `deleted_at` и фактические интервалы, не сериализуются.

Моменты `deadline`, `completed_at`, `created_at`, `updated_at`, `pinned_start` принимают явное смещение там, где являются входом, и возвращаются в UTC с `Z`. Например, `2026-11-11T14:00:00+05:00` нормализуется в `2026-11-11T09:00:00Z`. Дата без времени и момент без смещения для `deadline` недопустимы. `preferred_start` при чтении — локальные часы `HH:mm:ss` без смещения.

Прошлые `planned_date` и просроченные относительно текущего момента дедлайны допустимы. Локальная дата `deadline` в поясе профиля не может предшествовать `planned_date`; проверяется итоговое состояние после PATCH. CRUD не подбирает время, не проверяет ёмкость рабочего окна и не запрещает длительность лишь из-за того, что задача не помещается в будущий план.

При миграции старый `deadline`-день означает последний момент этого локального дня в поясе профиля; без профиля используется UTC. `NULL` сохраняется. Обратная миграция оставляет локальную дату и теряет точность времени. Старые ревизии Alembic не переписываются. Будущий планировщик должен учитывать точный момент дедлайна вместо сравнения только дат.

Пример создания:

```json
{
  "title": "Подготовить отчёт",
  "type": "intellectual",
  "duration_min": 60,
  "planned_date": "2026-11-11",
  "deadline": "2026-11-11T18:00:00+05:00"
}
```

Пример переноса с прочитанной версией, одновременно продлевающий дедлайн:

```json
{
  "version": 1,
  "planned_date": "2026-11-12",
  "deadline": "2026-11-12T18:00:00+05:00"
}
```

### 12.4. Статусы и закреплённые задачи

| Операция | Исходный статус | Итог |
| --- | --- | --- |
| Создание | Новая задача | `pending`, `completed_at=null` |
| `complete` | `pending`, `scheduled` | `done`, `completed_at` задаёт сервер по UTC-часам |
| `skip` | `pending`, `scheduled` | `skipped`, `completed_at=null` |
| `reopen` | `done`, `skipped` | `pending`, `completed_at`, `actual_start`, `actual_end` очищаются |
| PATCH полей размещения | `scheduled` | `pending` |
| PATCH остальных полей | Любой | Статус сохраняется |

Поля размещения: `planned_date`, `duration_min`, `type`, `priority`, `deadline`. При реальном изменении любого из них `scheduled` сбрасывается в `pending`; `done` и `skipped` сохраняются. Название и описание на размещение не влияют. `scheduled` назначает будущая интеграция, а не клиент CRUD.

Повтор `complete` для `done`, `skip` для `skipped` и `reopen` для `pending` с актуальной версией возвращает текущую задачу без изменения версии и времени. Остальные переходы вне таблицы дают `409 TASK_STATUS_CONFLICT`. Для перехода между `done` и `skipped` нужен `reopen`. Повтор `complete` не заменяет первоначальный `completed_at`.

У закреплённой задачи реальное изменение полей размещения запрещено с `409 TASK_PINNED`; название, описание и команды статуса доступны. Существующее закрепление не очищается и не пересоздаётся. Проверки пересечения слотов и автоматическое снятие закрепления не входят в CRUD.

### 12.5. Транзакции, версии и удаление

Любое изменение существующей задачи сначала находит собственную неудалённую задачу и блокирует её строку в транзакции. Затем проверяет входную версию и итоговую валидацию; устаревшая версия всегда даёт конфликт, даже при совпадающих значениях. Конкурирующие изменения одной версии дают один успех и один `409 TASK_VERSION_CONFLICT`. Ошибка не оставляет частичных записей.

Реальное изменение увеличивает `version` ровно на один и обновляет `updated_at`. PATCH с переданными изменяемыми полями, итоговые значения которых уже совпадают после нормализации, возвращает задачу без изменения версии и времени. Повторное чтение GET не меняет состояние.

Удаление мягкое: устанавливает `deleted_at`, обновляет `updated_at` и увеличивает версию. Строка сохраняется для будущей синхронизации. Чужие, удалённые и отсутствующие UUID одинаково дают `404 TASK_NOT_FOUND`; повтор DELETE также даёт `404`. Ссылки из расписания не удаляются и не изменяются.

После потери ответа записи клиент сначала перечитывает задачу, а после потери ответа создания — список; автоматически повторять создание нельзя. Идемпотентный клиентский ID и `Idempotency-Key` для CRUD в этот спринт не входят. Это не меняет существующий отдельный контракт идемпотентности онбординга.

### 12.6. Список

GET `/tasks` принимает необязательные `date`, `from`, `to`, `status`, `type`, `limit`, `offset`. `date` нельзя сочетать с `from` или `to`; диапазон допускает одну границу, обе включительны, `from <= to`. Без дат возвращаются задачи всех локальных дат. `status` и `type` — одиночные значения соответствующих enum. Пустые и повторяющиеся query-параметры, а также неизвестные параметры отклоняются с `422 VALIDATION_ERROR`.

`limit` — целое 1–100, по умолчанию 50; `offset` — целое от 0, по умолчанию 0. Порядок возрастающий: `planned_date`, затем `created_at`, затем `id`. `TaskList` имеет вид `{"items": [], "total": 0, "limit": 50, "offset": 0}`; `total` учитывает фильтры до пагинации. Удалённые и чужие задачи исключены всегда. Пустая выборка — успешный `200`.

### 12.7. Ошибки и будущая интеграция

| HTTP | Код | Смысл |
| --- | --- | --- |
| 404 | `TASK_NOT_FOUND` | Задача чужая, удалена или отсутствует |
| 409 | `TASK_VERSION_CONFLICT` | Переданная версия устарела |
| 409 | `TASK_STATUS_CONFLICT` | Переход статуса не разрешён |
| 409 | `TASK_PINNED` | Попытка изменить поля размещения закреплённой задачи |
| 409 | `PROFILE_INCOMPLETE` | Для записи нет профиля с корректным поясом |
| 422 | `VALIDATION_ERROR` | Неверные поля, форматы, фильтры или итоговое сочетание даты и дедлайна |

Применимы общие ошибки авторизации и инфраструктуры из разделов 2–3, включая `403 EMAIL_NOT_VERIFIED`. Формат — `{error: {code, message, details}}`; пути полей содержат источник, например `body.deadline` или `query.version`. Конфликты не раскрывают чужие данные; актуальную задачу клиент получает через GET.

Сервис использует расширение `TaskChanged` по образцу `ProfileChanged`: `user_id`, `task_id`, `operation` (`created`, `updated`, `deleted`, `completed`, `skipped`, `reopened`), `changed_fields`, `old_planned_date`, `new_planned_date`, итоговая `version`, `occurred_at` в UTC. При создании старая дата — `null`, при удалении новая — `null`; перенос содержит обе даты. `changed_fields` включает реально изменённые поля, включая статус и отметки выполнения, но исключает служебные `version` и `updated_at`.

Хук вызывается после успешного commit только при реальном изменении. При rollback или отсутствии изменений не вызывается. Обработчик этого спринта ничего не делает, не обращается к Redis, Celery или планировщику. Он не является надёжной очередью событий. Доставка событий, обработка сбоев пересчёта и атомарность задачи с новым расписанием определяются отдельно при интеграции.

### 12.10. Приёмочные тесты CRUD, шаг 7

Основные проверки схем, репозитория, миграции, сервиса и HTTP добавлялись вместе с реализацией. На шаге 7 добавлены 19 сценариев в `backend/tests/integration/test_tasks_acceptance.py`:

- Конкурирующие PATCH, выполнение, пропуск и DELETE с одной версией дают одну успешную запись. Второй запрос получает конфликт версии либо `404`, если победило удаление; версия и событие меняются ровно один раз.
- Повторные команды и PATCH без реальных изменений сохраняют версию, время и число событий. Устаревшая версия конфликтует даже при повторном выполнении той же команды.
- Частичный PATCH сохраняет пропущенные поля и очищает только явно переданные nullable-поля; некорректный перенос не оставляет частичных изменений.
- Список при пагинации не содержит чужие и удалённые задачи, сохраняет порядок и полный `total`, в том числе при offset за концом выборки.
- Ошибка после SQL flush в PATCH, выполнении и удалении даёт безопасный `500`, откатывает изменения и не отправляет событие.
- Удалённая задача недоступна во всех шести маршрутах чтения и изменения, а tombstone остаётся в БД.
- Обработчик события по умолчанию не меняет сохранённые расписания и слоты при переносе, выполнении и удалении задачи.

Новые сценарии используют настоящую авторизацию и отдельные тестовые PostgreSQL/Redis. Полный набор бэкенда также проверяет доставку писем с отдельным Mailpit. Команды из `backend` при запущенном Docker Desktop:

```powershell
$env:DEBUG = "false"
.\.venv\Scripts\python.exe -m pytest tests/integration/test_tasks_acceptance.py -q
.\.venv\Scripts\python.exe -m pytest -q --cov=app.modules.tasks --cov-branch --cov-report=term-missing
```

Первая команда должна дать `19 passed`. Отчёт покрытия второй команды показывает выполненные строки и ветви, а не гарантирует отсутствие всех возможных ошибок. Ручная проверка HTTP описана в 12.9; подключение фронтенда и ядра планировщика остаётся отдельной работой.
