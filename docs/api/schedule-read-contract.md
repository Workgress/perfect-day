# API чтения сохранённого расписания

Дата: **18 ноября 2026 года**. Шаг 3 задачи. Основание — [сверка](tasks-schedule-audit.md) и выбранные пользователем границы API.

**Статус:** контракт подготовлен для реализации на шаге 4. HTTP-маршрут ещё не подключён. Готовые `ScheduleReader`, `ScheduleReadResult`, хранение результата и Core не изменяются. Подтверждение фронтендера по отдельному [контракту CRUD](tasks-frontend-contract.md) по-прежнему ожидается и не считается полученным этим документом.

## 1. Запрос и доступ

```http
GET /api/v1/schedule?date=2026-11-18
Authorization: Bearer <access_token>
Accept: application/json
```

| Параметр | Правило |
| --- | --- |
| `date` | Обязательная календарная дата строго `YYYY-MM-DD`, например `2026-11-18`; ровно одно значение |
| Остальные query-параметры | Не поддерживаются; в том числе `user_id`, `from`, `to`, `timezone` дают `422 VALIDATION_ERROR` |

Дата без ведущих нулей, timestamp вместо даты, пустое значение, несуществующая дата и повтор `date` отклоняются с `422`. Нет неявного «сегодня»: пропуск `date` также даёт `422`. Прошлые и будущие корректные даты допустимы; отсутствие плана определяется отдельно.

`date` выбирает локальный календарный день сохранённого расписания, а не UTC-интервал, вычисляемый клиентом. Маршрутов-синонимов `/schedule/{date}`, чтения диапазона или истории в этой задаче нет.

Используется существующий `get_current_user`: валидный access-токен, активная сессия и подтверждённый email. Владелец берётся только из авторизации. Чтение чужих расписаний и анонимные ссылки не предоставляются.

Для чтения требуется профиль с `onboarding_completed_at != null`. Отсутствующий профиль или незавершённый онбординг дают `409 ONBOARDING_REQUIRED`, а не `404` расписания. Повторно проверять готовность профиля к расчёту или требовать текущий timezone для пересчёта не нужно: GET ничего не рассчитывает, сохранённый результат уже содержит пояс.

## 2. Успешный ответ

`200 OK`, `Content-Type: application/json`, `Cache-Control: no-store`. Тело — существующий `ScheduleReadResult`, без дополнительной оболочки и без `null` на верхнем уровне.

Источник структуры — [готовый DTO](../../backend/app/modules/schedule/read_models.py) и его [JSON Schema](../../contracts/fixtures/schedule_read.schema.json). В JSON последовательности сериализуются массивами. Все перечисленные ключи обязательны; nullable-ключи присутствуют со значением `null`.

| Поле | Тип и смысл |
| --- | --- |
| `id` | UUID активной сохранённой версии |
| `planned_date` | Локальная дата `YYYY-MM-DD`, соответствующая query `date` |
| `timezone` | IANA-пояс сохранённого результата; используется при отображении времени |
| `version` | Целое от 1, версия расписания; не является версией задачи |
| `algorithm_version` | Непустая строка версии алгоритма, записанная вместе с планом |
| `generated_at` | UTC-момент генерации сохранённой версии |
| `slots` | Массив сохранённых занятых интервалов по возрастанию начала |
| `unscheduled` | Массив нераспределённых задач и причин |
| `metrics` | Сохранённые метрики планировщика |
| `warnings` | Массив сохранённых предупреждений |
| `moves` | Массив сохранённых автоматических переносов |

### Вложенные объекты

| Объект | Поля |
| --- | --- |
| `slots[]` | `id: UUID`, `kind: task/break/lunch/rest`, `task_id: UUID/null`, `start_at`, `end_at`, `is_pinned: boolean`, `reason_codes: string[]`, `explanation: string/null` |
| `unscheduled[]` | `task_id: UUID`, `reason_codes: string[]` |
| `metrics` | `requested_min`, `planned_min`, `capacity_min`, `high_intensity_min`, `critical_level`, `moved_min` — целые; `load_factor` — число |
| `warnings[]` | `code: string`, `message: string`, `level: info/warning/critical`, `task_id: UUID/null`, `target_date: YYYY-MM-DD/null` |
| `moves[]` | `task_id: UUID`, `from_date: YYYY-MM-DD`, `to_date: YYYY-MM-DD`, `reason_code: string` |

`start_at`, `end_at`, `generated_at` — ISO 8601 в UTC с `Z`. Конец интервала позже начала. Только `kind=task` имеет ненулевой `task_id`; системные интервалы имеют `task_id=null`. Свободные промежутки не превращаются в отдельный вид слота.

Метрики передаются из Reader без пересчёта: запрошенные, запланированные, доступные, интенсивные и перенесённые минуты, уровень критичности и коэффициент нагрузки. Машинные коды причин и предупреждений остаются строками; HTTP-слой не вводит новый enum и не заменяет сохранённые объяснения. Клиент должен выдерживать незнакомый код, используя доступный текст или общее представление.

`user_id`, `is_active`, внутренний `summary`, `score`, граф `future_plans`, `status_changes`, ORM-объекты и сведения о других пользователях в ответ не включаются. Поля задач и рабочие часы также не добавляются в DTO. Фронтенд получает задачи через CRUD, часы через профиль и строит адаптер к своему `DailySchedule`.

### План без задач и отсутствие плана

- Существующий сохранённый план без задач — `200` с обычным DTO, метаданными и метриками. В `slots` могут остаться обед, перерывы и отдых; пустота списка задач не означает обязательное `slots=[]`.
- Если в готовом DTO массивы пусты, они передаются как `[]`, без подстановки `null` или удаления ключей.
- Нет активной сохранённой версии для владельца и дня — `404 SCHEDULE_NOT_FOUND`. Задачи на этот день сами по себе не означают, что план существует.
- Неполный сохранённый результат — `409 SCHEDULE_RESULT_INCOMPLETE`; ошибка Reader не маскируется пустым или отсутствующим расписанием.

## 3. Ошибки

Все ошибки используют общий `ErrorResponse`: `{error: {code, message, details}}`, `details` по умолчанию `{}`. Заголовок `Cache-Control: no-store` обязателен и при ошибках. Для реализации переиспользуется `PrivateAPIRoute`.

| HTTP | Код | Условие |
| --- | --- | --- |
| 401 | `AUTHENTICATION_REQUIRED` | Нет действующей авторизации или активной сессии |
| 403 | `EMAIL_NOT_VERIFIED` | Email не подтверждён |
| 409 | `ONBOARDING_REQUIRED` | Нет профиля или онбординг не завершён |
| 404 | `SCHEDULE_NOT_FOUND` | Для пользователя и дня нет активного сохранённого расписания |
| 409 | `SCHEDULE_RESULT_INCOMPLETE` | Reader обнаружил неполный сохранённый результат |
| 422 | `VALIDATION_ERROR` | Ошибка query; сообщения находятся в `details.fields[]`, пути начинаются с `query` |
| 503 | `SERVICE_UNAVAILABLE` | Существующая общая зависимость авторизации недоступна, например отсутствует JWT-конфигурация |
| 500 | `INTERNAL_ERROR` | Непредвиденная техническая ошибка через общий обработчик; внутренние детали не выдаются |

Для новых ошибок маршрута фиксируются сообщения: `SCHEDULE_NOT_FOUND` — «Расписание не найдено»; `ONBOARDING_REQUIRED` — «Сначала завершите настройку профиля». Ошибка `SCHEDULE_RESULT_INCOMPLETE` передаётся из Reader с его сообщением «Сохранённый результат расписания неполон». Их `details` — `{}`.

Отсутствие профиля проверяется до поиска расписания, когда авторизация и query корректны. При нескольких одновременно некорректных частях запроса клиент не должен зависеть от порядка ошибок авторизации и валидации FastAPI.

`PLANNER_UNAVAILABLE`, `PLAN_CAPACITY_EXCEEDED` и ошибки попытки генерации этим GET не создаются: планировщик не вызывается. Ошибка БД не переименовывается в отсутствие плана.

## 4. Примеры для фронтенда и OpenAPI

В [schedule_read_examples.json](../../contracts/fixtures/schedule_read_examples.json) подготовлены именованные примеры:

| Ключ | HTTP | Назначение |
| --- | --- | --- |
| `day_with_tasks` | 200 | Обычный сохранённый день с task-слотом и обедом |
| `empty_day` | 200 | Сохранённый день без задач, с обедом и ненулевой ёмкостью |
| `missing_schedule` | 404 | Отсутствие плана |
| `onboarding_required` | 409 | Незавершённая настройка |
| `incomplete_schedule` | 409 | Неполный сохранённый результат |

Значение каждого ключа — тело HTTP-ответа; статус задаётся таблицей, а не полем JSON. Примеры иллюстрируют контракт и не являются эталонными результатами расчёта биоритмов. Даты, UUID и версия алгоритма в них не зашиваются в обработчик.

Пример отсутствия плана:

```json
{
  "error": {
    "code": "SCHEDULE_NOT_FOUND",
    "message": "Расписание не найдено",
    "details": {}
  }
}
```

## 5. Граница реализации и приёмка

На шаге 4 добавляется отдельный router чтения с тегом `schedule` и регистрацией в приложении. Он использует существующие `get_current_user`, `get_schedule_reader` и `ScheduleReadResult`. Обязательная дата валидируется по тем же правилам календарной даты, что в CRUD; повторы и неизвестные query-параметры отклоняются до вызова Reader. HTTP-обёртка проверяет завершённый онбординг и вызывает Reader в транзакции чтения.

Не добавляются генерация, пересчёт, автоматическое исправление повреждённых данных, изменения версий и статусов, блокировки для записи или миграции. Поиск остаётся ограниченным текущим владельцем. Возвращается активная версия, наблюдаемая при чтении; последовательные GET могут различаться, если между ними прошла штатная запись. Без параллельных изменений повторное чтение сохраняет ID и версии.

Приёмка HTTP-реализации на шагах 4–5:

- `200` соответствует `ScheduleReadResult` и JSON Schema; OpenAPI публикует Bearer, обязательный `date`, успешную схему и общие ошибки.
- Проверены обычный день, отсутствие плана и существующий день без задач, включая системные интервалы.
- Все четыре вида слотов, причины нераспределения, метрики, предупреждения и переносы проходят из готового Reader без потерь.
- Нет токена, неподтверждённый email и незавершённый онбординг обрабатываются отдельно; данные второго пользователя недоступны.
- Пропуск, пустая/невозможная дата, timestamp, повтор `date` и неизвестные параметры дают `422`.
- UTC-моменты, сохранённый пояс и переход DST не подменяются текущим поясом компьютера или профиля.
- Неполный результат даёт `409`, а повторный GET не пишет в БД и не вызывает планировщик.
- После обычного изменения задачи читается результат существующей интеграции; её алгоритмы и хранение не меняются.

Готовность шага 3 означает зафиксированный контракт и проверяемые примеры. Прохождение HTTP-приёмки и наличие метода в запущенном API здесь не заявляются.
