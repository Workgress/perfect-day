# Сверка CRUD задач и чтения расписания с фронтендом

Дата: **18 ноября 2026 года**. Шаг 1 задачи «Сверка CRUD с фронтендом, согласование ограничений полей; подготовка публичного API чтения расписания». База сверки: `4db84f6`, ветка `feature/tasks-contract-schedule-read-backend`.

## 1. Статус и границы сверки

CRUD содержит восемь HTTP-операций. Интеграция изменения задач с пересчётом уже подключена. Готовы внутренний `ScheduleReader`, публично пригодная модель результата и её JSON Schema; HTTP-маршрута чтения расписания пока нет.

Форма создания задачи в `NewTaskPage` сохраняет результат только в React state для предпросмотра. Редактирование и таймлайн доступны на dev-экранах с фикстурами. В `shared/api` нет специализированных клиентов CRUD задач и чтения сохранённого расписания; обращения к `/tasks` в `http.test.ts` проверяют общий HTTP-клиент. Это незавершённая интеграция, а не установленная регрессия работающего сохранения.

Этот документ фиксирует наблюдаемое поведение и предложения для следующего шага. Он **не подтверждает согласование с фронтендером**. Исходный `backend-plan-v2.md` описывает весь проект; его указания не расширяют текущую задачу. При расхождении с ним ниже отдельно отмечено фактическое поведение.

Работа второго бэкендера не входит в изменения: Core, подключение пересчёта, атомарность записи, хранение результата, слоты, системные интервалы, нераспределённые задачи и автоматические переносы. В этой сверке их реализация не менялась.

Источники состояния фронтенда: [создание](../../frontend/src/pages/today/NewTaskPage.tsx), [редактирование](../../frontend/src/pages/today/EditTaskDialog.tsx), [таймлайн на фикстурах](../../frontend/src/pages/today/TimelinePreviewPage.tsx), [маршруты](../../frontend/src/app/router/routes.tsx).

## 2. Фактический контракт CRUD

Источник HTTP-схем — OpenAPI, полученный локально вызовом `create_app().openapi()` из текущих исходников. Живой сервер отдельно не опрашивался. Бизнес-правила дополнительно сверены с сервисом: OpenAPI не описывает все проверки и последствия пересчёта.

Все пути ниже относительны `/api/v1`. Требуются Bearer и подтверждённый email. Ответы, включая ошибки, используют `Cache-Control: no-store`. Пользователь определяется токеном.

| Метод | Запрос | Успешный ответ |
| --- | --- | --- |
| POST `/tasks` | `TaskCreate` | `201 TaskResponse` |
| GET `/tasks` | Фильтры и пагинация | `200 TaskList` |
| GET `/tasks/{task_id}` | UUID в пути | `200 TaskResponse` |
| PATCH `/tasks/{task_id}` | `TaskPatch` с `version` | `200 TaskResponse` |
| DELETE `/tasks/{task_id}` | `version` в query | `204`, без тела |
| POST `/tasks/{task_id}/complete` | `{"version": N}` | `200 TaskResponse` |
| POST `/tasks/{task_id}/skip` | `{"version": N}` | `200 TaskResponse` |
| POST `/tasks/{task_id}/reopen` | `{"version": N}` | `200 TaskResponse` |

### Поля и ограничения

| Поле | Фактическое правило сервера | Состояние фронтенда |
| --- | --- | --- |
| `title` | Обязательно при создании; trim; 1–200 символов | Trim и диапазон совпадают для обычного текста; различие Unicode см. F-04 |
| `description` | Строка или `null`, по умолчанию `null`; явного максимума нет | Строка обрезается по краям, пустая превращается в `null`; это дополнительная нормализация клиента |
| `type` | Обязательно; `intellectual`, `physical`, `creative`, `routine` | Перечисление совпадает |
| `priority` | `high`, `medium`, `low`; default `medium` | Перечисление и начальное значение совпадают; клиент передаёт явно |
| `duration_min` | Обязательно; строго целое 5–480, без bool и числовых строк | `Number.isInteger` и диапазон совпадают; пресеты не ограничивают произвольную длительность |
| `planned_date` | Обязательно; локальная дата `YYYY-MM-DD` в поясе профиля; прошлые даты допустимы | Запрещает новую прошлую дату, сохраняя исходную при редактировании — F-02 |
| `deadline` | `null` либо момент с явным UTC-смещением; ответ в UTC; локальная дата дедлайна не раньше `planned_date` | Преобразование из пояса профиля и проверка дня есть; новый просроченный момент запрещён — F-03 |
| `version` | Целое от 1; обязательно для PATCH, удаления и команд статуса; не принимается при создании | Тип PATCH и редактирование содержат версию; реальный цикл чтения/записи ещё не подключён |
| `preferred_start`, `is_pinned`, `pinned_start` | Только в ответе; POST/PATCH отклоняют даже `null`/`false` | Включены в тип запроса и всегда формируются — F-01 |
| `id`, `status`, служебные моменты | Назначает сервер; прямой записи через POST/PATCH нет | `Task` содержит ID, статус, `completed_at`, версию; `created_at` и `updated_at` отсутствуют в типе — F-07 |

В PATCH пропуск поля сохраняет значение, `null` очищает только `description` и `deadline`. Тело только с `version` и неизвестные поля отклоняются. Форма редактирования сейчас формирует все поля формы, а не минимальный diff; после исключения запрещённых полей полный набор допустимых полей сам по себе не запрещён сервером.

GET списка принимает `date` либо `from`/`to` включительно, `status`, `type`, `limit` (1–100, default 50), `offset` (от 0, default 0). `date` нельзя сочетать с диапазоном. Повторы, неизвестные параметры, некорректный диапазон отклоняются. Ответ: `{items, total, limit, offset}`; `total` считается до пагинации. Порядок: `planned_date`, `created_at`, `id`.

Чтение задач доступно без профиля. Для записи нужен профиль с корректным timezone, иначе `409 PROFILE_INCOMPLETE`; завершение онбординга для самого CRUD не требуется. Чужая, удалённая или отсутствующая задача даёт `404 TASK_NOT_FOUND`.

### Статусы, версии и пересчёт

- Публичный `TaskService` через dependency получает `ScheduleService` как `coordinator`. Координатор вызывается **внутри транзакции изменения задачи**, затем задача перечитывается и формируется ответ. После commit остаётся отдельный хук `on_changed`, по умолчанию без действий; он не является основным механизмом пересчёта.
- При завершённом онбординге пересчитываются затронутые даты. Изменение названия/описания и реальный no-op не создают новую версию расписания. Без завершённого онбординга задача может сохраниться без расписания.
- Созданная задача до пересчёта имеет `pending`, но HTTP-ответ после интеграции может содержать `scheduled`, изменённую дату и увеличенную версию. Клиент должен использовать фактически возвращённые поля, а не вычислять версию как предыдущую плюс один.
- `complete`: `pending`/`scheduled` → `done`; `skip`: `pending`/`scheduled` → `skipped`; `reopen`: `done`/`skipped` → `pending` до возможного пересчёта. Недопустимый переход даёт `409 TASK_STATUS_CONFLICT`.
- Устаревшая версия даёт `409 TASK_VERSION_CONFLICT`, в том числе при повторе совпадающих значений. No-op с актуальной версией не меняет задачу. У закреплённой задачи изменение полей размещения даёт `409 TASK_PINNED`; название и описание редактировать можно.
- Ответы записи сохраняют формат `TaskResponse` либо `204`, без `{task, schedule, changes}`. Идемпотентные клиентские ID и `Idempotency-Key` для CRUD не поддерживаются.

## 4. Граница готового чтения расписания

`ScheduleReader.get(user_id, day)` возвращает `ScheduleReadResult | None` для активной сохранённой версии. Чтение ограничено владельцем, не генерирует отсутствующий день и не пересчитывает расписание. Пояс берётся из сохранённого результата.

| Часть | Уже готовое представление |
| --- | --- |
| Метаданные | `id`, `planned_date`, `timezone`, `version`, `algorithm_version`, `generated_at` |
| Слоты | `slots[]`: ID, `kind` (`task`/`break`/`lunch`/`rest`), `task_id`, UTC-моменты начала/конца, закрепление, коды причин, объяснение |
| Нераспределённые задачи | `unscheduled[]`: `task_id`, `reason_codes` |
| Метрики | `requested_min`, `planned_min`, `capacity_min`, `high_intensity_min`, `critical_level`, `load_factor`, `moved_min` |
| Предупреждения и переносы | `warnings[]`, `moves[]`; без внутреннего графа `future_plans` и `status_changes` |

Проверка завершённого онбординга, HTTP-ошибки и валидация query остаются ответственностью будущего HTTP-слоя, а не самого Reader. Неполный сохранённый результат Reader уже сообщает как `409 SCHEDULE_RESULT_INCOMPLETE`.

Согласованные с пользователем рамки нового API: `GET /api/v1/schedule?date=YYYY-MM-DD`, Bearer, один день, готовый DTO без вложенных задач и рабочих часов, `404` при отсутствии, без генерации. Это решение для будущего маршрута, **не описание существующего HTTP API**. Исходный план проекта предлагает `/schedule/{date}` и оболочку результата записи `{task, schedule, changes}`; они не вводятся автоматически вместо выбранного контракта.

При подключении UI нельзя считать одну страницу `/tasks?date=...` полным набором задач: default limit — 50. Таймлайн требует запись задачи для каждого task-слота. Исторические сохранённые интервалы могут ссылаться на мягко удалённые задачи, которые CRUD уже не возвращает; контракт отображения такого случая нужно согласовать отдельно при фронтендовой интеграции, не менять ради него готовое хранение коллеги.

Источники: [Reader](../../backend/app/modules/schedule/reader.py), [DTO](../../backend/app/modules/schedule/read_models.py), [JSON Schema](../../contracts/fixtures/schedule_read.schema.json), [проверки чтения](../../backend/tests/db/test_schedule_reader.py).
