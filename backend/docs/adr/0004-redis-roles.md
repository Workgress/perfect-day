# ADR 0004. Роли Redis

**Статус:** принято · 2026-10-27

## Контекст

Redis нужен как кэш, брокер Celery, хранилище результатов задач, счётчики лимитов запросов и pub/sub для WebSocket. Отдельный инстанс под каждую роль избыточен для проекта такого размера.

## Решение

Один инстанс, роли разнесены по логическим базам:

| DB | Роль | TTL |
|---|---|---|
| 0 | кэш (`fastapi-cache2`, префикс `pd`), лимиты запросов | обязателен; по умолчанию 1 ч |
| 1 | брокер Celery | нет |
| 2 | результаты Celery | 1 ч (`result_expires`) |
| — | pub/sub `user:{id}` | каналы не зависят от номера БД |

Конфигурация (`redis/redis.conf`): `maxmemory 256mb`, `maxmemory-policy volatile-lru`, `appendonly yes`, `appendfsync everysec`. Пароль задаётся переменной `REDIS_PASSWORD` (в dev можно не задавать).

## Последствия

- При нехватке памяти вытесняются только ключи с TTL, то есть кэш; очереди Celery не теряются. Отсюда правило: **у любого кэш-ключа должен быть TTL**.
- AOF сохраняет очередь при перезапуске Redis.
- Если нагрузка вырастет, кэш выносится в отдельный инстанс заменой `REDIS_URL` для кэша, без изменения кода.
