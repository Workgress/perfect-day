# CRUD задач: передача спринта

Реализованы создание, чтение, редактирование, перенос даты, выполнение, пропуск, возврат в работу и мягкое удаление задач. API доступен в группе `tasks` в `/docs`; схемы и методы публикуются в `/openapi.json`. Источник требований — [контракт, раздел 12](../../docs/api/contract.md#12-crud-задач-контракт-спринта).

## Фронтенду

- Базовый путь `/api/v1/tasks`, авторизация `Authorization: Bearer <access_token>`. Refresh-cookie не заменяет access-токен. Для записи требуется существующий профиль с корректным `timezone`; завершение онбординга не требуется. При `409 PROFILE_INCOMPLETE` проверить GET `/me` и сохранить пояс через существующий PATCH `/me/profile`.
- POST принимает обязательные `title`, `type`, `duration_min`, `planned_date` и необязательные `description`, `priority`, `deadline`. ID назначает сервер. Приоритет по умолчанию `medium`; описание и дедлайн по умолчанию `null`.
- `planned_date` — локальная дата в поясе профиля. `deadline` — необязательный момент с датой, временем и UTC-смещением; ответ нормализован в UTC с `Z`. Для `datetime-local` формы преобразование делается в IANA-поясе профиля, а не автоматически в поясе компьютера.
- В предложении фронтенда есть `preferred_start`, `is_pinned`, `pinned_start`: текущий CRUD возвращает их только для чтения. Не отправлять их в POST/PATCH даже со значениями `null`/`false`; неизвестные поля дают `422`. Фронтендовая ветка не объединялась и требует адаптации.
- PATCH принимает `version` прочитанной задачи и хотя бы одно изменяемое поле. Пропущенные поля сохраняются; только `description` и `deadline` можно очистить через `null`. Перенос выполняется изменением `planned_date`; для переноса за дедлайн нужно одновременно изменить или очистить дедлайн.
- POST `/tasks/{task_id}/complete`, `/skip`, `/reopen` принимают `{"version": N}`. Статус через PATCH не задаётся. `scheduled` предназначен для будущей интеграции планировщика; создание всегда даёт `pending`.
- POST возвращает `201 TaskResponse`, PATCH и команды статуса — `200 TaskResponse`. Оболочки `{task, schedule, changes}` нет. DELETE `/tasks/{task_id}?version=N` возвращает пустой `204`: JSON разбирать не нужно.
- GET списка принимает `date` либо включительный диапазон `from`/`to`, дополнительно `status`, `type`, `limit`, `offset`. Ответ `{items, total, limit, offset}`; пустая страница при большом offset сохраняет полный `total`. Повторы query-параметров отклоняются.
- После `409 TASK_VERSION_CONFLICT` сохранить черновик и перечитать задачу. После удаления все обращения к задаче дают `404`. После потери ответа записи сначала проверить состояние; автоматический повтор POST может создать дубликат. Клиентские ID и `Idempotency-Key` для CRUD не поддерживаются.
- Любое реальное изменение увеличивает версию ровно на один. Повтор команды с актуальной версией и уже достигнутым статусом либо PATCH с совпадающими значениями не меняет версию, время и события. Устаревшая версия конфликтует и при таком повторе.

Пример POST `/api/v1/tasks`:

```json
{
  "title": "Подготовить отчёт",
  "type": "intellectual",
  "duration_min": 60,
  "planned_date": "2026-11-13",
  "deadline": "2026-11-13T18:00:00+05:00"
}
```

При профиле `Asia/Yekaterinburg` ответ содержит `deadline="2026-11-13T13:00:00Z"`, `status="pending"`, `version=1`. Затем PATCH с `{"version":1,"description":"Обновить таблицы"}` возвращает версию 2; `/complete` с `{"version":2}` — `done` и версию 3.

## Второму бэкендеру

- CRUD не рассчитывает энергию, слоты, перерывы или критические дни и не изменяет `schedules`/`schedule_slots`. Изменение задачи не означает, что сохранённое расписание пересчитано. Проверка ёмкости дня и генерация плана остаются интеграцией планировщика.
- Точка подключения — `app.modules.tasks.dependencies.get_task_changed_handler`. Она возвращает асинхронный обработчик `TaskChanged`; по умолчанию он ничего не делает. Поля события и операции описаны в [контракте, 12.7](../../docs/api/contract.md#127-ошибки-и-будущая-интеграция).
- Событие вызывается после commit задачи; при rollback или отсутствии реальных изменений не вызывается. Это не outbox и не надёжная очередь: доставка, повторы, сбои обработчика и согласованная фиксация задачи с расписанием требуют отдельного решения при интеграции.
- `TaskService` сам открывает и завершает транзакцию. Его публичные методы нельзя вызывать внутри уже открытой транзакции для попытки атомарно сохранить задачу и расписание. Репозиторий делает только flush/refresh; бизнес-версии, статусы и события назначает сервис.
- `Task.deadline` теперь `datetime | None`, в PostgreSQL — `timestamptz`; сравнение только дат больше не описывает точный срок. `planned_date` остаётся локальной датой. Типы, приоритеты и статусы переиспользуются из существующих enum модуля задач.
- При будущих изменениях публичных полей задачи планировщиком нужны блокировка строки, увеличение версии и обновление времени. Поле `moved_from_date` зарезервировано для автоматического переноса и текущим ручным CRUD не заполняется.

## Миграция и запуск

Новая единственная локальная head — `0006`, родитель `0005`. Старые ревизии сохранены. Дедлайны-даты переводятся в конец указанного дня в текущем поясе профиля, без профиля — в UTC; `NULL` сохраняется. Downgrade теряет время и оставляет дату в текущем поясе профиля. Подробности — [схема БД](db.md#работа-с-миграциями).

Использовать существующий `backend/.env` с постоянным `JWT_SECRET`. Для входа из Swagger Origin `http://localhost:8000` должен быть в `CORS_ORIGINS`. Из `backend` запустить `docker compose up -d --build --wait`; команда применяет миграции локального стенда. Полная ручная проверка — [контракт, 12.9](../../docs/api/contract.md#129-ручная-проверка-http-после-шага-6). Доступ восстанавливается существующими `/auth/password/forgot` и `/auth/password/reset`, затем нужен новый вход.

## Проверка и готовность

На шаге 7 полный набор бэкенда прошёл: 1437 тестов за 7 минут 11 секунд; покрытие модуля задач — 398 строк и 68 измеряемых ветвей, 100%. Это измерение покрытия, а не гарантия отсутствия всех возможных ошибок. Ручную проверку Swagger пользователь также выполнил успешно.

На шаге 8 OpenAPI запущенного локального API совпал с исходниками: 8 операций задач и 9 публичных схем, включая общую ошибку. Повторно прошли 80 проверок схем/OpenAPI, общие Ruff и mypy; Compose-конфигурация корректна. Запущенная локальная БД находится на `0006 (head)`; `alembic check` не обнаружил расхождений с ORM. Объявления зависимостей совпадают с metadata `uv.lock`. Изменения шага 8 относятся к документации, бизнес-код после полного прогона не менялся.

Проверки из `backend` при запущенном Docker Desktop:

```powershell
$env:DEBUG = "false"
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
.\.venv\Scripts\python.exe -m mypy app
.\.venv\Scripts\python.exe -m alembic heads
.\.venv\Scripts\python.exe -m pytest tests/unit/test_tasks_openapi.py tests/unit/test_task_schemas.py -q
```

Ожидаются `0006 (head)` и `80 passed`. Полный повтор при изменении кода: `.\.venv\Scripts\python.exe -m pytest -q --cov=app.modules.tasks --cov-branch --cov-report=term-missing`. Тесты используют отдельные PostgreSQL, Redis и Mailpit, не БД ручного стенда.

CRUD готов к ревью. Перед объединением повторно сверить общую Alembic head с веткой коллеги. Генерация расписания, pin/unpin, ввод предпочтительного времени и фактических интервалов, офлайн-синхронизация, фронтендовая интеграция, preview, завершение онбординга и изменение ответа регистрации не входят в завершённый спринт CRUD.
