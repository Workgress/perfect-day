# Профиль и биоритмы: спецификация реализации

Дата: 2026-11-07. Этап 1 — границы задачи и правила расчёта.

Документ фиксирует контракт для последующих этапов реализации. Он не означает,
что перечисленные эндпоинты уже доступны. Основание — разделы 4.2, 5, 9.1,
10.1, 10.3, 10.4 и этапы 2–3 общего плана `backend-plan-v2.md`.
Уточнения, которых нет в исходном плане, явно перечислены в конце документа.

## 1. Объём и текущее состояние

В задачу входят профиль текущего пользователя, перевод данных рождения в UTC,
чистое математическое ядро на NumPy, критические дни, временные ряды, прогнозы,
Redis-кэш расчётов, HTTP-контракты и эталонные данные для фронтенда.

В репозитории уже есть:

- `app/modules/users/models.py`: `User`, `UserProfile`, перечисления хронотипов;
- миграция `0002_users.py`: таблицы пользователей и профилей;
- `app/core/redis.py`: асинхронный Redis-клиент;
- `app/main.py`: инициализация `fastapi-cache2`, общий префикс `pd`;
- ADR [0002](adr/0002-utc-time.md), [0003](adr/0003-biorhythms-computed-not-stored.md)
  и [0004](adr/0004-redis-roles.md).

Модуль аутентификации, зависимость `current_user`, профильные роутеры,
сервис времени и модуль биоритмов пока отсутствуют. Для профиля сначала нужно
использовать существующую модель и ограничения, а не создавать таблицу повторно.
На этапе 1 миграции и исполняемый код не менялись.

Вне задачи: регистрация и JWT, тест хронотипа, создание расписания,
рекомендации по нагрузке, уведомления и офлайн-синхронизация. Полноценный
`POST /onboarding/complete`, возвращающий дашборд, относится к интеграции
с онбордингом и планировщиком. Поле `onboarding_completed_at` остаётся
серверным, PATCH профиля не завершает онбординг автоматически.

Математическое ядро можно реализовывать независимо от auth. HTTP-интеграция
требует `current_user` и механизма завершения онбординга от соответствующего
модуля. В API нельзя подменять их произвольным `user_id` из запроса.

Роутер не обращается к БД напрямую. Ядро не импортирует ORM, FastAPI, Redis

имеют один источник; будущий `/meta/algorithm` использует его же.

## 3. Данные профиля

`GET /me` возвращает `{id, email, is_email_verified, profile,
onboarding_completed}`. `profile` может быть `null`, пока профиль не создан.
Хэш пароля, служебные данные сессий и поля удаления не возвращаются.
`onboarding_completed` определяется по `onboarding_completed_at`.

`PATCH /me/profile` создаёт профиль при его отсутствии либо частично обновляет
существующий. Ответ — полный публичный профиль. Данные проверяются после
слияния с существующим состоянием; сохранение происходит одной транзакцией.
Пустой объект допустим: возвращает существующий профиль или создаёт профиль
с настройками по умолчанию. Неизвестные поля отклоняются с 422.

| Поле PATCH | Правило |
|---|---|
| `display_name` | строка после удаления пробелов по краям, 1–100 символов; `null` очищает |
| `birth_date` | локальная дата рождения, от 1900-01-01 до текущей даты в `birth_tz` |
| `birth_time` | локальное время рождения без UTC-смещения |
| `birth_time_known` | булево; `false` означает расчёт от 12:00 |
| `birth_tz` | IANA-пояс места рождения |
| `timezone` | IANA-пояс отображения и определения локальных дней |
| `chronotype` | `lark`, `dove`, `owl`; ручной выбор устанавливает источник `manual` |
| `wake_time`, `sleep_time` | локальное время; сон через полночь допустим, равные значения запрещены |
| `lunch_start` | локальное время начала обеда |
| `lunch_duration_min` | целое 0–180, в соответствии с существующей схемой БД |
| `work_start`, `work_end` | локальное время, `work_end > work_start` |
| `work_days` | уникальные целые 1–7; пустой список допустим |

Локальные значения времени имеют формат `HH:MM[:SS]`, точность до секунды,
без смещения и дробных секунд. Настройки рабочего окна через полночь пока
не поддерживаются существующим CHECK-ограничением; режим сна через полночь
не меняет это правило. Проверки размещения задач выполняет будущий планировщик.

Настройки нового профиля повторяют модель: `timezone=UTC`, сон 07:00–23:00,
рабочее окно 08:00–18:00, дни 1–5, обед с 12:00 на 60 минут.
`birth_time_known=true` само по себе не означает готовность данных рождения.

Пропущенное поле PATCH сохраняет значение. Явный `null` допустим только
для `display_name`, `birth_date`, `birth_time`, `birth_tz`, `chronotype`.
До завершения онбординга эти поля могут быть не заполнены. Нельзя очистить
обязательные данные уже завершённого профиля: возвращается 422.
Очистка `chronotype` также очищает `chronotype_source`.

`birth_at_utc`, `chronotype_source`, `onboarding_completed_at`, `updated_at`
и `user_id` доступны только для чтения. Публичный профиль содержит перечисленные
выше поля и эти служебные поля, кроме `user_id`; принадлежность задаёт `/me`.

### Нормализация рождения

1. Проверить IANA-пояса через `zoneinfo`.
2. При наличии даты рождения и отсутствии `birth_tz` записать текущий `timezone`
   как пояс рождения. Применять это после слияния всех полей запроса.
3. Если время неизвестно, записать `birth_time=12:00`. Одновременно переданное
   другое время отклонить с 422; `null` в этом режиме нормализуется в 12:00.
4. Если `birth_time_known=true`, а время отсутствует, профиль остаётся
   незавершённым и `birth_at_utc=null`. При переключении с неизвестного времени
   на известное потребовать явный `birth_time`, чтобы не принять заглушку за факт.
5. Если дата, время и пояс доступны, вычислить `birth_at_utc` на сервере.
   Полученный момент не должен находиться в будущем относительно `Clock`.
6. Если исходных данных недостаточно, очистить производный `birth_at_utc`;
   для завершённого профиля такое обновление запрещено.

Смена только `timezone` сохраняет уже записанные `birth_tz` и `birth_at_utc`.
Явное изменение `birth_tz` означает исправление места рождения и пересчитывает
`birth_at_utc`. Это также позволяет повторно выбрать текущий пояс через `null`
по правилу пункта 2, если дата рождения задана.

### Неоднозначное и несуществующее время рождения

Не выбирать UTC-смещение молча. Для времени в пропущенном часе или повторяющемся
часе DST возвращать 422 с кодом `BIRTH_TIME_NONEXISTENT` или
`BIRTH_TIME_AMBIGUOUS`. Различать случаи проверкой преобразования в UTC
и обратно для `fold=0` и `fold=1`, сравнивая полученные моменты.
В этой версии контракта нет поля выбора `fold`; пользователь может указать
неизвестное время. Правило применяется и к нормализованным 12:00.

## 4. Временная модель и математические правила

Входные моменты — aware datetime; `at` без `Z` или явного UTC-смещения
отклоняется с 422. В ядре моменты нормализуются в UTC. Длительность суток
в формуле всегда 86400 секунд, независимо от календаря и DST.

```text
PERIODS = {physical: 23, emotional: 28, intellectual: 33}
t = (at_utc - birth_at_utc).total_seconds() / 86400
value = sin(2πt / P)
percent = round_half_even(value * 100, 1)
```

Для совпадения клиента и сервера округление процентов определяется явно:
до ближайшего значения с одним десятичным знаком, при точной середине —
к чётной цифре. Значение `-0.0` сериализуется как `0.0`.

Перед классификацией результат ограничивается диапазоном [-1, 1]. Значения
на расстоянии не более `1e-12` от 0, ±0.5, ±1 приводятся к соответствующей
границе; приоритет — ближайшая граница. Это правило является частью версии
алгоритма. Фаза определяется по нормализованному `value`, а не по `percent`.

| Интервал `value` | `phase` |
|---|---|
| [0.5; 1] | `peak` |
| [0; 0.5) | `rising` |
| (-0.5; 0) | `declining` |
| [-1; -0.5] | `minimum` |

`trend` имеет значения `up` и `down` по знаку косинуса. В экстремуме,
когда `abs(cos) <= 1e-12`, использовать направление сразу после экстремума:
на максимуме `down`, на минимуме `up`. Фаза и направление независимы:
код `rising` описывает диапазон, а не знак производной.

Чистое ядро допускает отрицательное `t` для математических проверок.
Публичное API отклоняет запросы, содержащие точки до `birth_at_utc`, с 422
`BEFORE_BIRTH`; ряды не обрезаются молча.

## 5. Локальные дни, диапазоны и критичность

Дата в query имеет формат `YYYY-MM-DD` и трактуется в `profile.timezone`.
`from` и `to` включительны. Требуется `from <= to`; число локальных дат
`(to - from).days + 1` не больше 62 для ряда и списка критических дней.

Локальный день — полуинтервал `[D_start_utc; D_end_utc)`, где конец вычисляется
из следующей локальной даты. Нельзя заменять его `D_start_utc + 24 часа`.
Если полночь пропущена, границей считается первый существующий момент этой
даты; если повторяется — более ранний момент. Полностью пропущенную локальную
дату отклонять с 422 `LOCAL_DATE_NONEXISTENT`.

Для каждого цикла аналитически найти `k` с пересечением внутри дня:

```text
crossing(k) = birth_at_utc + k * P / 2 суток
D_start_utc <= crossing(k) < D_end_utc
```

Полупериоды кратны половине суток, поэтому границы пересечений можно считать
целочисленной арифметикой длительностей; эпсилон не должен переносить событие
между днями. После получения кандидата проверяется сам UTC-момент.

`critical.level` — число разных циклов с пересечением, от 0 до 3.
`critical.kind` — `none`, `single`, `double`, `triple` соответственно.
`crossings` содержит `{cycle, at}`, сортируется по UTC-моменту, затем
по порядку `physical`, `emotional`, `intellectual`.
Нулевой момент рождения (`k=0`) считается пересечением.
Список критических дней возвращает только дни с `level > 0`.

## 6. Сетки и прогноз

- `step=day`: одна точка в 12:00 каждой локальной даты.
- `step=hour`: сетка от начала каждого локального дня с шагом 3600 секунд
  в UTC, пока момент меньше конца дня. В обычные дни получается 24 точки,
  при часовом DST — 23 или 25. Повторяющиеся часы имеют разные UTC-смещения.
- Если локальные 12:00 неоднозначны, выбрать более ранний момент. Если они
  не существуют, вернуть 422 `LOCAL_TIME_NONEXISTENT`, не сдвигая точку молча.

Все времена в JSON — ISO 8601 со смещением `timezone` пользователя;
`birth_at_utc` и служебные метки профиля возвращаются в UTC с `Z`.

Прогноз начинается с локальной даты, вычисленной один раз через `Clock`:

| `period` | Интервал | Шаг |
|---|---|---|
| `day` | текущая локальная дата | `hour` |
| `week` | текущая дата и следующие 6 дат | `day` |
| `month` | от текущей даты до такой же даты следующего месяца, не включая её | `day` |

Для `month`, если такого числа в следующем месяце нет, конечная исключительная
дата — последний день следующего месяца. Например, 2026-11-07 → точки
2026-11-07…2026-12-06; 2027-01-31 → 2027-01-31…2027-02-27.
Это скользящий календарный месяц, а не фиксированные 30 суток.

Краткие рекомендации и оценки нагрузки не входят в математический прогноз:
для них в общем плане предусмотрены отдельные правила и модуль рекомендаций.

## 7. HTTP-контракт

Префикс `/api/v1`. Все шесть эндпоинтов требуют авторизации. Для биоритмов
после авторизации проверяются завершённый онбординг и наличие `birth_at_utc`:
при отсутствии возвращается 409 `ONBOARDING_REQUIRED`. Профиль доступен
до завершения онбординга. Каждый успешный запрос ниже возвращает 200.

| Метод и путь | Параметры / тело | Ответ |
|---|---|---|
| `GET /me` | нет | пользователь, nullable-профиль, флаг онбординга |
| `PATCH /me/profile` | поля раздела 3 | полный публичный профиль |
| `GET /biorhythms/now` | необязательный `at`; без него один вызов `Clock` | `Snapshot` |
| `GET /biorhythms` | обязательные `from`, `to`; `step=day` по умолчанию | `Series` |
| `GET /biorhythms/critical-days` | обязательные `from`, `to` | `CriticalDays` |
| `GET /biorhythms/forecast` | обязательный `period=day\|week\|month` | `Forecast` |

`Snapshot` содержит `algorithm_version`, `timezone`, `at`, `date`, `cycles`
и `critical`. `cycles` всегда содержит три ключа `physical`, `emotional`,
`intellectual`. Каждый цикл содержит числовые `value`, `percent`, строковые
`phase`, `trend`. `critical` относится ко всему локальному дню поля `at`.

`Series` содержит `algorithm_version`, `timezone`, `from`, `to`, `step`, `points`.
Точка: `{at, date, cycles, critical}` с теми же правилами, что у `Snapshot`.
Порядок точек — по возрастанию UTC-момента, без дублей. Пустой список при
валидном диапазоне не возвращается; несуществующая локальная дата — ошибка.

`CriticalDays` содержит `algorithm_version`, `timezone`, `from`, `to`, `days`.
Элемент `days`: `{date, level, kind, crossings}`. Порядок — по локальной дате.
Пустой список допустим, если в диапазоне нет критических дней. Диапазон,
чей начальный день начинается до рождения, отклоняется как `BEFORE_BIRTH`;
для остальных эндпоинтов сравниваются фактические точки расчёта.

`Forecast` содержит поля `Series` и `period`; `from` и `to` показывают
фактические включительные даты рассчитанного прогноза.

Пример содержимого `critical` при отсутствии пересечений:

```json
{"level": 0, "kind": "none", "crossings": []}
```

Пример ошибки:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные параметры запроса",
    "details": {
      "fields": [{"field": "to", "code": "RANGE_TOO_LONG", "message": "Максимум 62 дня"}]
    }
  }
}
```

Ошибки полей возвращаются с HTTP 422 и верхним кодом `VALIDATION_ERROR`;
конкретные коды из этого документа находятся в `details.fields[].code`.
Отсутствующая/недействительная авторизация — 401 `UNAUTHORIZED`, незавершённый
онбординг — 409 `ONBOARDING_REQUIRED`. Сообщения пользователю — на русском.

## 8. Кэш и изменение профиля

Кэшировать результаты биоритмов в Redis DB 0 через существующее подключение
`fastapi-cache2`. TTL — 86400 секунд, явно для этого модуля: общий TTL приложения
сейчас составляет 3600 секунд и не должен менять это требование.

Логическая структура ключа, с сохранением общего префикса `pd`:

```text
pd:bio:{algorithm_version}:{user_id}:{birth_hash}:{timezone_hash}:{request_hash}
```

- `birth_hash`: SHA-256 канонического набора `birth_date`, нормализованного
  `birth_time`, `birth_time_known`, `birth_tz`, `birth_at_utc`.
- `timezone_hash`: SHA-256 IANA-имени текущего пояса.
- `request_hash`: SHA-256 канонических параметров: вид запроса, разрешённый
  `at` в UTC или включительные даты диапазона, `step`, `period` при наличии.
- Канонизация: UTF-8 JSON, отсортированные ключи, компактные разделители,
  даты ISO 8601, UTC-моменты с единым представлением и точностью до микросекунд.
- `at` и начальная дата прогноза разрешаются до формирования ключа. Строка
  `now` или один только `period` не являются достаточными параметрами ключа.
- Сначала авторизация, проверка профиля и валидация; затем чтение кэша.
  Ошибки и данные чужого пользователя не кэшируются.
- NumPy-типы перед записью преобразуются в обычные JSON-типы; NaN/Infinity
  недопустимы. Ответы попадания и промаха имеют одинаковую структуру.

Изменение исходных данных рождения или текущего пояса меняет ключ. Старые
значения истекают по TTL, удаление через `KEYS` или `SCAN` не требуется.
Изменение версии алгоритма тоже создаёт новое пространство ключей.
Хронотип и режим дня не влияют на синусоиды и не входят в ключ биоритмов.
Сам профиль в этой задаче не кэшируется.

Ошибка соединения/тайм-аут Redis означает расчёт без кэша. Использовать
ограниченное ожидание существующего клиента; ошибки математики и валидации
нельзя скрывать как сбой кэша. Ошибка записи кэша не отменяет успешный расчёт.

Обновление профиля формирует перечень изменённых полей для будущего обработчика
`profile_changed`. Пересчёт расписаний подключается отдельным этапом после
реализации сервиса расписания; сейчас нельзя обещать его через PATCH.

## 9. Проверки и критерии завершения всей задачи

Тесты добавляются вместе с соответствующими реализациями:

- математика: контрольные точки, периодичность, диапазон, границы фаз,
  направление в экстремумах, одинаковые одиночный и векторный расчёты;
- время: UTC, `Asia/Yekaterinburg`, `Europe/Moscow`, `Europe/Berlin`,
  `America/New_York`; 23/25-часовые дни, неоднозначное рождение, високосный год;
- критичность: точные границы полуинтервала, одинарный/двойной/тройной день,
  число пересечений в интервале длиной `N*P` равно `2*N`;
- профиль: частичный PATCH, null, исходные значения, неизвестное время,
  изменение текущего пояса без изменения момента рождения, изоляция пользователей;
- API и Redis: авторизация, guard онбординга, валидация, предел 62 дней,
  совпадение ответа при промахе/попадании, TTL, смена ключа и отказ Redis.

Не использовать «2–3 пересечения за любой месяц» как инвариант: количество
зависит от длины и границ интервала. Эталонные тесты должны проверять точные
моменты, а почасовой перебор может быть только дополнительной проверкой.

Итоговые артефакты: работающие шесть маршрутов, OpenAPI с примерами,
`contracts/fixtures/biorhythm_vectors.json` минимум с 200 точками и генератор,
покрытие ядра не менее 95%, ruff и mypy без ошибок. Контрольные значения
проверять также независимо от генератора фикстур.

## 10. Уточнения относительно общего плана

Для устранения неоднозначностей в этом документе выбраны: включительный `to`,
скользящий календарный месяц, конкретные правила PATCH и DST, направление
после экстремума, численный допуск и округление, полный состав ответов,
версия алгоритма в ключе кэша и работа без Redis при его отказе.
Это решения для последующей реализации; согласованность с клиентом проверяется
по OpenAPI и общим фикстурам. Начальная версия алгоритма — `1.0.0`.

Этап 1 завершён при наличии этой спецификации, сверенной с существующими
моделями и ADR. Следующий этап — сервис времени и профиль пользователя;
создание движка и HTTP-обработчиков относится к последующим этапам.

## 11. Реализация этапа 2

Добавлены `core/time.py`, `users/schemas.py`, `users/repository.py` и
`users/service.py`. Существующая схема БД достаточна, миграции не требуются.
`tzdata` объявлена прямой зависимостью, чтобы `zoneinfo` работал и в Windows.

Сервис получает `AsyncSession` и `Clock`. `get_profile(user_id)` возвращает
публичный профиль либо `None`. `update_profile(user_id, ProfilePatch)` возвращает
`ProfileUpdate`: публичный профиль и `changed_fields` для будущего обработчика
изменений. `user_id` должен поступать из будущего `current_user`, не из тела PATCH.

Внешняя транзакция принадлежит вызывающему коду: после успешного вызова нужно
выполнить `session.commit()` либо использовать внешний `session.begin()`.
Сервис использует savepoint и не делает commit. Блокировка строки пользователя
сериализует обновления, включая одновременное создание отсутствующего профиля.
Валидация завершается до изменения ORM-объекта. Ошибка не оставляет частично
сохранённый профиль, внешняя транзакция остаётся пригодной для работы.

Проверки синтаксиса полей возвращаются как Pydantic `ValidationError`;
межполевые и временные проверки — как `ProfileValidationError` с `field`,
`code` и русским сообщением. HTTP-преобразование ошибок и роутеры добавляются
на этапе 7, вместе с зависимостью авторизации.

Тесты этапа: `tests/unit/test_time.py`, `tests/unit/test_profile_schemas.py`,
`tests/db/test_profile_service.py`. Интеграционные тесты используют временный
PostgreSQL через testcontainers; покрывают частичный PATCH, защиту завершённого
профиля, откат и конкурентные обновления в отдельных транзакциях.

## 12. Реализация этапа 3

Добавлен пакет `app/modules/biorhythm/`:

- `config.py` — версия 1.0.0, неизменяемые периоды, порог фаз и численный допуск;
- `types.py` — перечисления циклов, фаз и трендов, dataclass-результаты;
- `engine.py` — `cycle_value`, `phase`, `percent`, `snapshot`, `series`.

Одиночный расчёт возвращает `float`; `snapshot` — `BioSnapshot` с UTC-моментом
`at` и словарём `cycles`. Значения цикла имеют поля `value`, `percent`, `phase`,
`trend`. Ядро не обращается к БД, Redis, HTTP или текущему времени. Поля
критичности и публичные Pydantic-схемы будут добавлены на следующих этапах.

`series(birth_utc, moments)` принимает последовательность aware datetime либо
одномерный NumPy-массив `dtype=object` с такими моментами. Массивы `datetime64`
не содержат пояс и отклоняются; нельзя молча считать их локальным временем
или UTC. Возвращается словарь из трёх одномерных массивов `float64`, порядок
и повторы входных моментов сохраняются. Пустой вход даёт три пустых массива.

Временная разность считается в целых микросекундах; перед вычислением синуса
из неё выделяется остаток по периоду. Это сохраняет точную периодичность
и исключает потерю точности из-за большого аргумента синуса для далёких дат.
Тригонометрические расчёты векторизованы одновременно по моментам и циклам.
Проценты рассчитываются как `rint(value * 1000) / 10` с приведением -0.0 к 0.0.

Пример использования:

```python
from datetime import UTC, datetime

from app.modules.biorhythm.engine import snapshot
from app.modules.biorhythm.types import Cycle

birth = datetime(2000, 1, 1, 12, tzinfo=UTC)
at = datetime(2000, 1, 7, 6, tzinfo=UTC)  # четверть физического периода
physical = snapshot(birth, at).cycles[Cycle.PHYSICAL]
assert physical.value == 1.0
assert physical.percent == 100.0
assert physical.phase == "peak"
assert physical.trend == "down"
```

Unit-тесты: `tests/unit/test_biorhythm_engine.py`, включая property-based
проверки Hypothesis. Интеграция с данными профиля проверяется в
`tests/db/test_biorhythm_profile.py`. CI проверяет покрытие строк и ветвей
`biorhythm/engine.py` с порогом 95%.

Команда полного прогона из `backend/` (нужен запущенный Docker):

```text
uv run pytest --cov=app.modules.biorhythm.engine --cov-branch --cov-report=term-missing --cov-fail-under=95
```

Следующий этап — аналитическое определение критических дней; построение
календарных сеток, прогноз, Redis-кэш и HTTP-эндпоинты выполняются после него.

## 13. Реализация этапа 4

В `biorhythm/engine.py` добавлена чистая функция
`critical_info(birth_utc, day, tz)`. В `types.py` добавлены `CriticalKind`,
`CriticalCrossing` и `CriticalInfo`. Результат содержит `level` (0–3),
`kind` (`none`, `single`, `double`, `triple`) и кортеж `crossings`.
У каждого пересечения есть `cycle` и точный aware-момент `at` в UTC.
Локальный пояс определяет принадлежность дню; перевод `at` в пояс отображения
выполняется через `astimezone(tz)`, как и для остальных результатов ядра.

Для каждого цикла рассчитывается длина полупериода в целых микросекундах `H`.
Если `S` и `E` — смещения начала и конца локального дня относительно рождения,
первый кандидат имеет индекс `k = -(-S // H)`. Он принадлежит дню при `k*H < E`.
Начало включено, конец исключён; округления и численный допуск не применяются.
В полупериоде минимум 11,5 суток, поэтому внутри локального дня возможен
максимум один кандидат на цикл. Расчёт проверяет три кандидата, а не сетку часов.

События сортируются по UTC-моменту, при совпадении — в порядке физический,
эмоциональный, интеллектуальный. Уровень равен числу разных циклов. Момент
рождения (`k=0`) включается, отрицательные индексы допускаются в чистом ядре;
ограничение публичных запросов до рождения относится к будущему API.
Переходы DST и пропущенные локальные даты обрабатываются через уже реализованный
`local_day_bounds`; для полностью пропущенной даты выдаётся `LocalTimeError`.

Пример тройного критического дня:

```python
from datetime import UTC, datetime, timedelta
from zoneinfo import ZoneInfo

from app.modules.biorhythm.engine import critical_info

birth = datetime(2000, 1, 1, 12, tzinfo=UTC)
at = birth + timedelta(days=10626)  # общий кратный полупериодов 23/2, 28/2, 33/2
info = critical_info(birth, at.date(), ZoneInfo("UTC"))
assert info.level == 3
assert info.kind == "triple"
assert all(crossing.at == at for crossing in info.crossings)
```

Проверки: `tests/unit/test_biorhythm_critical.py` и интеграция с профилем
в `tests/db/test_biorhythm_profile.py`. Включены точные границы с шагом
в микросекунду, совпадающие и разнесённые пересечения, отрицательные индексы,
23/25-часовые дни, повторяющиеся часы, пропущенная полночь и дата. Результаты
сверяются с независимым почасовым поиском смены знака и property-based перебором
корней; число пересечений в интервале `N*P` суток проверяется как `2*N`.

Версия 1.0.0 сохранена: добавлена предусмотренная контрактом функция,
правила существующих расчётов не изменены. Следующий этап — временные сетки
и прогнозы; HTTP-эндпоинты и кэш подключаются позднее.
